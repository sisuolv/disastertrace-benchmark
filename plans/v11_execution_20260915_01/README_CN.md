## 正在后台执行的固定范围

### 1. 完整季节周五组对照

目录 `fullweek_02/`，登记见 `PLAN.json`、`REGISTRATION.json`。

- 原有纽约、芝加哥、丹佛三个地区，每区三个站点。
- 2025 年 3、6、9、12 月各一个完整周；保留全部七天和全部逐小时机会。
- 1km 与 5km 两个阈值，共 12,096 个目标机会。
- 168 个日会话条件 × 五组 = 840 条轨迹；每个日会话共享 48 次来源查询。
- 五组为 FOLLOW、F_COMMON、F_BASE_ONLY、B11_BATCH、B11_COVERAGE。
- 四个 values 银行条件属于同后端对照；F_COMMON 使用不同银行，单独绑定评分合同。
- 每日新会话，不跨日继承付费缓存；采用 base_bound_override。
- 程序计算/持久化各 1ms 是登记的时延情景，不是部署速度测量。

真实预检和旧/新评分等价证明已通过。前两个 16 核 CPU 分片启动后，平台拒绝第三个
16 核申请：剩余 CPU 配额仅 8 核。第三片已使用 8 核启动，前三片分别使用 12/12/6 个计算进程。
`advance_resume.py` 等待已有作业释放 16 核配额后提交第四片，再提交完整 roster 审计。
当前阶段见 `STATUS_03.json`；`QUOTA_AMENDMENT_03.json` 记录调整，旧失败记录保留。
`finish_batch_02.py` 在审计通过后自动生成
`fullweek_analysis_01/REPORT_CN.md` 与 `RESULT.json`。

报告保留总体、季节周、地区、地区周、逐日、正负例损失贡献和缺失结果敏感性界。
只有四个全局周，不会用逐小时 bootstrap 冒充大量独立天气过程。

### 2. 全年数据获取

`annual_catalog_01/` 固定 2023/2024 两年、九站、两类产品，合计 432 个逻辑分片。
对应 72 个地区月，每地区月六个目录/站报请求。2023 为拟合/内部选择候选资料，
2024 为最终校准候选资料；尚未进行拟合。

先用预先指定的闰月三个地区做样例。样例通过后，脚本继续剩余全年目录。
实际网络请求会因预登记的一次精确重试多于 432；不能将逻辑分片数当作 HTTP 次数。

`annual_native_sample_01/` 是另一个已启动的工作：下载样例中的 2,470 份原生 TAF，
使用已取得的 METAR 构建三个完整月的原生版本/目标/结果连接。
该样例预期包含 12,528 个双阈值机会，但实际完整性须等构建审计通过后确认。
它完成后也仅代表三个完整月，不代表全年所有原文已经取得。

历史查询采用明确的归档可用时间情景，不伪称已证明当年的 first-seen 时刻。
跨年、跨月份的捕获 padding 只是获取范围；拟合前必须按完整证据/结果足迹剔除跨角色依赖。

### 3. C2 的具体落点

`c2_design_01/DESIGN.json` 与 `ROSTER.json` 固定首批范围：原有 12 个地区周，
各取首日 12UTC 的三个站点、两个阈值，共 72 个目标前缀，涉及 24 个日会话条件。
选择规则只依赖日历/目标身份，未按效果或正例筛选。

同状态的四个候选分支为：停止补充查询、取第一个合法邻站槽、取第二个合法邻站槽、
获取其余登记邻站槽。所有分支继承原有时钟、已花/预留预算、共享权限、缓存、pending、
专业基线、当前修订及失败续行规则。无法及时完成的分支保留不可行状态。

`public/TASKS.json` 已构建 144 个原生 TAF 覆盖/版本任务，参考答案独立放在
`evaluator_only/REFERENCES.json`。当前 72 个覆盖任务全部是完整覆盖，因此尚未证明
覆盖任务有足够难度。后续须按固定完整日历普查部分覆盖、订正、冲突、删失与缺报，
同时保留当前样本，不能只挑容易得到模型收益的案例。

真正需要测量的是“原生字段变化 → 特征变化 → 概率变化 → 及时采用 → F 损失变化”。
现有 F 后端不直接消费最终 E 归约标签；只修好 E 标签、却没有改变 F 输入的情况，
不能被描述为预测改进。
