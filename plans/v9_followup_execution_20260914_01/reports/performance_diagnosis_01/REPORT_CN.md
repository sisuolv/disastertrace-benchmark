# 本轮运行耗时诊断

核验日期：2026-09-14，约 13:10 UTC。本文记录运行性能，不改变已冻结的实验、评分或调用预算。

## 结论

普通 F 的模型会话阶段已经完成。该阶段大部分墙钟时间在 HTTP 调用之外，此前将缓慢主要归因于 API 调用的解释不准确。当前实现的状态序列化、完整检查点保存、历史重放及串行审计需要优化；还没有通过采样 profiler 将这几类开销精确分摊。

## 实现中的开销来源

- `scripts/run_api_pilot.py` 每个会话步骤都调用 `SessionCoordinator.step()`、复制 snapshot、保存完整 checkpoint，随后处理远端调用。
- `monitoring_v1/session_checkpoint.py` 和 `policies.py` 通过 checkpoint 恢复每步上下文；保存的状态包含随时间增长的历史。
- 会话结束后，`run_api_pilot.py` 依次恢复事件历史、写入持久日志，再调用 `score_admitted`。
- `monitoring_fixed_v1/admission.py` 的正式评分会从日志逐条重放并核对状态及哈希；独立审计再次执行这些检查。
- `scripts/analyze_api_followup.py` 的 F 审计按案例串行执行，`score_admitted` 内部也按方法串行恢复日志。13:08 UTC 检查时，普通 F 审计在 CCI 上以一个 Python 进程持续使用 CPU，约 10 分钟墙钟对应约 10 分钟 CPU 时间；这段观测显示审计当时主要在计算。
- 温度程序轨迹以 12 个 worker 执行，后续 24 个月的正式评分却是串行循环。温度扩展已经全部完成并通过最终审计。

这些检查有复现和完整性用途，但不意味着当前重复执行与存储方式已经高效。不能把 19.5 GB 文件大小直接换算为 AFS 等待耗时，也不能把全部非 HTTP 时间都称为磁盘瓶颈。

## 对收尾范围的澄清

普通 F 已完成 48/48 个模型会话及 120/120 个程序对照；后面仍有此前登记的 Denver 正例诊断和 F 独立审计。发布程序等待整批终态，因此主模型调用结束不等于立即上传。Denver 诊断按普通 F 完成后再启动的既定顺序执行，没有因本次性能诊断新增实验。

## 应优先优化的实现

1. 将独立案例的只读评分/审计分发到 CPU 进程，保留原日志、完整校验及稳定合并顺序。
2. 在逐步运行中保留可信的内存上下文，明确进程恢复时才需要的完整重放；用历史轨迹验证行为等价。
3. 用追加事件日志与周期性完整检查点降低重复序列化和保存量，同时保留中断恢复、计费和时间语义。
4. 分别记录 API、本地计算、持久化和审计用时，按整个剩余流程估算完成时间。

以上是待实施的性能修正建议；本记录没有热修改当前冻结的评分代码，也没有增加模型调用或重跑实验。单纯增加 H100 数量不能直接加速目前这些 Python 串行重放和 JSON 处理。
