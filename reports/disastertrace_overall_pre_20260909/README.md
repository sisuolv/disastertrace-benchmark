# DisasterTrace 整体 benchmark 汇报

本版将已核验的受控结果、原文结果与最新诊断整理成一场完整研究汇报。默认听众尚不了解项目，先解释 benchmark 怎样构建，再讨论模型结果。

## 两份主要文件

| 文件 | 用途 |
| --- | --- |
| [总体 Markdown 页面稿](DisasterTrace_Overall_Pre_CN.md) | 28 页正文＋8 页备查附录，用水平线划分页面，可交给 ChatGPT 精简或制作幻灯片 |
| [独立演讲稿](DisasterTrace_Overall_Speech_CN.md) | 与全部 36 页一一对应，正文包含讲述与转场，附录提供重点问题的备答 |

完整路线建议 35—40 分钟，演讲稿还给出约 25 分钟的压缩路线。页面稿前 17 页介绍动机、真实例子、构建流程、数据、题目、Gold、输入输出、评分、历史条件、程序基线和指标；之后再呈现结果、限制和后续计划。

## 重点回答的听众问题

- 当前测的是已发布预报陈述的使用，还是物理天气预测能力？
- 受控任务和原文任务为什么都需要，真实与生成部分怎样区分？
- 一份公告怎样变成题目，目标时间与当前来源怎样确定？
- 不用人工逐题评分或 LLM judge，参考答案如何核对？
- 模型能看到什么，是否看到 Gold、未来公告或纠正后的历史？
- 三种历史配置到底比较什么，规则程序满分意味着什么？
- 怎样理解严格正确、字段、轨迹、重复、覆盖与未完成实验？
- 现有结果支持哪些贡献，哪些泛化、污染和执行问题仍需证据？

主文把问题放在对应设计处回答，备查附录保留完整 JSON、受控生成细节、数据边界、泄漏与污染、全模型表、覆盖分解、验收口径和文献来源。

## 证据与验证

结果沿用 **2026-09-09 02:44 UTC** 已核验快照。本次整合没有新增模型调用、GPU 评测或模型结果重算，没有更改旧报告。

`evidence/facts.json` 保存关键数字与 Francine 真实来源示例；`evidence/source_manifest.json` 记录实际读取来源及哈希。少量冻结任务规范代码用于核对演示 JSON 与历史载体说明，它们的哈希与既有验收记录绑定。此目录不是完整科学实验复现包。

`validate_materials.py` 核对页面与讲稿的一一对应、主要结果表、参考 JSON、来源节选和引用链接；实际状态见 `evidence/document_validation.json`。示例原文从已有保存字节检查，没有重新下载。本文没有重新执行全部研究审计。

页面稿含两幅 Mermaid 构建流程图，可在支持 Mermaid 的 Markdown 阅读器中显示；转成其他幻灯片格式时，可以按节点关系重绘。此次没有额外生成 PDF，也没有声称已验证特定幻灯片软件的分页渲染。

## 使用建议

先通读演讲稿 01—17，确认自己能够解释“从资料到分数”的过程；再看页面稿挑选主讲结果。彩排时先说明分母再读数字，保留从问题到设计、从发现到下一步的转场。

如果交给 ChatGPT 进一步压缩，建议同时提供两份主文件，并要求保留：整体构建过程、真实来源案例、自动 Gold 的可信度边界、规则程序基线、主结果分母与未收齐条件。阶段编号继续留在附录。

可在当前目录执行下面的只读结果核对与文档验证；已有事实快照会被复用：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 validate_materials.py
```
