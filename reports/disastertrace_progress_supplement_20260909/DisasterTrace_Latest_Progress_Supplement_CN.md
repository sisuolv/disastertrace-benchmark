## 1. 先把整项研究的前因后果讲清楚

### 1.1 应用中真正需要的能力是什么

极端天气资料会连续发布。同一个风暴、同一个未来时刻，可能在不同公告中得到不同的预报。新的公告也可能没有覆盖我们要问的那个时刻。一个系统要根据这些材料回答问题，需要同时判断：我们问的是哪个对象与时间、哪些资料已经可见、哪个版本明确支持当前答案，以及能否把这种判断持续做对。

因此，DisasterTrace 当前研究的是：**当与天气有关的证据持续更新时，LLM 能否持续输出与目标对齐、并由当前允许来源支持的答案？**

“预测未来天气是否准确”需要把预测与真实观测比较；当前任务的参考对象则是已发布资料中的预报陈述。这一区分决定了我们的输入、Gold、评分和可声称的贡献。项目长期面向极端天气信息使用，但现有官方原文证据主要来自热带气旋公告，尚不能代表所有灾种。

### 1.2 为什么需要两种任务

如果只使用真实文本，出现错误时，很难知道模型是读错数字、搞错目标时间、选错版本，还是被历史答案误导。因此先建立受控诊断：让“应该更新”和“不应该更新”的情形明确可分。例如，某个来源被同值新版本替代时，数值可以不变，引用必须更新；另一个风暴的资料进入上下文时，本目标答案应保持不变。

如果只保留受控材料，又无法确认这些测量要求能否在真实公告中落实。因此另建官方原文任务：保留原始公告，按发行顺序交付，以绝对有效时间对齐预报行，并要求输出可检查的来源与行号。

两条任务共同回答一个问题。受控任务提供诊断清晰度；官方原文任务提供真实资料中的时间、覆盖和引用约束。它们的材料、输出字段和难度组成不同，得分应分别报告。

### 1.3 一个原生检查点究竟要求模型做什么

可以把一个问题理解成：“截至本轮已经交付的公告，对风暴 X 在绝对时间 T 的风速和位置，最新的明确陈述是什么？”每个检查点产生一份结构化回答，包含目标键、状态、风速、经纬度及支持来源定位。

当前规则是 `latest visible explicit coverage`：在已经可见的资料中，寻找**明确覆盖同一个目标时刻的最新来源**。这不等于机械选择最新公告，也不等于始终取同一个相对预报时长。

如果新公告没有覆盖目标时刻，任务允许沿用之前最近一次明确覆盖的陈述。这个保留规则是 benchmark 的任务约定，不能延伸成“NHC 官方认为该旧预报在业务上仍有效”的声明。没有足够历史公开可见时间证据的部分，应称为按发行时间控制的回放。

三种历史条件共享截至当前的累计可见原始资料：`snapshot` 不额外附加自己的历史答案；`structured_state` 携带前一轮答案状态；`answer_history` 携带此前的答案历史。具体可携带内容由各自冻结协议决定，错误不会被 Gold 修正。比较对象是附加历史载体对回答的帮助或干扰，目前没有构造必须只依赖记忆才能完成的任务。

## 3. 旧版已有结果应怎样继续使用

受控主实验的 2,160 份回答已经验收，1,861 份完整正确。按 8,640 个字段机会计算，值／状态正确为 8,517，当前来源约束下正确为 8,258，相差 259 个“内容正确但引用未满足当前要求”的字段。这组数据继续支持“只看值会漏掉证据使用问题”。

受控实验还比较检查点、完整轨迹和两次重复的整段成功。它说明局部准确与持续可靠并不等价。新增原生实验沿用这一测量思路，但不应把受控的 86.16% 与原生的 34.18% 画成同一条性能变化曲线：两者不是同题同条件比较。

建议整场汇报的实验顺序是：先用受控结果解释为什么需要这些指标，再用原生结果检验这些指标在真实材料中揭示了什么，最后讨论协议和收集过程怎样影响这些测量。

## 4. 发现一：在官方原文上，合法输出仍远不足以保证可靠回答

### 4.1 完成了什么

Francine 与 Ida 两个风暴的原生试点，包含 46 个目标、257 个未来检查点。三种历史条件、两次重复，共计划并返回 **1,542／1,542** 份 Qwen3-8B 回答。所有回答结构合法，目标键和要求的单位字符串也全部正确；没有缺失、长度截断、推理提取错误或重试。

这里的“结构合法”只表示输出符合公共格式，不表示数值、状态、来源或行号已被语法保证正确。

| 历史条件 | 严格正确／514 | 严格正确率 | Francine 正确／256 | Ida 正确／258 |
| --- | ---: | ---: | ---: | ---: |
| snapshot | 187 | 36.38% | 115 | 72 |
| structured_state | 194 | 37.74% | 106 | 88 |
| answer_history | 146 | 28.40% | 85 | 61 |
| 三种条件合计 | 527／1,542 | 34.18% | 306／768 | 221／774 |

这一结果提供一个明确观察：**即使格式、目标键和单位都没有问题，模型仍经常无法同时满足内容与来源要求。** 因而新增原生失败不能统一归结为 JSON 输出失败。

### 4.2 失败发生在哪些环节

按 scorer 固定优先级划分的互斥类别如下，合计为 1,015 个失败检查点。

| 互斥错误类别 | 检查点数 | 解释 |
| --- | ---: | --- |
| 值／状态／单位类别 | 764 | 本轮单位均正确，因此本组实际反映值或状态失败 |
| 来源定位错误 | 223 | 引用位置不满足规则 |
| 来源版本错误 | 23 | 选错支持版本 |
| 同值旧版引用 | 5 | 数字碰巧一致，当前版本要求仍未满足 |

后三类共 251 份回答可归为该优先级下的引用相关失败。不要把它与独立组件检查的失败数再相加：组件检查允许重叠，同一个回答可能同时存在状态、来源与行号问题。

这一实验对论文的作用，不只是提供一个低分，而是把低分分解成可检查的失败形式。格式有效性不能替代严格正确；严格正确也应配合分项，解释测量究竟在惩罚什么。

### 4.3 单点正确与整段可靠的差距

全部 276 条“目标 × 方法 × 重复”轨迹中，只有 **19／276** 条所有检查点都正确。进一步要求同一目标在两次重复中都整段正确，三个方法分别只有 **1／46、2／46、2／46**。

这与应用动机直接相连：系统在若干时刻能答对，不等于在一个目标的连续更新过程中可持续依赖。只展示 34.18% 仍会遗漏整段成功的稀缺程度。

方法排序也不能被过度推广。总体上 structured_state 略高于 snapshot；但 Francine 上是 snapshot 更高，Ida 上是 structured_state 更高。只有两个风暴来源，无法据此提出通用的记忆方法排名。

证据：`evidence/sources/p7_FINDINGS.md`、`p7_qwen3_analysis.json`、`p7_qwen3_report_excerpt.json`。

## 5. 发现二：相同历史信息的不同表示，可以产生可观察的单步差异

### 5.1 为什么追加这个实验

三种历史条件改变的不只是表示，还改变历史多少、长度以及哪些错误被继续携带。因此“structured_state 比 answer_history 高”不能直接归因于结构化表示更优。

为缩小问题，新增实验取原生试点 structured_state 的 **422 个非初始历史前缀**。每个前缀各生成一个 JSON 载体分支和一个可逆文本载体分支，两边保留相同历史信息与已有错误，使用配对的新种子，分别生成下一步回答。一个分支的新答案不会进入另一个配对，也不会被串接成新的完整轨迹。

### 5.2 观察到什么

| 配对结果 | 数量 |
| --- | ---: |
| 两边都正确 | 88 |
| 只有 JSON 正确 | 30 |
| 只有文本正确 | 55 |
| 两边都错误 | 249 |
| 总配对数 | 422 |

JSON 分支严格正确 **118／422＝27.96%**；文本分支 **143／422＝33.89%**。差异为 **25／422，即 +5.92 个百分点**。共 844 份实际回答全部收齐且结构合法。

这不是“新增 422 个独立天气事件”，而是来自两个风暴的相关历史前缀。它也不与原始 structured_state 的 194／514 直接比较：这里去除了初始轮，只研究已选前缀上的新单步回答。

### 5.3 可以怎样解释，不能怎样解释

可以说：在这些保存的前缀上，当前文本编码的单步严格正确率高于当前 JSON 编码。实验比原来的三方法比较更接近表示层面的对照。

仍需保留的边界是：文本分支每个请求比 JSON 多 **36—54 个 token**，平均多 **47.34** 个，没有等 token 长度的配对。观测差异因此属于这个具体表示方案，包括语法和长度。它不能单独识别“纯格式”的作用，更不能证明文本普遍优于 JSON、内部记忆机制变好，或完整闭环轨迹会同幅度改善。

在论文中的位置：这是“为什么需要解释方法差异”的进一步诊断。贡献是缩小可解释的比较问题，同时保留尚未控制的因素。

证据：`evidence/sources/p8_FINDINGS.md`、`p8_qwen3_report_excerpt.json` 中的 `paired_representation`。

## 6. 发现三：任务扩展后，绝对时间与明确覆盖仍然是必要的测量要求

### 6.1 扩展了哪些数据

新增开发队列包括 **Dorian、Isaias、Henri、Fiona、Lee、Helene**，各取最初六份编号公告，合计 36 份原文。来源按风暴、年份和公告编号在扩展模型得分出现前选定。

| 计数对象 | 数量 | 应如何理解 |
| --- | ---: | --- |
| 独立风暴来源组 | 6 | 不是 804 个独立事件 |
| 原始产品 | 36 | 每风暴 6 份早期公告 |
| 目标 | 144 | 对象与绝对目标时刻的组合 |
| 候选目标／交付组合 | 864 | 准入前的候选检查点 |
| 非未来检查点排除 | 60 | 排除规则明示并保留记录 |
| 纳入未来检查点 | 804 | 每种历史条件的题目机会 |
| 明确预报行 | 282 | 与模型回答数是不同单位 |
| 同目标的相继覆盖修订 | 138 | 其中风速变化 96，经纬度变化 137，可重叠 |
| 每模型、每协议条件计划回答 | 2,412 | 804 × 3 方法 × 1 次重复 |

试点两个风暴加上这六个风暴，共覆盖八个不同的原生风暴来源、48 份原生产品。这个原生统计不能再与可能重叠的受控历史来源简单相加。

原解析器最初只准入 26／36 份产品，原因是部分公告使用 `POTENTIAL TROP CYCLONE` 标头。通过单独版本化的拼写支持扩展后，36／36 份原文均可准入。原始失败记录和原始字节保留，公开文本求解器无需更改。解析器一致性是证据之一，仍不能替代对共同规范化逻辑和历史可见时间的核对。

### 6.2 为什么“最新公告”不等于“最新目标预报”

相邻编号公告的预报时效网格会交替变化。如果只检查相邻公告是否有同一个目标时刻，可能误判为没有修订。按同一绝对目标时刻寻找相继明确覆盖的版本后，可以识别 138 次修订。

这也可以用程序对照验证：公开 `latest_explicit` 求解器在 2,412 个机会中全部正确；机械选最新公告只有 1,434／2,412，始终取相同相对时长只有 1,020／2,412，取最后一行只有 108／2,412。

这些是**程序诊断**。它们证明公开规则可解，也表明几个常见捷径不等价于正确策略。程序没有使用隐藏 Gold 作答，但它掌握任务的明确结构，不能作为“LLM 自然理解已经被证明”的替代证据。

### 6.3 当前扩展仍缺什么

参考状态分为 598 个 numeric、196 个 not_stated、10 个 DISSIPATED；乘三种方法后分别是 1,794、588、30 个计划回答机会。

`not_stated` 表示可见资料没有按任务规则明确给出该目标陈述，不表示现实中没有风暴；`DISSIPATED` 是来源中的消散状态；numeric 要求数值与对应来源正确。

该队列包含终止状态，却**没有按既定定义构成的终止修订检查点**。最初六份公告也不能代表完整生命周期、登陆极端阶段或所有灾种。扩展证明可以加入更多真实来源，尚未构成正式泛化验证。

证据：`evidence/sources/p10_FINDINGS.md`、`p10_acceptance_excerpt.json`。

## 7. 六风暴模型结果：先交代分母和收集完整性

本节每行都是单独冻结并生成自身历史的模型／协议条件。六风暴矩阵均只有 **一次重复**，每行固定计划分母为 2,412。DeepSeek 指本地 **DeepSeek-R1-Distill-Qwen-7B**，不是早期测试过的托管 DeepSeek API 模型。

“默认空白”指 XGrammar 的默认 JSON 分隔符空白规则，**不是完全没有空格的紧凑 JSON**。原条件允许任意 JSON 空白。`system`／`user` 指同一段任务契约文本在消息中的角色位置；角色移动也改变了原生聊天模板的 token 序列。

| 模型 | 契约角色／空白设置 | 返回／计划 | 结构合法 | 严格正确／计划 | 主正确率 | 未尝试 | 结果未知 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Qwen3-8B | system／任意空白 | 2,412／2,412 | 2,411 | 1,000／2,412 | 41.46% | 0 | 0 |
| Qwen3-8B | system／默认空白 | 2,412／2,412 | 2,412 | 1,060／2,412 | 43.95% | 0 | 0 |
| Qwen3-8B | user／默认空白 | 1,628／2,412 | 1,628 | 952／2,412 | 39.47% | 780 | 4 |
| DeepSeek 蒸馏模型 | system／任意空白 | 1,604／2,412 | 1,514 | 3／2,412 | 0.12% | 808 | 0 |
| DeepSeek 蒸馏模型 | system／默认空白 | 1,994／2,412 | 1,943 | 9／2,412 | 0.37% | 418 | 0 |
| DeepSeek 蒸馏模型 | user／默认空白 | 2,064／2,412 | 2,011 | 6／2,412 | 0.25% | 348 | 0 |

主正确率始终以计划机会为分母。没有返回的回答不算正确；`unknown` 是已记录提交但没有保存到可确认返回的机会，不能当作普通未尝试请求重发。主分母保留了实验实际的端到端失败，但它不会自动校正执行时长和调度带来的偏差。

三个角色／空白单元不是完整的二乘二因子实验，没有 `user／任意空白` 单元。每个条件自己的历史会随输出不同而分叉，所以它们也不是第 5 节那种固定同一历史前缀的单步实验。

补充背景：在较早的两风暴本地 DeepSeek 蒸馏模型试点中，返回 986／1,542、严格正确 1／1,542，另有 556 个未尝试机会。停止前缀核验通过，但四个 worker 均因上下文保护而失败退出。这组数据应单列，不能与六风暴矩阵混为一次重复。

证据：`tables/model_results.csv`；各条件的 `FINAL_STATUS`、报告节选、完整描述性分析和阶段验收节选。

## 8. 发现四：方法排序与总分会随指标和状态构成改变

### 8.1 最多单点正确的方法，不一定最可靠地走完整个目标

以收齐的 Qwen 六风暴条件为例：

| 方法 | 任意空白：检查点正确／804 | 任意空白：整目标正确／144 | 默认空白：检查点正确／804 | 默认空白：整目标正确／144 |
| --- | ---: | ---: | ---: | ---: |
| snapshot | 356 | 4 | 369 | 6 |
| structured_state | 345 | 22 | 369 | 23 |
| answer_history | 299 | 15 | 322 | 13 |

在任意空白条件下，snapshot 的检查点正确数最多，但 structured_state 的整目标成功数最多。默认空白下，snapshot 与 structured_state 的检查点正确数相同，整目标成功数仍相差明显。

这说明整段可靠性提供了总分没有包含的分布信息：同样数量的错误，集中在少数目标，还是分散到许多目标，会得到不同的整段成功表现。默认空白下 answer_history 的单点得分上升，整目标成功反而从 15 降到 13，也提醒我们不能只围绕一项指标选配置。

这里是一轮采样的整目标成功，**不是两次重复均成功**。部分继承代码字段名仍含 `both_repeats`；本次汇报统一根据真实重复数改称“单次整目标成功”。

### 8.2 总分包含不同类型的问题

| Qwen 条件 | numeric 严格正确／1,794 | not_stated 严格正确／588 | DISSIPATED 严格正确／30 | 总严格正确／2,412 |
| --- | ---: | ---: | ---: | ---: |
| system／任意空白 | 485，27.03% | 502，85.37% | 13，43.33% | 1,000，41.46% |
| system／默认空白 | 502，27.98% | 545，92.69% | 13，43.33% | 1,060，43.95% |

从任意空白到默认空白，总正确数增加 60，其中 **43 来自 not_stated，17 来自 numeric**，终止状态正确数不变。因此整体增加 2.49 个百分点，不等于具体数值提取和引用能力也增加同样幅度。

在三个六风暴 DeepSeek 条件中，严格正确的 3、9、6 份回答全部来自 not_stated；numeric 与终止组均没有完整正确回答。这个结论针对当前精确协议下的联合正确，不能直接转述成“模型对风速完全没有任何信息”。

每个风暴内的检查点高度相关。当前只有六个开发风暴，一次重复，适合做描述性比较。后续正式区间或检验应明确风暴分组与配对结构，不能把数千检查点当作数千个独立事件。

## 9. 发现五：输出协议和历史增长影响了测量过程本身

### 9.1 第二个模型的弱结果应如何解释

本地 DeepSeek 蒸馏模型出现了多类失败：部分回答长度耗尽、部分结构无效、经纬度单位经常输出 `N`、`W` 或 `degrees` 而非规定的 `deg`，以及错误目标、数值和引用。即使结构合法，精确单位等协议要求也可能不满足。

| DeepSeek 六风暴条件 | 返回数 | 结构合法数 | length 结束数 | 合法回答中纬度使用 deg | 最终文本空白字符总数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| system／任意空白 | 1,604 | 1,514 | 90 | 137 | 1,657,688 |
| system／默认空白 | 1,994 | 1,943 | 51 | 198 | 51,783 |
| user／默认空白 | 2,064 | 2,011 | 53 | 271 | 53,711 |

空白统计包括字符串内部空白，各条件返回数也不同，因此这些总量是运行描述，不是归一化的纯效果估计。改变空白规则后，异常空白显著减少，严格正确率仍很低。它帮助缩小了问题，却没有解决全部协议与语义失败。

这些实验没有做单位归一化、答案修补或 LLM judge 复核。若以后允许确定性的等价单位，应事先定义独立评分版本与符号转换规则，并保留旧结果，而不是看到低分后修改这次答案。

### 9.2 为什么限制空白后仍然超长

默认空白规则不会自动限制任意整数或字符串的表示长度。已保存的 DeepSeek 停止前缀中，有两条未完成的引用行号整数分别连续产生 **7,498 位和 7,811 位尾部数字**；相应回答各只有 6 个空白字符。

这些异常输出说明“语法合法的某种前缀”仍可能非常长。历史载体继续携带这类输出后，下一轮请求可能超出上下文上限。因此不能把“限制空白”写成“已经解决历史长度问题”。

也不能用数据依赖的语法直接把正确行号或候选来源集合写进去，否则任务难度会被答案提示改变。下一版可以研究公开、与正确答案无关的整数和字符串表示边界，并通过错误但格式合法的反例检查没有把语义答案编码进语法。

### 9.3 更关键的收集器问题：一条轨迹失败，会牵连其他轨迹

当一个 answer_history 请求加上 8,192 token 输出预留超过 32,768 上下文上限时，旧收集器会终止整个 worker。同批的其他请求和后续其他目标也失去执行机会。

对冻结调度顺序和实际停止前缀的 CPU 对账如下：

| DeepSeek 条件 | 未尝试机会 | 属于最先超限轨迹的剩余机会 | 属于其他轨迹的剩余机会 |
| --- | ---: | ---: | ---: |
| system／任意空白 | 808 | 5 | 803 |
| system／默认空白 | 418 | 3 | 415 |
| user／默认空白 | 348 | 2 | 346 |

在重建的六个“下一个批次”中，每批还有三个请求可以容纳。表中的“其他轨迹”不代表所有更远请求都能容纳，也不预测修复后会答对多少；它量化的是整 worker 停止扩大缺失范围这一现象。

这对方法比较尤其重要：虽然最先超限的是历史轨迹，snapshot 与 structured_state 也可能因为共享 worker 而被迫停止。固定分母正确保留了失败，但未能把某一方法自身的失败与调度牵连完全分开。

下一版应在进入批处理前逐请求检查，让无法继续的轨迹保留明确失败记录，其他独立轨迹继续执行。历史版本保持冻结，不能补跑成一份看似从未失败的旧报告。

证据：`evidence/sources/context_censoring_v1.json`、`CONTEXT_STOP_WORKER0.md`；各模型分析中的单位、空白和 worker 记录。

## 10. 发现六：未收齐条件下，分母和可见样本构成会改变表面结论

### 10.1 一个最容易误讲的数字

Qwen 的 `user／默认空白` 条件返回 1,628／2,412，严格正确 952。只在返回部分计算得到 **952／1,628＝58.48%**；固定计划分母得到 **952／2,412＝39.47%**。

上一组完整的 `system／默认空白` 条件为 **1,060／2,412＝43.95%**。不能用 58.48% 与 43.95% 直接宣布角色移动提高了能力：两个比率评估的题目集合不同。

后启动条件共享同一绝对截止窗口，因此得到的可用收集时间更短。两个 Qwen worker 在窗口结束附近被记录为 FAILED 并释放，没有写出可用的最终 worker `stop_reason`。报告保留了 780 个未尝试和 4 个结果未知；可以确认不完整和时限不对等，不能从不存在的 stop reason 推导每个缺失的精确原因。

### 10.2 为什么返回子集可能更容易

| 参考状态 | user 条件返回／计划 | 覆盖率 | user 条件严格正确／计划 |
| --- | ---: | ---: | ---: |
| numeric | 1,053／1,794 | 58.70% | 398／1,794 |
| not_stated | 567／588 | 96.43% | 549／588 |
| DISSIPATED | 8／30 | 26.67% | 5／30 |

较容易答对的 not_stated 几乎收齐，而 numeric 和终止组缺失较多。返回子集中的状态组成已经改变，且其选择与轮次、历史长度和执行时长有关。

只做共同返回子集也不能完全消除这个问题。配对覆盖分析显示：在双方都返回的 1,628 个槽位上，system 正确 884，user 正确 952，差 68；但 system 独有的 784 个已返回槽位中还有 176 个正确答案。因此整体正确数差为 **+68 − 176＝−108**，与 952 − 1,060 一致。

这个分解帮助解释两个分母为什么给人不同印象。共同返回子集仍是运行过程选择出来的，不是对不等时限的无偏校正，也不能据此选择所谓最佳角色。

### 10.3 下一次应先明确比较哪一种问题

如果目标是完整任务准确率，就给各条件足够完成整个矩阵的预算，另报告资源消耗。如果目标是固定资源下的端到端表现，就固定各条件相同的计时起点、独立时长上限和资源规模，把未完成纳入结果。

两种问题都有研究价值，但不能混用。后启动条件继承更短的剩余窗口，会让协议与执行时限混杂。

证据：`evidence/sources/p14_FINDINGS.md`、`p14_qwen3_analysis.json`、`pair_coverage_v1.json`。

## 11. “完成”现在应该分成三层说

### 11.1 结果收集、阶段验收与全局发布

第一层是**模型矩阵是否收齐**。例如两风暴 Qwen、表示配对、六风暴两个 system Qwen 条件已收齐；本地 DeepSeek 多组条件和 Qwen user 条件未收齐。

第二层是**已有运行能否独立重建并通过阶段验收**。截止本包快照，P7—P14 的相应离线／运行阶段验收均存在且为 passed，包括刚完成的 P14。这里验收的是保留下来的真实运行与失败前缀，不会把失败作业改成成功。

第三层是**完整跨阶段科学证据、资源账本与对外发布是否统一闭合**。本包没有重新执行全局资源核算、截止时间审计和完整归档恢复，也没有核验一个包含全部新增结果的 GitHub commit。因此不以本包代替科学证据归档，也不声明所有新结果已经上传。

### 11.2 一个需要保留的历史验收补充

六风暴首轮的原始 P11 验收清单漏绑定了 14 个分析／命令文件，原始回答和模型报告已覆盖，得分未改变。已另建 30 文件的验收补充，原清单与归档保留；完整科研复查应同时读取原 P11 包和该补充。

本阅读包保存了该补充的完整小型验收记录，并核对所引用分析的归属。后续验收使用更新版本。这一事实是证据覆盖的修正，不应写成“重新跑模型获得了更好的成绩”。

### 11.3 本次制作实际核验了什么

本包读取了 125 个来源文件，完成 178 项收集时一致性检查，包括报告与最终状态的 SHA256 绑定、报告与分析 ID、分析记录数量和正确数、固定分母守恒、互斥错误计数、相关命令成功回执，以及被引用报告／分析的验收清单覆盖。PDF 和打包还有独立制作检查，见 README 与验证文件。

我们使用已有的 token 回放与隔离 CPU 重建成功回执，没有在这次汇报制作中重新遍历所有原始回答、重放全部 token 或复验完整科学归档。`evidence/sources/` 中明确命名的 `excerpt` 是节选；完整报告的大量逐条捕获内容没有放入阅读附件。

## 12. 怎样重写整项 benchmark 的当前结论

### 12.1 可直接用于汇报或论文摘要的段落

> DisasterTrace 面向持续更新的极端天气资料，评测 LLM 能否在对象与目标时间对齐的前提下，持续输出具有当前来源支持的答案。我们建立了互补的受控更新诊断和官方预报原文任务，通过公开任务规则、自动参考答案、确定性评分和独立重建，分别衡量内容、来源与整段可靠性。受控实验表明，内容正确仍可能伴随过期引用；新增官方原文实验进一步显示，Qwen3-8B 在 1,542 份结构合法回答中仅有 527 份严格正确，276 条轨迹中仅 19 条整段正确。同历史前缀的表示对照、六风暴开发队列及第二个本地模型的结果揭示，历史表示、状态构成、输出协议与执行缺失会共同影响观测分数。当前成果支持一个可复核、可诊断的动态证据评测框架；后续将优先隔离轨迹故障、冻结公共输出协议并给予可比较的完成预算，再开展更独立的数据与模型验证。

### 12.2 三项可以 defend 的贡献候选

| 贡献候选 | 当前证据 | 结论边界 |
| --- | --- | --- |
| 明确动态天气证据中的测量对象 | 对象／目标时间、可见来源、版本、定位与连续轨迹有统一可执行定义 | 当前原生材料主要是热带气旋预报陈述 |
| 使错误可以被复算和解释 | 自动 Gold、公开求解器、受控错误类型、原生模型失败及逐项回执 | 自动化保证可检查性，仍依赖任务语义和解析准入范围 |
| 显示端到端可靠性不能由单个总分代表 | 引用与内容差异、整段指标、表示配对、状态分层、协议和覆盖分析 | 不据此声明通用方法胜负或跨模型家族泛化 |

不宜声称：已经证明物理天气预测能力；已经覆盖所有极端天气；文本形式普遍优于 JSON；structured_state 在所有事件上最好；DeepSeek 的结果代表整个模型家族；已有无污染的 heldout 结论；格式通过或审计通过等于科学问题已解决。

关于相关工作，沿用旧版核对过的 ALCE、LongMemEval、StateMemBench、STALE、tau-bench 与 Extreme Weather Bench 六条研究线索。它们分别关联引用、更新、状态与重复可靠性等测量思想。本次没有重新检索或宣称复现这些外部 benchmark，也不据此声称首创性。引用记录见 `baseline/references.json`。

## 13. 下一步计划：让每一步解决已经观察到的问题

### 第一步：版本化修复收集器的轨迹故障隔离

原因：已观察到一条历史轨迹的上下文超限，导致其他轨迹失去机会。交付物是新版本收集器与离线故障注入记录，不需要先调用模型。

验收要点：批次中的一条超限不停止其他独立轨迹；该轨迹的后续计划槽位继续计入分母；未知返回不静默重发；原始返回已保存后可以恢复评分；提交后返回前的中断保留 unknown；不同 worker 分配不改变失败归属。GPU 使用管理也应有统一容量账本，将待启动申请计入上限。

### 第二步：公开选择一个共同输出协议，并冻结版本

原因：默认空白缓解了异常空白，但不能约束无界数字；精确单位等也影响模型适配。交付物是公共 schema、提示、表示边界和独立反例。

选择必须公开说明依据来自当前开发集。不得把正确答案或候选引用集合写入语法；错误但格式合法的答案仍应可生成。旧分数不变；若增设等价单位诊断，单独命名和报告。协议选择后的同开发集最佳得分不能充当未调参的泛化结果。

### 第三步：按生命周期和修订类型扩展真实资料

原因：现有扩展集中在早期公告，缺少真实终止修订等结构。交付物是预先固定取样规则的新数据包与来源核对记录。

应覆盖发展期、成熟期、登陆附近与终止阶段，以及同一绝对时刻覆盖变化、跨月／跨年和经纬度符号边界。程序 fixture 的覆盖与真实资料覆盖分别统计；独立解析器一致之外，继续检查共同规范化与可获得的独立结构化资料。历史可见时间不足时保留明确标签。

### 第四步：等完成预算的开发比较，再增加模型独立性和重复

原因：共享绝对截止窗口与不同启动时刻妨碍角色效果解释。交付物是明确研究问题、固定计划分母、失败规则、时长和 GPU 分配的新登记矩阵。

先决定完整任务准确率与固定资源效率哪个是主问题，再确定预算。优先加入来源更独立的模型家族，并区分“更多采样重复”与“更多独立风暴”。如果仍以 804 个检查点、三方法、两个模型、两次重复为例，需要 9,648 个回答；增加第二套协议会翻倍。这个公式用于预算讨论，不是已经启动的新实验。

### 第五步：协议冻结后才进入独立 heldout

原因：当前大量配置选择与诊断都在开发资料上完成。交付物是独立 heldout 计划、污染与时间依据说明，以及按风暴组织的统计分析规则。

开发集运行可靠性未解决时，不通过扩大 heldout 调用掩盖缺失。公开历史资料可能进入预训练，时间划分本身不能证明去污染。本包提出执行顺序，没有新增 heldout 推理或 GPU 任务。

## 14. 汇报时最可能遇到的追问

**“为什么公开程序能满分，还需要测 LLM？”** 公开程序表明规则可解，也给出可检查上限。LLM 结果测的是通用模型在原文、任务契约和自身历史共同输入下，是否能可靠实现这些步骤。下一步应加入明确检索／版本选择流程作为强基线，避免把规则程序藏起来。

**“不用人工评分，可信度来自哪里？”** 来自限定任务语义、原始来源留存、解析准入、公开求解器、反例、确定性评分和独立重建。自动化减少逐题主观判断；任务定义与数据边界仍需要科研复查。这里没有声称所有开放式气象问题都可自动判定。

**“为什么结构合法率很高，分数却低？”** schema 只约束公共格式。Qwen 两风暴试点所有回答合法，仍会错数值、状态、版本或行号。合法性和语义正确是不同指标。

**“是否应该直接用得分最高的协议？”** 当前开发结果可以指导候选选择，但指标可能变化，后启动条件还存在覆盖偏差。应先解决故障隔离并明确主指标，冻结一个共同协议，再用新证据验证。

**“四卡并行是否已经证明加速？”** 本包不做加速结论。终态与分配时长有记录，但分配 H100 小时包含模型加载与 worker 生命周期，不等于设备有效利用率、纯推理时间或账单费用；不同阶段的预检和队列口径也需统一。

**“现在可以把项目称为完成的 benchmark 吗？”** 已具备可执行任务、真实模型结果、程序对照与可追溯证据。作为研究开发版可以完整讲述；正式泛化结论仍需要协议冻结、独立评测、更多真实结构覆盖和可比较的完成预算。阶段验收完成不能替代这些证据。
