这份文档帮助你从头理解项目：我们想测什么、具体怎样测、各阶段做了什么、已有结果说明什么，以及下一步还缺什么。它可以作为后续让 ChatGPT 精简汇报的完整底稿。

内容截止于已验收的 **P6 真实模型评测**与 **P7 原生预报任务离线验收**。对应证据于 2026-09-08 核对。本说明不将进行中的后台任务计数混入这些已完成结果。

最重要的三个状态先放在这里：

- **P6 已获得真实模型结果**：Qwen3-8B 完成 2,160 条回答，1,861 条完整正确，约 86.2%。
- **P7 已完成原生任务的软件准备与验收**：使用官方 NHC 预报原文建立 46 个目标、257 个查询，并完成独立求解、评分及程序对照。
- **P7 还没有模型成绩**：1,542 是待模型作答的计划机会数；程序生成的诊断答案不是 LLM 的回答。

建议先读第 1–5 章理解任务，再读第 6–9 章理解 P6 结果，第 10–12 章理解新增 P7，最后读第 13–16 章理解工程状态、限制和后续路线。

## 1. 项目究竟想解决什么问题

### 1.1 最初的目标与当前落点

你的总体目标是建立一个与极端天气有关、用于评测大语言模型的 benchmark。Benchmark 在这里可以理解为一套固定的考试体系：题目怎么来，模型能看哪些材料，要交什么答案，怎样判分，以及不同模型怎样公平比较，都要事先说明。

“极端天气 benchmark”本身仍然很宽。它可以测试气象知识问答、预报解读、风险沟通、数值预测、工具使用或应急决策。当前 DisasterTrace 选择的具体落点，是**天气证据不断更新时，LLM 使用证据和维护状态的可靠性**。

这里的“状态”就是模型当前认为目标对象有哪些属性，以及每项属性由哪条证据支持。例如，对于一个指定风暴、指定有效时段，当前支持的风速是多少，气压是多少，位置在哪里；如果支持材料还没出现，哪些字段应当暂时保持未知。

模型不是凭常识猜答案。实验会把相关资料交给模型，再观察它能否按公开规则使用这些资料。后续材料可能只更新其中一部分，也可能属于其他对象或时间；旧资料还可能在新资料之后重新出现。

### 1.2 为什么不能只问一次、对一下数字

假设旧记录给出的风速是 100 mph，新记录也给出 100 mph，但明确替代了旧记录。模型继续回答 100，数值没有错。然而，如果它仍引用旧记录，就不能说明它正确追踪了当前证据版本。

再假设一份更新的记录给出 120 mph，却属于另一个风暴或另一个有效时段。模型如果只采用“最新”“最大”或“最后看到”的数字，也可能出错。

所以当前研究希望把三个问题分开测量：**内容是否正确、来源是否正确、这种正确性能否持续保持**。多个检查点和重复运行，就是为了把第三个问题也纳入评测。

### 1.3 当前尚未评测的能力

当前没有要求 LLM 独立预测真实未来天气，再与实际观测比较误差。P7 使用“预报”这个词，是因为输入材料是官方已经发布的预报；模型要正确读取和更新其中的陈述。

目前也没有证明模型能够做好真实撤离、港口停运或救灾资源分配。P6 的动作字段是由公开阈值唯一决定的研究规则。它方便检查状态与下游输出是否一致，不能替代业务决策验证。

当前自然来源主要是 NHC 热带气旋资料。项目的长期名称可以面向极端天气，但现有证据还不能代表暴雨、热浪、暴雪、洪水等全部灾种。

## 2. 先把几个容易混淆的单位讲清楚

### 2.1 从一份资料到一条回答

| 术语 | 在本项目里的具体含义 |
| --- | --- |
| 来源风暴 | 一个独立天气事件，例如 Ida 或 Francine；同一风暴的多份公告不算多个独立风暴 |
| 产品或公告 | 官方在某个时刻发布的一份资料；一个风暴会有多个版本 |
| 目标事实键 | 需要回答的是哪个实体、哪个时间、哪个变量、哪种测量及单位 |
| episode | 围绕同一个目标组织的一段更新任务，可以包含多个检查点 |
| 检查点 checkpoint | 资料交付过程中的一个提问时刻；模型在这里提交一次答案 |
| 方法 method | 如何把先前模型答案附加到当前输入，例如只附上一轮状态或全部历史 |
| 重复 repeat | 在冻结设置下重新运行同一任务的一次身份；不等于出错后补考替换 |
| 轨迹 trajectory | 一个 episode 在一个方法、一个条件、一次重复下实际走过的完整过程 |
| 回答机会 slot | 计划中本来应该有一次回答的位置；即使无效或没有返回，也保留这个位置 |

P6 中，一条基础 episode 有五个检查点。三个方法、两个条件、两次重复，会让同一基础 episode 产生 12 条轨迹，每条轨迹五次回答。

因此 P6 的 36 条基础 episode 对应 432 条轨迹、2,160 个回答机会。它们仍然来自三个独立风暴来源，而不是 2,160 个独立天气事件。

### 2.2 Gold、公开求解器和 scorer 各是什么

**Gold** 是根据任务规则计算出的参考答案。对于某个检查点，它记录正确状态、数值以及应引用的当前来源。Gold 保存在评测侧，不放进模型请求，也不用于修正模型历史。

**公开求解器**是一段只读取模型可见材料的独立程序。它按同样公开规则求解，检查模型是否有足够的信息得到答案。它不能读取隐藏 Gold 来“答题”。其实现与参考答案编译器分开，以减少两边共享同一个实现错误的风险。

**scorer** 是评分程序。它比较提交答案与任务规则，分别检查结构、目标、状态、值、单位、当前来源和定位等要求。确定性评分意味着：同一份输入和答案在同一版本规则下应得到相同结果。

这三者的职责不同。Gold 给出参考，公开求解器检查公开可解性，scorer 判定实际提交。程序对账一致可以增强可信度，但仍不能排除共同误解了任务语义，因此规则和限制也需要公开。

## 3. 一次完整评测怎样运行

### 3.1 先建立题目，再调用模型

完整流程可以按下面的顺序理解：

1. 保存来源原文、版本信息、文件哈希和可定位的行号。
2. 声明任务目标、时间语义、来源选择规则和允许的答案格式。
3. 生成 episode 与证据交付安排，确定每个检查点能看到哪些材料。
4. 在评测侧生成 Gold，并用独立公开求解器对账。
5. 冻结方法、模型、输入预算、输出轨道、调度和机会数量。
6. 逐检查点调用模型，先保存原始回答，再解析与评分。
7. 按该方法的规则把模型自己的答案带入后续检查点，保留原有错误。
8. 汇总分数与失败模式，并在独立环境中重建结果。

“冻结”是为了防止看到结果后再调整题目、挑选容易成功的样本、修改评分规则或替换不满意的回答。未来如果发现通用实现缺陷，应另立版本并保留原始结果，不能静默覆盖。

### 3.2 模型究竟看到了什么

模型能看到公开任务说明、当前目标、当前检查点的信息，以及截至当前已交付的证据。根据方法不同，还可能看到自己先前生成的答案。

模型看不到尚未交付的证据正文、隐藏参考答案、正确来源标签、评分结果或为了让它答对而修复过的历史。研究者事后看 Gold 分析错误，与把 Gold 提供给模型，是两件不同的事。

每个检查点都是新的请求。所谓多轮状态，不依赖服务端悄悄记住整段聊天，而是由实验明确规定传入哪种历史载体。这样才能知道模型在这一轮实际获得了哪些信息。

### 3.3 为什么必须保留无效和缺失回答

假设计划有 100 道题，模型只在 80 道上返回可用答案。如果只在这 80 道上计算正确率，会掩盖交付失败。当前协议把所有计划机会留在分母中，缺失、无效和某些基础设施失败都不能通过悄悄减少分母消失。

当前 P6 恰好收齐了全部 2,160 个答案。P7 的无效与缺失程序对照，则是主动检查未来遇到这类情况时，评分和聚合是否仍然保留机会数。

## 4. 用一个教学样例理解 P6

以下是解释规则的教学示例，不是实际模型回答，也不是新增 benchmark 样本。只展示风速这一字段；真实 P6 要联合提交四字段与动作。

假定目标一直是同一个实体、同一个有效窗口。R1、R2、R3 都在材料中明确说明它们属于该目标，并声明修订关系。

| 检查点 | 新交付材料 | 正确的风速状态 | 当前引用应是什么 |
| --- | --- | --- | --- |
| c0 | 尚无支持风速的材料 | unknown，值为 null | 空引用 |
| c1 | R1：风速 100 mph | known，100 | R1 的支持行 |
| c2 | R2 替代 R1：110 mph | known，110 | R2 的支持行 |
| c3 | R3 替代 R2：仍为 110 mph | known，110 | 更新到 R3 的支持行 |
| c4 | 另一目标的 160 mph；旧 R1 重新出现 | 保留 known，110 | 继续使用 R3 |

这个例子里有四种不同能力。c0 检查缺证时能否承认未知；c2 检查数值更新；c3 检查同值时的来源刷新；c4 检查目标作用域与旧版重放。

如果某次修订只更新风速，未提及的气压、纬度和经度不应被清空。P6 的局部更新语义明确要求保留其他字段；遗漏某字段不是撤销它的事实。

### 4.1 正确输出不只是一句自然语言

下面是 c3 的风速字段节选，省略了其他字段和动作，因此不是完整合法的最终答案：

```json
{
  "maximum_wind_mph": {
    "status": "known",
    "value": 110,
    "evidence": [{"record_id": "R3", "line": 2}]
  }
}
```

评分可以分别发现：把 110 写成 100，是值错误；写成未知，是状态错误；值写对却引用 R2，是当前来源错误；引用一个不存在的行号，是定位错误。

### 4.2 三个任务族怎样对应这些行为

| P6 任务族 | 主要控制的变化 | 检查的行为 |
| --- | --- | --- |
| U1 局部更新 | 部分字段更新，也包括数值不变但来源更新 | 更新该更新的字段，保留其他字段，刷新当前引用 |
| U2 同窗口修订 | 同键修订、其他实体或窗口的记录、旧记录再交付 | 识别正确事实键与当前版本，不被其他作用域带偏 |
| U3 支持恢复 | 某字段支持暂未交付，之后交付 | 正确表达 unknown，并在有证据时恢复 known |

基础平衡设计是三个来源、三个任务族、两个 case、两个 branch，共 36 条基础 episode。它让不同来源覆盖同样的任务类型。case 和 branch 是受控任务的设计变体，不是新的天气事件。

### 4.3 为什么材料中有人工构造的时间和实体

P6 的初始值借助真实 NHC 来源，但后续实体、有效窗口、修订与交付是明确标记的 `controlled_generated` 内容。它们用于建立可精确判分的实验。

因此某些记录中出现 2040 年等时间，是受控实验时间轴，不代表正在预测 2040 年的真实天气，也不代表官方发布了这些修订。汇报时需要把真实来源初值与受控后续变化区分开。

## 5. 三种方法比较的究竟是什么

### 5.1 所有方法都能重新读取累计原始证据

| 方法 | 本说明中的简称 | 截至当前累计已交付证据 | P6 中额外附加的模型信息 |
| --- | --- | --- | --- |
| snapshot | 仅证据 | 都能看到 | 不附加历史答案 |
| structured_state | 上轮状态 | 都能看到 | 上一份结构合法的完整模型答案 |
| answer_history | 全部历史 | 都能看到 | 此前全部结构合法的模型答案 |

这里特别容易误解的是 snapshot。它不是只看最新公告，也不是失去旧资料后凭记忆回答。它仍然可以重新读取截至当前已交付的累计证据，只是不额外看到自己之前怎么答。

structured_state 提供一个紧凑的上轮答案载体。answer_history 提供更长的答案历史。若先前答案结构合法但数值或引用错误，这个错误会原样传递，不会用 Gold 修正。

### 5.2 更多历史为什么未必更好

更多历史可能帮助模型保持状态，也可能让它继续依赖旧结论或错误引用。输入还会变长，重复的模型陈述可能与权威原文竞争注意力。这些都是值得检验的可能解释，而不是由当前分数直接证明的内部机制。

因此当前比较的是三种完整输入配置的实际表现。它同时改变历史数量、表示形式、token 长度和错误携带方式。观察到 structured_state 分数较高，不能单独归因于“结构化记忆更优”。

下一阶段的等信息载体控制，就是把同一份保存的模型状态分别渲染为 JSON 和文本，保留完全相同的值、状态、引用和已有错误，再测量表示与长度差异。信息相同也不意味着 token 数相同，这两件事要分别核验。

### 5.3 P7 的同名方法有独立契约

P7 仍使用这三个方法名称，但历史处理按原生任务另行冻结：structured_state 携带上一答案或显式无效/缺失标记；answer_history 保留此前自己的原始最终文本与缺失标记。

所以代码不能只看方法名字相同，就把 P6 的载体处理、五轮假设和动作结构直接搬过去。两阶段的成绩和运行契约需要分开解释。

## 6. 从早期试跑到 P6，具体完成了哪些阶段

### 6.1 为什么先花时间解决格式与交付

一个模型可能推理了很久，却因为输出上限耗尽，没有留下完整答案；也可能输出带代码围栏的 JSON 或额外解释，违反预先声明的解析规则。此时低分混合了交付、格式和内容错误，不容易解释为状态更新能力差。

早期 DeepSeek 阶段因此先进行输出契约和预算校准。这里的 token 可以近似理解为模型处理与生成文本的计量单位，不等同于中文字符。启用推理时，预算还需要为推理和最终答案共同留出空间。

### 6.2 各阶段的完成情况

| 阶段 | 做了什么 | 实际结果 | 推动了什么下一步 |
| --- | --- | --- | --- |
| P1 | 首轮三方法 DeepSeek 开发试验 | 90 个收到的 benchmark 回答；68 个合法，67 个全对 | 发现输出上限和格式交付是主要瓶颈 |
| T6 校准 | 对照原说明/4096、明确说明/4096、明确说明/8192 | 270 个新回答；8192 条件 90/90 合法、83/90 全对 | 选择更充分的共同输出预算，并区分格式与内容 |
| P2 v1 | 受控任务的首轮开发比较 | 270 回答，264 合法、262 全对 | 进一步明确共同输出契约 |
| P2 v2 | 新契约下重新采集 | 270/270 合法且全对 | 小矩阵区分度不足，需要扩展平衡任务 |
| P3 | 36 episode 的 Qwen3-8B 自由输出评测 | 540 回答，200 合法、193 全对 | 需把输出形式问题与语义诊断分轨处理 |
| P4 | 独立的结构约束输出轨 | 540/540 合法，490 全对 | 形式可靠后，仍有状态和来源错误 |
| P5 | 三种 level 4 压力条件 | 1,620 回答，全部合法，1,360 全对 | 需要进一步控制比较条件并做重复实验 |
| P6 | 基础/无关作用域配对，两个重复 | 2,160 回答，全部合法，1,861 全对 | 获得可解释的来源错误与轨迹可靠性结果 |

P1 的 90 个回答跨 91 次物理尝试，历史中断与单次补发另有记录；不能把尝试数和已收到答案数混用。T6 的 270 包含三个条件，不能只拿其中 90 个格式全过的子条件代表全部校准结果。

这张表展示的是研究过程。模型、任务范围、提示词、输出轨道、种子、硬件或运行时间不同，因此不能把行与行之间的分数差都归因于单一改动，也不能画成模型经过训练后能力提升的曲线。本项目这些阶段没有训练模型。

### 6.3 结构约束到底做了什么

P4 之后采用单独的 structure-only 输出轨，用语法约束提高答案符合结构契约的可靠性。它约束容器、字段、类型等形式，不把正确数值、正确来源 ID、正确行号或正确动作给模型。

结构合法只说明答案符合规定的外形，不说明内容正确。P4 的 540 条答案全部合法，但仍只有 490 条完整正确，就是一个直接例子。

结构约束会改变解码分布，也会影响模型后续历史，因此它不是把 P3 的旧回答“修一修”后得到的新分数。自由输出与结构约束是分别运行和报告的轨道。

### 6.4 P5 与 P6 不能混在一起说

P5 做了 revision_chain、irrelevant_scope、late_stale_replay 三种压力因素。P6 当前完成的配对实验只比较 **base 与 irrelevant_scope level 4**。

P6 的 base 是基础受控任务，不等于完全没有更新或作用域辨别。干扰条件是在这个基础上增加冻结的 level 4 无关作用域压力，目标 Gold 不变。

P6 采用同一完整 H100、同一固定 Qwen3-8B、同一输出轨道，并在对应条件间共享采样种子。这样增强了条件比较的可解释性，但不自动解决所有统计或机制问题。

## 7. 最新 P6 实验的规模与结果怎样理解

### 7.1 2,160 是怎样得到的

```text
2 个条件 × 36 条基础 episode × 5 个检查点 × 3 种方法 × 2 次重复
= 2,160 个回答机会

2 个条件 × 36 条基础 episode × 3 种方法 × 2 次重复
= 432 条运行轨迹

36 条基础 episode × 5 个检查点 × 3 种方法 × 2 次重复
= 1,080 对条件配对的检查点
```

对应条件共享种子，但方法与重复仍进入种子标识；不同方法和不同重复不是全部使用一个无差别种子。载体按轨迹隔离，没有把一种方法的答案交给另一种方法。

模型设置为固定 Qwen3-8B、BF16、一张完整 H100、TP=1，启用 thinking，输出上限 8192，上下文 16384，结构约束为 XGrammar。当前整个矩阵实际由单卡完成。

所有 2,160 条回答已收到且结构合法，36/36 格式屏通过；没有通过重试、替换或 Gold 修补消除失败答案。完整正确为 1,861/2,160，即 86.2%。

### 7.2 “完整正确”比“数字大致对”严格在哪里

P6 一条答案要同时满足四字段的状态、数值和当前来源引用，以及研究动作。任何一个必要部分错了，这个检查点就不是完整正确。

当前动作规则为：已知风速至少 100 mph 时输出 prepare，低于 100 时 monitor，未知时 request_evidence。这是公开、确定性的研究规则，不是对真实应急建议质量的人工判断。

因此总体 86.2% 是当前受控任务的联合指标，不是模型的天气预测准确率，也不是仅风速数值的准确率。

### 7.4 三种成功率为什么不同

“检查点全对”问的是：任取本矩阵的一次回答，它是否全部正确。每方法每条件有 36 × 5 × 2 = 360 次回答。

“五轮全对”问的是：一次完整运行能否五个检查点全部正确。每方法每条件有 36 × 2 = 72 条轨迹。一个检查点失败，就会使所在轨迹不能算五轮全对。

“两次均五轮全对”进一步要求同一条基础 episode 的两次运行都五轮全对。每方法每条件只有 36 个这样的判断单位。本项目把它记为 pass^2。

pass^2 不是两次中至少一次成功的 pass@2，不是单点准确率的平方，也不是置信区间。因为错误在检查点、episode 和重复之间相关，不能把单次概率假设独立后相乘，替代这里的实测比例。

### 7.5 最值得在汇报中解释的结果

上轮状态方法加入干扰后，检查点全对率从 96.9% 降到 88.6%。只看后一个数字，可能会觉得系统仍相当可靠。

但同一方法的“两次均五轮全对”从 30/36 降到 15/36，即 83.3% 降到 41.7%。这揭示了不同评价粒度会影响对可靠性的判断：单次回答表现较高，不代表整段流程反复执行时都稳定。

这也是当前 benchmark 的一项实证价值：它能把短期回答正确与持续更新可靠分开呈现。现有结果仍局限于这个模型、这批来源和这套任务，不能直接宣布某种方法普遍最好。

## 8. 模型具体错在哪里：从统计到真实例子

### 8.1 先区分字段错误与回答错误

2,160 条回答各有四个字段，因此共有 8,640 个字段机会。字段归因发现 123 个值或状态错误，以及 259 个纯引用错误，合计 382 个字段错误。

完整错误的检查点是 2,160 − 1,861 = 299 个。一条回答可能有多个错误字段，所以 382 不等于 299，也不能把它们相加。

另有 43 个动作错误，可能与字段错误重叠。例如风速错了，按该风速选择的动作也可能错。它不是可以直接加到 299 上的另一批独立失败。

| 字段主要错误类别 | 数量 | 直观含义 |
| --- | ---: | --- |
| 状态或数值不匹配 | 123 | 应有的数值或 known/unknown 状态不对 |
| 同值旧版本 | 116 | 数字正确，但引用的版本已被替代 |
| 不存在的记录 ID | 42 | 引用没有对应的记录 |
| 错误有效窗口或测量种类 | 35 | 取了其他时间或其他类型的事实 |
| 行号越界 | 26 | 记录存在，但所指行不在范围内 |
| 错误实体 | 22 | 引用属于其他对象 |
| 错误变量或单位 | 10 | 来源支持的字段或单位与问题不符 |
| 异值旧版本 | 8 | 输出数值可正确，但附带引用的旧版本内容不同 |

“纯引用错误”表示值或状态已经正确，但引用规则没有满足。116 个同值旧版本占 259 个纯引用错误的 44.8%。只检查数值会遗漏这一类问题。

以下记录来自已保存的 P6 字段归因，不是教学编造。按原文件顺序，选取第一条主要错误为 superseded_same_value 的记录，没有按哪个方法最差来挑选。

| 项目 | 实际记录 |
| --- | --- |
| 来源组与受控样本 | AL052019，即 Dorian 来源组；U1、secondary、control 衍生 episode |
| 实验条件 | irrelevant_scope |
| 方法与重复 | answer_history，repeat 0 |
| 检查点与字段 | c2，maximum_wind_mph |
| 模型答案 | known，60 mph |
| 正确参考值 | known，60 mph |
| 模型引用 | record-62dacf3b5260c5a4f615951f，第 2 行 |
| 当前应引用 | record-0db797c9653dc4d169f593f5，第 2 行 |

“与前序载体相同”是观察到的关联，不能据此单独证明模型内部发生了哪一种记忆机制。要判断载体本身的因果影响，还需控制相同前缀和证据的表示实验。

这条受控记录使用 2040 年的实验有效窗口。它不是 Dorian 的实际未来预报，而是从该来源组生成的受控任务。完整记录保存在本报告配套的 evidence/p6_actual_error.json 中。

### 8.3 为什么要分开字面支持与当前版本

字面支持回答的是：“这条来源有没有写出模型所说的内容？”当前版本回答的是：“根据公开任务规则，现在应当由哪一版来源支持这个目标？”

在同值修订中，两个问题的答案可能不同。为了让读者判断任务要求是否合理，应分别报告数值、字面支持和版本正确性，而不是把它们全部折成一个无法解释的总分。

P7 已把这种区分进一步写入原生评分规则：可以检查旧公告是否字面支持指定目标的值，也单独检查它是否满足任务内的当前来源选择规则。

## 9. 配对比较说明了什么，又没有说明什么

### 9.1 为什么共享种子还要核对输入输出

P6 的对应条件共享采样种子，是为了减少不必要的随机差异。但相同种子本身并不保证所有硬件、调度和后端下逐比特一致，所以还需要实际检查。

额外无关作用域压力从 c2 开始出现。c0 和 c1 尚未暴露于这个新增因素，因此它们是重要的前置对照。实际核对发现，c0、c1 各有 216 对，共 432 对，请求与最终文本全部一致，两边都完整正确。

这使“差异在新增干扰出现后才发生”的描述有了证据。它不意味着后面所有差异都来自单个孤立机制。

### 9.2 曝光后的四类结果全部保留

每种方法在 c2–c4 有 216 对检查点。每对可以是两边都对、仅基础条件对、仅干扰条件对，或者两边都错。

| 方法 | 两边都对 | 仅基础对 | 仅干扰对 | 两边都错 |
| --- | ---: | ---: | ---: | ---: |
| 仅证据 | 151 | 45 | 14 | 6 |
| 上轮状态 | 168 | 37 | 7 | 4 |
| 全部历史 | 97 | 38 | 24 | 57 |

三种方法都是“仅基础对”多于“仅干扰对”，但反方向的改善确实存在。完整保留这四类，才能看到净变化由哪些配对组成。

只计算曝光后部分，基础与干扰条件的全对数分别是：仅证据 196/216 与 165/216，上轮状态 205/216 与 175/216，全部历史 135/216 与 121/216。这是补充切片，不替代完整预定矩阵的主分母。

全部历史的净下降较小，不足以称它最抗干扰：它在基础条件下已经较低，两边都错的配对也更多。比较鲁棒性需要同时看起点、终点和错误分布。

### 9.3 为什么暂时不能做普遍的机制结论

在 c2，两条件可能产生不同答案；到 c3，先前不同答案又可能进入载体。因此后续差异混合了当前新增材料和之前输出的影响。这叫闭环轨迹比较，意思是模型自己的输出会进入后续输入。

若要只研究 JSON 与文本表示的直接影响，需要从同一个保存前缀开始、看到同一份当前证据，只改变载体的表示形式。这个固定前缀诊断回答的问题与自主运行整段 episode 不同，不能混在同一可靠性表里。

统计上，当前只有三个独立风暴来源、两个重复。不能把 2,160 次相关回答当成 2,160 个独立天气事件，计算出很窄的置信区间后宣称对所有极端天气显著成立。

## 10. 从受控任务推进到官方预报原文

### 10.1 为什么需要新增这条研究线

P6 的优点是语义明确、错误可控、Gold 可以精确计算。它的限制也清楚：后续更新由研究程序构造，不能直接证明模型在自然形成的官方预报文本中会出现同样的问题。

因此下一步不是单纯增加受控模板数量，而是检查真实官方资料中是否存在可严格对齐、可追溯的版本变化，并将其变成独立任务。

来源试点选择 Francine 的 005–010 号和 Ida 的 009–014 号 NHC 预报公告，共 12 份。全部收到并通过两个独立实现的解析器对账，0 份隔离。保存了原始内容、来源地址、哈希、获取信息、规范文本及原始字节/行映射。

这些产品提供 95 行预报，其中 9 行为终止状态；同一绝对有效时刻的相邻覆盖版本形成 49 对，其中 23 对持续风速变化、24 对风速不变、2 对涉及终止状态。

两个解析器读取同一份官方产品，作用是交叉核验实现，不是两个独立气象观测源。12 份产品也只来自两个风暴，Ida 还与旧开发来源重叠。

### 10.2 一个真实 Francine 修订例子

固定目标：Francine 在 **2024-09-10 18:00 UTC** 的最大持续风速。

| 公告 | 发布时间 UTC | 对该目标时刻的明确内容 |
| --- | --- | --- |
| 005 | 2024-09-09 21:00 | 75 KT；位置 25.9N、95.9W |
| 006 | 2024-09-10 03:00 | 没有该目标时刻的明确预报行，包含其他有效时刻 |
| 007 | 2024-09-10 09:00 | 70 KT；位置 25.4N、95.6W |

对应原文节选：

```text
Advisory 005
FORECAST VALID 10/1800Z 25.9N  95.9W
MAX WIND  75 KT...GUSTS  90 KT.

Advisory 007
FORECAST VALID 10/1800Z 25.4N  95.6W
MAX WIND  70 KT...GUSTS  85 KT.
```

注意 MAX WIND 是最大持续风速，GUSTS 是阵风，不能因为后面的数字更大就替换前者。经度 W 在任务的有符号数值里表示负数。

第 005 号中，目标时间相对其中心参考时刻为 21 小时；第 007 号中为 9 小时。同一绝对有效时刻可以对应不同相对时效。如果拿两份公告里“同样相对时效”的行来比较，就可能对错日期。

### 10.3 第 006 号没有目标行时，任务为什么保留旧明确行

P7 明确声明：在已交付、可见的产品中，选择最新且明确覆盖同一目标有效时刻的预报。较新产品没有这一行时，不通过插值创造一个来源没写出的值，也不自动删除先前明确陈述。

这是一个任务内的已发布陈述解析规则。它**不证明**旧公告的该时效在真实气象业务中始终被认为“当前有效”，也不代表 NHC 将所有旧预报都判为错误。这是研究需要持续讨论的任务效度边界。

换句话说，当前要测的是“按明确规则找出可见资料中的目标预报陈述”，而非重建完整业务系统的预报生效政策。

### 10.4 五个时间概念需要分开

| 时间 | 含义 | 当前能否确定 |
| --- | --- | --- |
| issued_at | 产品所标注的发布时间 | 可从产品解析 |
| center_at | 文本中明确的风暴中心参考时刻 | 可从产品解析，不等同于数值模式初始化 |
| valid_at | 某一预报行所针对的未来时刻 | 可从预报行解析并补全日期 |
| retrieved_at | 本次归档内容被获取的时间 | 本次采集记录可确定 |
| available_at | 历史上首次能公开取得该产品的时刻 | 尚未证明，保持未知 |

P7 用发行顺序安排受控交付，并用当前交付产品的发行时刻定义未来查询截止线。这不证明当年的网络到达顺序，也不把归档获取时间当成历史可用时间。数值模式初始化时间同样保持未知。

## 11. P7 新增了什么：从资料变成完整原生任务

### 11.1 当前已经完成的不只是下载和解析

P7 实现了原生任务规范、数据编译器、独立公开求解器、评分器、调度、上下文检查、程序对照和可迁移 CPU 验证。它读取已保存的 12 份官方公告，没有新增下载，也没有触及 heldout。

参考编译器从原始字节重建双解析入库结果与支持位置。独立公开求解器使用自己的文本解析实现，只读取模型将看到的完整带行号公告。scorer 单独检查目标时间、状态、单位、数值、版本、字面支持和定位。

所以相比 P6 后的来源试点，P7 已经从“有了资料”推进到“有了一套可以运行并自动验证的原生任务”。但此阶段的执行对象是程序对照，尚不是 LLM。

### 11.2 46、276、257 和 1,542 分别是什么

先对每个风暴取全部已入库预报行的绝对有效时刻并集。每一个“风暴 + 有效时刻”是一个目标，共得到 46 个目标。

每个风暴有六份选定公告，也就是六个交付检查点。46 个目标与各自六次交付组合，得到 276 个候选查询。然后严格排除目标时刻已经不晚于当前参考时刻的 19 个非未来查询，最终保留 257 个。

| 计数 | 数量 | 怎样得到 |
| --- | ---: | --- |
| 独立风暴 | 2 | Francine 与 Ida |
| 公告产品 | 12 | 每风暴六份 |
| 来源预报行 | 95 | 各公告中的明确预报行，含终止行 |
| 目标 episode | 46 | 不同风暴与绝对有效时刻的组合 |
| 候选查询 | 276 | 46 个目标各与六次交付组合 |
| 非未来排除 | 19 | 不满足严格未来条件 |
| 纳入查询 | 257 | 276 − 19 |
| 每策略计划回答机会 | 1,542 | 257 × 三方法 × 两重复身份 |
| 方法/重复轨迹 | 276 | 46 × 三方法 × 两重复身份 |

候选查询与方法/重复轨迹恰好都为 276，但它们是两个不同的计数，不能互相替代。

每条目标 episode 的有效检查点数量不同：长度为 2、3、4、5、6 的 episode 数量分别为 2、2、2、1、39。它们的加权和是 257。因此原生运行器必须支持可变长度，不能继续假设每条都五轮。

### 11.3 三种查询状态如何形成

257 个纳入查询中，有 176 个 numeric、26 个明确终止状态、55 个 not_stated。

numeric 表示可见公告中存在该目标的数值预报。终止状态例如 DISSIPATED，要明确输出终止状态和 null 数值，并引用终止行；不能把它变成零风速。not_stated 表示当前可见资料尚无该目标的明确预报行，输出空数值与无引用。

目标目录来自整批声明的来源，因此一个被提问的目标时刻可能尚未在当前交付资料中出现。这是公开声明的查询设计，不是在模拟实验者事先不知道会出现哪些日期的惊喜查询。未来公告正文、答案及来源身份不会因此进入模型请求。

### 11.4 257 个检查点上发生了哪些变化

| 变化标签 | 数量 | 含义 |
| --- | ---: | --- |
| 首个检查点 | 46 | 每个目标 episode 的起点 |
| 仍未陈述 | 25 | 仍然没有可见的明确目标行 |
| 首次明确预报 | 30 | 目标预报第一次进入可见材料 |
| 新公告未覆盖目标 | 107 | 依任务规则保留先前明确行 |
| 覆盖版本间风速变化 | 23 | 同目标持续风速发生变化 |
| 覆盖版本间风速不变 | 24 | 风速相同，但仍要跟踪版本 |
| 涉及终止状态的修订 | 2 | 需要处理明确终止语义 |

这七类合计 257。24 个风速不变修订不代表坐标和限定语也完全不变。107 个覆盖缺口来自自然公告网格差异，并非为了制造困难而伪造的修订。

### 11.5 输出与 P6 有什么不同

P7 联合回答纬度、经度与最大持续风速。纬经度单位为 deg，北和东为正；风速单位为 KT。答案还必须包含 storm_id、绝对 valid_at、measurement_kind、状态和支持行定位。

原生任务不要求未来气压，不从当前观测气压推算未来风速，也没有 P6 的研究动作字段。原始公告中的阵风、观测、半径和限定语仍保留为完整可见上下文，但 v1 不把它们全部设为必答字段。

## 12. P7 的程序成绩怎样读，为什么还不是模型成绩

### 12.1 程序对照是给测量工具做检查

在投入模型采集之前，需要知道题目确实公开可解，评分能抓住想测的错误，缺失和无效回答会正确留在分母里。为此使用一个合法公开求解器和八个错误或异常策略。

程序不是通过 API 请求某个 LLM 生成的答案。它们按事先写好的规则从公开输入生成结果。三种方法和两个重复身份在这里主要验证调度、载体和核算逻辑，不提供随机模型可靠性证据。

### 12.2 九种程序对照的实际结果

| 程序策略 | 收到的回答 | 结构合法 | 完整正确 /1,542 |
| --- | ---: | ---: | ---: |
| 最新明确覆盖目标键 | 1,542 | 1,542 | 1,542 |
| 取最后展示行 | 1,542 | 1,542 | 72 |
| 按相同相对时效错配 | 1,542 | 1,542 | 606 |

### 12.3 错误程序为什么还能拿到不少正确项

“错误策略”表示该规则在一般情况下不能正确完成任务，不表示它对每道题必错。例如，最新文档恰好覆盖目标时，“只取最新文档”可能与合法策略一致。

当前气压策略对非数值查询保持不变，因此 486 个自然正确项有明确来源：26 个终止查询加 55 个未陈述查询，共 81 个，乘三方法和两重复身份为 486。不能为了让错误基线看起来更差而抹掉这些一致项。

缺失策略只有 780 个实际收到的答案，但计划分母仍为 1,542，另外 762 个计为失败。无效策略虽然收齐全部输出，也有 762 个不能拿到结构信用。这验证了固定分母处理。

最早来源策略还出现了 42 个“所有三个数值仍获字面支持，但当前版本错误”的回答。这说明真实资料也提供了区分字面支持与当前来源的机会。不过这是程序策略行为，不是已经观察到的 P7 LLM 失败。

### 12.4 上下文检查完成到什么程度

程序历史生成了 2,831 个不同请求，已用固定 Qwen3 tokenizer 计算实际长度。最长 prompt 为 16,059 tokens，加完整 8,192 输出预留，共 24,251，低于新任务共同上下文 32,768。

P7 没有为了塞进旧的 16,384 上下文而截掉来源行或错误历史。官方原文更长，任务版本因此使用新的上下文预算，并在未来实际后端预检后绑定运行配置。

但是程序历史的长度有限。未来真实模型可能生成更长的历史文本，每个实际请求仍需要重新做 tokenizer 检查。若溢出，应停止该次调度并按固定机会报告，而不是静默截短证据或挑选重试。

## 13. 为什么有 FAILED，却仍说 P6 已完成

### 13.1 模型采集完成，与整个作业全步骤成功不同

原始 P6 ACP 作业 pt-gxxtikov 的状态仍是 FAILED。它包含模型采集、报告与验证等步骤。模型采集器退出 0，已经保存全部 2,160 条回答；后面的原始 CPU 报告与验证步骤失败。

失败原因是审计程序对 EOS 的文本表现作了错误假设。EOS 可以理解为结束 token：后端保留了它的 token ID，但冻结设置要求最终显示文本不包含其停止标记。原审计却期待显示出这个标记，因此错误判定文本不一致。

另行冻结的 repeat_live_review 按实际绑定的渲染策略比较，核对了全部原始文本、答案提取、载体和分数。它没有重新生成模型答案，也没有改变 Gold 或评分语义。原作业的 FAILED、原始失败日志和捕获数据均保留。

所以准确的状态是：**模型矩阵已收齐并经独立 CPU 审阅完成核验，原始作业的后处理失败仍真实存在**。

### 13.2 这些验证工作具体带来什么信心

P6 的输出约束复核重放了 571,603 个最终输出/EOS token，未发现违反约束的 token。独立复制环境在原工程、模型权重和网络不可用的条件下重建了相关报告。

最终验收绑定 9,434 个文件。它们能支持“这批保存结果与报告一致、可被复核”的结论，不能支持“模型已覆盖更多天气事件”或“统计显著”。工程证据与科学外推是不同层面。

### 13.3 P7 的已保留失败

P7 第一版复制 CPU 隔离 wrapper 在成功重建对象后退出 1，因为 urllib3 导入时尝试做一个本地 IPv6 能力探测，被隔离层拒绝。外层检查原先把它作为未预期网络行为。

v2 wrapper 仍然拒绝这个探测，只对确认的特定模块、函数和本地地址单独识别记账，没有放开网络或原始路径访问。初始失败、依赖证据与后续成功记录都保留。

另一个大整数回归用例曾暴露 scorer 把巨大整数转 float 时崩溃。修复后，整数仍作为语义错误保留，评分过程不崩溃；初始失败也保存。此类通用实现修复与手工改某一道 Gold 不同。

P7 当前通过 64 个新增测试和 26 个相关历史来源测试，共 90 个测试；验收绑定 327 个证据文件。本次制作详细报告重新核对了 P7 文件哈希与关键数字，但没有再次执行全部科学实验。

## 15. 下一步怎样推进，每一步解决什么

### 15.1 第一优先级：原生采集器与独立聚合

现在缺的关键工程，是把冻结的 P7 任务接到真实模型，并能在多个 worker 部分失败时仍准确重建发生了什么。

新的 collector 要为每次请求保存原始输出、尝试身份和持久日志。它必须按各自轨迹的真实历史构造新请求，不能从程序对照或 Gold 初始化模型历史。

聚合器要独立重建每个 worker 的请求、载体、解析答案与分数，再按冻结的全局顺序合并。重复结果、未知尝试、缺失 worker、写入中断和归属变化都需要明确处理。一个不确定的提交不能通过静默再次生成掩盖。

完成标志应是：在模拟部分失败与重启情况时，机会不丢失、不重复计算、不被偷偷移交或补考，最终结果可独立重建。

### 15.2 第二优先级：后端测试与不生成的 H100 预检

正式采集前，要在实际 H100 上核验模型权重、tokenizer、推理后端、精度、上下文、结构约束和停止 token 到显示文本的行为。

这一步尤其要复用 P6 的 EOS 回归经验。token 列表和最终可见文本不是同一种对象，不能通过任意删特殊字符或空白来让审计“通过”。

预检不生成 benchmark 答案。预检的资源释放后，再启动最多四个正式 worker，确保同时最多四张 H100 的限制始终成立。

### 15.3 第三优先级：冻结第一次原生模型矩阵

| 项目 | 当前后续计划中的候选边界 |
| --- | --- |
| 模型 | 先沿用固定 Qwen3-8B，避免同时改变任务和模型 |
| 输入 | P7 v1 完整公告，自然发行顺序的受控交付 |
| 方法与重复 | 三种方法、两个重复 |
| 机会数量 | 最多 1,542；每个计划位置一次尝试，不重试 |
| 上下文与输出 | 32768 / 完整输出预留 8192，须在实际预检后绑定 |
| GPU | 最多四张完整 H100，四个 TP=1 独立副本 |
| 时间与资源候选上限 | 四小时阶段截止；四卡同时分配时至多十六 H100 小时 |
| heldout、付费 API、训练、LLM judge | 当前这一步都不包含 |

这些是计划中待预检后写入新 live freeze 的边界，不是当前已经消耗的资源。不能修改离线 execution 的 generation flag 来把旧包临时变成实测包。

四个 worker 的预览分配如下。每个目标的所有方法、重复和检查点留在同一 worker 中。

| Worker | 目标 episode | 计划回答 | 轨迹 |
| --- | ---: | ---: | ---: |
| 0 | 12 | 390 | 72 |
| 1 | 12 | 390 | 72 |
| 2 | 11 | 384 | 66 |
| 3 | 11 | 378 | 66 |
| 合计 | 46 | 1,542 | 276 |

这能分散计算，但不意味着必然四倍加速。加载、不同 episode 长度、生成长度、批处理效率和最后等待最慢 worker 都会影响实际耗时。正式结果应分别报告阶段时间、各 worker 时间和 token 使用。

### 15.4 第四优先级：等信息载体、第二模型和更多独立来源

首次原生任务实测之后，优先回答三个互不替代的问题。

等信息载体实验研究表示形式：从同一保存前缀分支，保留相同事实与错误，只改变表达方式。它不是重新从头自主运行的轨迹成绩。

匹配第二模型研究模型适用性：使用同一任务、证据预算、方法定义、输出轨道与评分。旧版 DeepSeek 结果不能替代新任务上的匹配实测。

扩展独立来源研究事件外推：预先规定年份、产品、选择顺序和排除规则，按风暴分组，而不是继续堆叠同一风暴的模板。全部八个原定 heldout ID 继续保护；Francine 已明确作为开发来源，Ian 仍不能因计划中出现过就拿来做开发演示。

更多 GPU 主要解决已定义矩阵的计算速度，不能代替这三类研究设计。

## 16. 怎样判断研究贡献，以及怎样交给 ChatGPT 精简

### 16.1 目前最有证据支持的贡献表述

第一，建立了明确区分事实键、状态更新、当前来源与定位的可执行任务，使逐题人工评分和 LLM judge 不是主评分的必要环节。

第二，完成了真实模型实测，并表明数值正确、当前来源正确和重复整段可靠是不同的测量层面。P6 的同值旧来源错误和单点/轨迹成功率差距，提供了具体证据。

第三，已经把这一思路推进到官方预报原文，建立独立求解与程序对照，并保留自然覆盖缺口、未陈述和终止状态等情况。P7 的贡献当前是任务与测量工具验证，模型表现是下一步。

这些表述不等于已经证明项目具有文献上的首创性。与已有静态问答、证据问答、长上下文、动态知识和多轮状态 benchmark 的关系，还需逐篇比较输入、更新语义、引用规则、评分、数据来源与统计单位。

### 16.2 当前最需要主动承认的限制

任务规则可由程序求解，说明当前主要测试 LLM 执行和保持这些规则的可靠性；不能直接推导为深层气象推理。最新明确覆盖来源的选择规则，也需要与业务解释边界共同呈现。

独立风暴来源少，且公开 NHC 历史档案可能已在预训练中出现。目前没有证明彻底排除预训练曝光。P7 使用完整官方原文改善任务自然性，但两个风暴仍不足以代表广泛天气场景。

方法比较混合了信息量、长度与历史错误，只有一个匹配的当前实测模型和两个重复。它支持条件性的描述，不支持普遍方法排名或总体显著性。

自动 Gold 与多实现对账减少了一些人工成本和实现风险，但共同的任务定义仍可能不合理。因此“无需逐题人工复核”与“无需研究者审查任务设计”必须分开。

### 16.3 一个适合你先讲清楚的口头版本

> 我们的 benchmark 关注极端天气资料不断更新时，LLM 能否维护正确状态，并把每个结论对应到当前来源。先用明确规则的受控任务建立自动评分体系，再进行真实模型实验。目前 P6 已完成 2,160 条 Qwen3-8B 回答，完整正确率为 86.2%。结果显示，即使数值正确，也可能引用旧版本；而单次回答较高的正确率，仍可能对应明显较低的重复整段成功率。
>
> 为了检验这种问题在自然资料中是否成立，我们进一步使用官方 NHC 预报原文，建立 P7 原生任务。它现在有 46 个目标、257 个查询，已经通过独立求解、评分与程序对照的离线验收。这里还没有模型成绩，1,542 是后续矩阵的计划机会。下一步要完成原生采集、多 worker 聚合和实际硬件预检，再开展首次原生模型实测，随后补充载体控制、第二模型和更多独立风暴。
