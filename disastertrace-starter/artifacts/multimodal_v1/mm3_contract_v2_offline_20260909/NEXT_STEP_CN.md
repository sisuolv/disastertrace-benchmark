# 下一步：先验证输出契约 V2，再做原子感知

## 为什么调整顺序

MM-3 已验证真实图片输入、H100 加载与前向计算，但 12/12 输出把 `state` 写成数组。
旧提示要求根对象包含 `state`，没有明确说明 `state` 本身是以地点 ID 为键的对象。
现有解析器一直要求这种对象结构。这是一项应补齐的公共契约说明；不能将首轮零个
格式合格答案解释成模型极端天气能力为零，也不能将失败数组自动转换后算作通过。

## 已实际完成的离线工作

- 新增 `multimodal_contract_v2`，明确 `state` 对象、地点 ID 键、每地点七个字段和唯一 JSON 键。
- 附上结构 JSON Schema；不嵌入正确值、当前权威来源、答案示例或下一步状态。
- 30 个公开请求只改变 `output_contract`；图片、证据、时间、查询点、规则和参考答案不变。
- 原有 30 份参考答案全部通过新 schema，公开像素程序在 30 个请求上仍与原参考一致。
- 41 项测试通过，覆盖数组结构缺陷、约束不编码逻辑答案、输入不被原地修改。
- 12 个候选请求均用真实 processor 完成 CPU 检查；使用明确标注的程序历史时，最大
  输入 5,130 token，加 2,048 输出预留小于 16,384。真实模型历史仍需逐次检查。

`CANDIDATE_PLAN.json` 保留原来的 5+5+1+1 开发设计，便于覆盖相同接口场景。
本目录的模型生成、GPU 作业与付费 API 调用均为零；它不是已测成功的 V2 模型结果。

## 后续执行顺序

1. 保留首轮 MM-3 的 12 个失败，给 V2 登记新的执行身份、起止时间和最多 12 次生成。
   固定同一模型 revision、BF16/SDPA、单 H100、贪心自由输出、2,048 token 上限。
   新运行独立建立自己的历史，不复用旧答案或程序答案作为模型历史。
2. 将 V2 请求、适配器、processor 和运行库重新冻结。核验资源槽位，先做无生成预检，
   再执行完整候选批次；失败仍保留、不重试、不扩充到四卡矩阵。
3. 门槛为 12 个回答均契约有效且以 EOS 完成。格式与语义分别报告，不把新旧两批的
   差异包装成无偏因果效果；如要比较提示方法，另做预先平衡的独立重复设计。
4. 接口稳定后，建立原子感知检查：两张真实地图乘三个地点，共六个地图–地点单元。
   分别报告单图空间关系、版本选择、缺失模态下的 unknown，以及 provenance 更新。
   原图、局部图、oracle_visual_facts 采用不同诊断标签；特权事实不能进入正常赛道。
5. 若主要失败来自感知，先改进可读性与原子任务；若版本过滤已能解决当前任务，明确
   报告其充分性。随后按事件扩充数据与统计设计，再考虑最多四个独立单卡 worker。

这六个地图–地点单元仍然只来自一个事件，不是六个独立风暴，更不是 24 个独立锚点。
多事件扩量、独立模型家族和正式 heldout 测试继续后置。常规准备沿用已有 GPU 授权，
执行门槛用于保证记录有效，不形成逐项人工复核或反复审批流程。
