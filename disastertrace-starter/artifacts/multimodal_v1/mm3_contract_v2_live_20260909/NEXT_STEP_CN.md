# 下一步：原子诊断与并行扩展

V2 在 12/12 请求上能输出结构可解析的 JSON，但地点覆盖为 10/12、完整正确为 0/12。
因此下一步要区分错误来自读取、定位、来源选择、逻辑组合还是沿轨迹重复自己的错误。

## 先完成原子诊断的离线设计

1. 空间感知：两张地图乘三个已公开地点，共六个地图–地点单元；先做单图、单地点
   的关系与定位任务，去掉版本切换和名单组合的负担。声明它们仍只来自一个事件。
2. 文本读取：针对真实公开的 watch-01/watch-02，单独输出 watched、artifact_id 和
   L 开头的行号；另列缺失名单条件。不能把 intensity excerpt 当作 watch 证据。
3. 规则组合：使用明示的公开输入事实检查三值逻辑，覆盖 true/false/null。若输入
   空间关系来自 oracle_visual_facts，明确标为特权诊断，不放入正常模型赛道。
4. 来源和查询覆盖：单独检查同有效时间的新旧版本选择、旧图重放、同值来源更新，
   以及当前查询集合增加 C。分开报告 JSON 结构、查询完整性、引用合法性和任务正确率。
5. 修订诊断：原子任务通过后再比较完整轨迹与独立检查点；完整轨迹仍传递自己的
   原始回答。不能直接用参考答案替换历史后称模型完成了正常任务。

每组先冻结公开请求、自动参考、输出契约和失败规则，再开展有限的新模型评测。
无需逐题人工 Gold 或 LLM judge。已有 V1、V2 的结果不重试，不重新解释为通过。

## 四卡如何发挥作用

当多个事件、模型或足够多的独立诊断单元准备好后，使用最多四张 H100 并行：

- 并行单位为完整独立轨迹，轨迹内部检查点保持顺序。
- 四个 worker 都有确定的任务清单与预算，包含排队、加载和预检的全局槽位不超过 4。
- 比较条件在各 worker 间平衡，避免把某个方法与某张卡或运行顺序完全绑定。
- 同模型、同输入长度的独立请求可进一步做批处理；报告实际吞吐、启动开销和显存。
- 小型接口探针仍根据实际开销选择卡数，不将四卡权限等同于任意扩大生成预算。

完成这些诊断后再确定需要更明确的任务说明、更强或不同模型家族，还是新的数据渲染。
随后扩充独立开发事件，再制定 heldout 与统计方案；不从单事件结果直接发布排行榜。
