# P4 之后的进一步计划

当前路线围绕 LLM 的证据处理能力展开：在天气记录持续更新的情况下，模型能否
维持正确状态、区分作用域、更新引用，并遵守明确的研究动作规则。标签由程序
产生，评分由确定性代码完成，继续保持无需逐题人工标注或 LLM judge 的要求。

## 1. 首先固定两条输出轨道的解释

自由 JSON 轨道继续测量模型遵守输出接口的可靠性。P3 的 340 个非法输出保留在
该轨道的分母和错误清单中。受约束轨道用统一 grammar 缩小输出形式的选择空间，
帮助观察语义错误；它仍允许错误数值、错误引用、错误动作以及部分违反任务
契约的组合。二者分别报告，不能把受约束后的分数替换为原始自由输出分数。

两条轨道的公开证据、数据、Gold、评分器和基础采样设置已经建立逐项比较规则。
模型输出变化会改变后续合法历史载体，因此应同时报告实际 prompt 是否一致。
相同随机种子并不意味着两条轨道的随机样本具有相同含义。

## 2. 下一个建议执行单位：level 4 难度包

上下文校准实际覆盖 216 个既有候选、3 种方法和 10 种程序载体，共 32,400 条
请求；其中 5,991 条唯一请求与真实 adapter 的 token 化及长度保护逐一核对。
每条请求都预留完整的 8,192-token 输出空间，上下文总上限为 16,384。

| 因素 | level 4 最大输入 | level 16 最大输入 | level 16 超预算行 / 5,400 |
| --- | ---: | ---: | ---: |
| 修订链 revision_chain | 6,630 | 15,041 | 1,487 |
| 无关作用域 irrelevant_scope | 7,002 | 16,128 | 3,240 |
| 旧记录重放 late_stale_replay | 6,992 | 16,054 | 1,080 |

三个 level 4 单元在全部已测程序载体下均满足预算。level 16 的输入本身尚未超出
16,384，但留给输出的空间不足以满足既定 8,192 上限。不能通过静默截断证据或
逐题降低输出上限，让这些候选混入同一个受控比较。

下一实现顺序建议如下：

1. 增加独立的 stress 数据 profile，冻结原始候选、Gold 等价证明、来源组、因素、
   有效强度和新的调度身份。现有 balanced verifier 固定为原始 36 episodes，
   不能通过直接替换 episodes 文件来绕过它。
2. 每个因素构成一个完整单元：36 episodes × 5 checkpoints × 3 methods = 540
   回答。三个 level 4 因素合计 1,620 回答，是后续单独冻结的范围。
3. 保持三种方法、相同 grammar、thinking、采样和固定分母；分别建立一次性执行
   目录、期限和自动停止后的前缀报告。先完成全量程序演练，再进行 GPU 推理。
4. 按因素报告相对于基础任务的语义变化、引用更新、未知状态、动作、token 使用量
   和长度失败。保留全部样本，包括没有可扩展 PATCH 的 6 个修订链 control。

这些候选仍来自同样的 3 个开发风暴，不能描述为新增 216 个独立天气事件。
程序载体校准也不是对任意 LLM 输出长度的保证：模型可能生成更长但合法的引用
数组或历史。真实执行继续采用明确的上下文保护和完整分母，保留此类停止原因。

## 3. 补齐同版本的模型与重复对照

完整 balanced 540 版本目前只有 Qwen3-8B 的实际模型覆盖，已分别完成自由和
受约束输出轨道。历史 DeepSeek
实验只有旧 18-episode / 270 版本，不能直接与完整 540 的总分组成排行榜。
建议为 DeepSeek 或另一个明确选定的模型准备同一 540 数据版本的适配。

对远程模型，先重新核实接口实际支持的是普通 JSON object、严格 JSON Schema，
还是其他约束能力。能力不同的解码方式分轨记录。重新确认当时价格、输出 token
口径及预算后，再建立独立的调用范围；旧的已消耗实验范围不自动成为新预算。

开发定位可以继续使用单次采样。需要报告方法优劣时，预先固定至少 3 个独立
种子，并版本化 repeat ID、trajectory ID、每次 seed、调度和预算。直接复制
540 行列表会造成历史载体或种子复用风险。重复数改变时，可靠性单元的分母与
门槛也应在推理前重新冻结。按来源报告配对变化，明确 checkpoint
和匹配分支存在依赖；只有 3 个来源组时，显著性和广域结论仍应克制。

## 4. 在正式保留集之前完成冻结

在开发集上固定任务生成分布、模板、数值种子、因素强度、输出轨道、模型设置、
重复次数、评分和失败处理后，再建立保留集执行包。分别区分新来源事件、新数值
或种子、未参与开发的操作组合这三个泛化目标。七个保留风暴继续保持未调用状态，
本轮没有训练，也没有依据保留集答案调整提示词或 grammar。

如果要加入更复杂的修订冲突、撤销或新的操作，先写明自动 Gold 的形式规则，
再独立实现公开证据 oracle 和针对性错误对照。现有规则不支持的操作需要新任务
版本，不能混入旧分数。选择变体依据预先规定的因素，不依据模型具体答错的题号。

## 5. 扩展为更完整的极端天气 benchmark

当前主要覆盖热带气旋来源的受控记录任务。可以继续拆成三个研究层次：结构化
记录上的更新推理、真实官方文本中的可追溯抽取、具有可验证标签的其他灾种任务。
各层单独说明数据来源、语言、任务构造比例和标签规则。

高温、寒潮、洪水等候选应优先选择包含结构化观测或预警更新链的公开数据。
纳入主评测前，要求来源可追溯、字段或规则标签可执行、错误对照可检测。区分
发布时间、生效时间和已经证明的公开可得时间。再分析数据和事后修订不直接充当
过去时点已经可见的证据。没有自动可核对标签的开放式建议题，可暂留为独立探索，
避免为了扩展灾种而引入逐题主观评分。

## 6. 工程验收与复查

后续各阶段继续保留真实 raw token、文本、推理边界、停止状态和每个方法的载体。
独立报告在无 GPU、无权重、无 API key 的环境重建。指标实现和分母修改都需要
单独版本及回归检查。独立 CPU 校准曾与本轮 GPU 采集并行，因此本轮耗时只作
描述；严肃的吞吐或延迟比较应另行固定资源隔离与测量协议。

当前 review 包可交给其他审阅者检查设计与代码。其审阅结果不参与逐题 Gold 或
自动评分。下一轮优先执行第 2 节的离线 stress profile 封装，再按新冻结范围
使用 GPU；这一建议不重启已经消耗的 P4 采集。
