# DisasterTrace：供 ChatGPT Pro 独立审阅的项目说明

文档日期：2026-09-07。以下实现、模型结果和验证记录对应截至 2026-09-06 已完成的工作。本文件整理现有证据，没有新增模型调用、外部审阅结果或测试执行。

希望审阅者评估的是：这个以极端天气资料为起点的 LLM benchmark，是否有清晰且值得测量的能力目标，当前实现与实验能支持哪些结论，下一步应该如何提高任务区分度和实验可信度。请特别指出会改变研究结论的协议问题，并区分必须先修复的问题与可以后续扩展的功能。

## 1. 项目目标与当前阶段

长期目标是评测 LLM 在持续到来的灾害资料中选择有效证据、更新显式状态、保留未改变事实、识别证据不足并提供可追溯答案的能力。当前可运行的天气主线聚焦 NHC 热带气旋公告文本。

项目评测对象是 LLM，不是数值天气预报模型。当前问题要求回答“截至本检查点，已提供材料支持的最新报告值是什么”，尚不评测未来天气预测误差、完整多模态感知、真实港口调度或真实工具执行。

用户明确希望不依赖新增的逐题人工标注、专家复核或 LLM judge。因此主线采用可自动生成参考答案、可确定性评分、可保留来源和失败原因的任务。这里的“无需人工复核”不等于原始资料绝对无误，也不等于任意自然语言事实都能被自动验证。

| 工作项 | 当前状态 | 能说明什么 |
| --- | --- | --- |
| 官方资料获取、来源记录、自动准入与事件划分 | 已完成当前小规模资料集 | 数据来源和排除原因可追溯 |
| 顺序回放、三种输入方法、严格回答解析、确定性评分 | 已实现并验证 | 有可执行评测链路 |
| DeepSeek 初始试用 | 已执行一次连接探测和 10 个 Ida 检查点 | 单事件烟雾测试，单独保留 |
| P0 证据评分修订及历史离线重评 | 已完成 | 同一答案在两版规则下可比较 |
| P1 三方法开发集实验 | 经一次明确授权的重启续跑后完成 | 90 个回答，91 次累计请求尝试 |
| 公共输出契约与输出预算校准 | 离线准备完成 | 270 次新请求的方案已具体化，尚无该实验的模型成绩 |

## 4. 模型具体看到什么、回答什么

每个检查点提供公共任务说明、当前检查点时间、研究规则、带行号的已交付原文，以及该方法声明的回答载体。每次调用都构建新的消息，不依靠隐含的服务端对话记忆。

模型提交完整的 `state` 和一个 `action`。`state` 含五个固定字段：

| 字段 | 当前任务中的含义 |
| --- | --- |
| `maximum_wind_mph` | 最新可用公告报告的最大持续风速 |
| `latitude_deg` | 报告的中心纬度 |
| `longitude_deg` | 报告的中心经度 |
| `minimum_pressure_mb` | 报告的最低中心气压 |
| `port_reopening_time` | 当前材料没有提供支持的开放时间控制字段 |

每个字段包含 `status`、`value`、`evidence`。已知值使用有限数值；未知值使用 `null` 和空引用列表。引用由 `record_id` 与原文行号组成。`action` 是 `monitor`、`prepare`、`request_evidence` 三个字符串之一。

公开研究规则是：风速已知且至少 100 mph 时 `prepare`，低于 100 mph 时 `monitor`，风速未知时 `request_evidence`。这是用于检验规则执行和状态变化的研究阈值，不是官方预警或港口操作建议。当前第五字段始终缺乏证据，是基本的不足证据控制，还不足以构成全面的“会拒答”测试。

| 方法 | 每次收到的原始证据 | 额外回答载体 |
| --- | --- | --- |
| `snapshot` | 截至当前累计交付的全部证据，包括重复到达的旧公告 | 无 |
| `structured_state` | 同上 | 本轨迹最近一次结构有效的模型决定，初始为 `null` |
| `answer_history` | 同上 | 本轨迹此前全部结构有效的模型决定，按顺序排列 |

这里的 snapshot 不是“只看最后一份公告”。三种方法看到相同的累计原始证据，因此当前比较研究的是已有原文条件下显式回答载体带来的行为变化，不能据此证明记忆依赖或内部记忆机制。

结构无效的答案完整保存并计为失败，但不替换此前有效状态。结构有效、事实错误的答案则原样进入载体，系统不使用参考答案修复它。不同事件、分支、方法、实验条件和重复之间必须隔离状态。

公共视图来自 [dynamic.py](src/disastertrace/automated/dynamic.py) 的明确字段选择。完整事件对象包含未来交付计划，解析后的记录包含参考字段，这些都属于 harness 内部数据，不能把整个 build 目录开放给模型。新契约仅扩展公共 instruction；其余证据与载体不变。

## 5. 时间语义与自动参考答案的边界

当前任务把三份原始公告放入明确声明的受控交付计划中。它包含迟到或重复的旧资料，要求模型区分“最后到达”和“最新发行且已提供”的报告。

必须区分三个概念：公告写明的发行时刻、资料中的事实适用时刻，以及资料真实首次公开可见的时刻。2026 年取得历史网页，只能证明取得了该存档，不能证明资料在历史检查点之前已公开到达每个用户。

因此当前主线的标签是 `schedule_origin=controlled_release`、`fact_origin=derived_from_source`、`gold_origin=generated_by_spec`。它没有声称复现严格证实的历史公开可用性。当前公告描述的是不同时间的连续观测，也不是“同一个有效时间窗口的预报修订”。后一种能力需要新的版本、事实键和替代关系，尚未实现。

自动参考编译器从准入资料和交付规则产生答案；评分器按固定值、状态、行定位及支持规则判断。独立审计、负例和变形测试用于发现两端共同出错的风险。自动化降低了新增逐题标注依赖，但不能让研究者跳过协议定义、来源检查或评测工具验证。

## 6. 评分：为什么要区分值、证据与未知

主指标是已知字段的 grounded correctness：模型必须给出正确值，并引用当前规则能够验证的已提供证据。格式成功率、数值正确率、未知正确率、行动正确率和总体 grounded correctness 分开报告，不混成一个不透明总分。

每个方法的 30 个开发检查点有固定的 150 个字段机会，其中 96 个应为已知，54 个应为未知。总体分数包含未知字段，因此仅报告总体分数容易掩盖对已知事实的失败。主要比较保留全部固定机会：无效、缺失和预算不足的回答都留在分母里。

V2 还报告 64 个由参考序列定义的变化机会、56 个保留机会、8 个来源刷新机会。自身错误恢复等条件指标保留模型相关的机会数；没有机会时报告 `null`，不当作 100%。行动规则较粗，只作为辅助指标。

### P0 的 V1/V2 变化

最初十个 Ida 回答的字段值和状态全部正确。V1 的严格 grounding 为 49/50，已知字段为 31/32。唯一差异是一个正确的 105 mph 风速引用了正文中有效的表述，而不是原参考固定的摘要行。

后来新增受限的 NHC 等价证据支持规则，允许经过验证的摘要或正文表述。相同十个回答在 V2 下变成 50/50，总体已知字段 32/32。原始回答、V1 结果和规则版本全部保留。这是评分规则改变，不是模型能力提升；V2 在后续 P1 正式运行前冻结，没有依据 P1 输出继续改评分器。

V2 版本是 `dynamic_score_v2.0`，证据规则是 `nhc_equivalent_support_v2`。它不是通用文本蕴含模型，不覆盖任意措辞、语言和来源。`evaluator_unverifiable` 表示该规则无法验证支持，不能自动推断模型说了一个错误事实。

详见 [README_SCORING_V2.md](README_SCORING_V2.md)、[EVIDENCE_SUPPORT_V2.md](docs/EVIDENCE_SUPPORT_V2.md)、[METRICS_V2.md](docs/METRICS_V2.md) 和 [OFFLINE_RESCORING.md](docs/OFFLINE_RESCORING.md)。

## 7. 已经执行的 DeepSeek P1 实验

P1 使用 `deepseek-v4-flash`、`reasoning_effort=high`、thinking enabled、`max_tokens=4096`，不指定 temperature。原计划为三个方法、三个开发风暴、各完整分支、一次重复，共 90 次新请求。早期一次连接探测和十个 Ida 回答单独保留，没有混入 P1。

原实验进行到第 79 次请求时机器重启，已保存 78 个响应，第 79 次结果未知，另外 11 个检查点未发送。后来用户明确同意一次单独的续跑修订：累计条件额度 USD 1.5、最多新增 12 次请求、仅重新发送原第 79 次未知请求一次。所有 78 个已有响应，包括无效答案，全部复用且不重试。

因此最终是 90 个收到的 benchmark 回答，对应 91 次累计请求尝试。原未知请求及其费用预留仍然存在。最终报告标为 amended continuation；原中断、无重试实验的部分报告单独保留。

| 方法 | 收到回答 | 结构有效 | V2 已知字段 grounding | V2 全字段 grounding | V1 全字段 grounding |
| --- | ---: | ---: | ---: | ---: | ---: |
| snapshot | 30/30 | 14/30 | 39/96，40.625% | 69/150，46.00% | 65/150 |
| structured_state | 30/30 | 30/30 | 96/96，100.00% | 150/150，100.00% | 139/150 |
| answer_history | 30/30 | 24/30 | 76/96，79.17% | 120/150，80.00% | 120/150 |

观察到的失败有很明确的结构：

- snapshot 的 16 个无效答案中，14 个触及输出上限：12 个最终内容为空，2 个只输出了部分 JSON；另外一个把 action 写成对象，一个交换了 state/action 结构。
- answer_history 有 6 个最终内容为空的输出上限失败。
- 全部 68 个结构有效回答的字段值、状态和行动均正确。snapshot 仍有一个引用位置未获支持：正确报告 45 mph，但引用到了移动速度所在行，非对应最大风速行。
- 有效回答上的高正确率只是条件诊断，不能替换表格中包含无效回答的固定分母。

这提示格式说明和推理/输出预算可能强烈影响观测成绩。历史载体还会提供有效 JSON 示例，而原公共提示没有明确写出 action 必须是字符串。这些是需要控制实验检验的解释，目前没有确定其因果贡献。

### 成本与时延

90 个保存响应报告 293,816 个 prompt tokens、170,378 个 completion tokens，共 464,194 个 tokens；其中 158,370 个 reasoning tokens 已包含在 completion 中，不能再次计费。

按捕获的适用价格，已收到响应的缓存感知费用小计为 USD 0.146989544，续跑新增 12 个响应的小计为 USD 0.023630952。完整实际总费用未知，因为原第 79 次请求没有使用量记录。高峰保守费用记账为 USD 0.354178，仍保留 USD 0.46678016 的未知请求预留；预留不是已测量的实际扣款。

平均 HTTP 传输时延分别约为 snapshot 19.832 秒、structured_state 6.782 秒、answer_history 14.154 秒。计时不包含解析、评分和准备，也不代表整个实验墙钟耗时。固定执行顺序、缓存和重启都影响比较，不能据此宣称某方法天然更快。

结果入口：[README_P1_DEEPSEEK.md](README_P1_DEEPSEEK.md)。完整的每事件、失败、用量和来源绑定见 [P1 REPORT.md](work/p1-deepseek-background-continuation-v1/report/REPORT.md) 与 [report.json](work/p1-deepseek-background-continuation-v1/report/report.json)。

## 8. 新的输出契约与预算校准：已完成什么

新增 [output_contract.py](src/disastertrace/automated/output_contract.py) 和 [calibration.py](src/disastertrace/automated/calibration.py)。原 20 个自动化源码文件、源解析器、回答解析器、provider 与 V1/V2 scorer 未修改。

`legacy_v1` 保持原请求字节；`explicit_v1` 向所有方法的公共 instruction 添加完全相同的明确字段类型、词法要求与 JSON Schema。没有提供填好的任务答案，没有要求 provider 的 `response_format` 或约束解码，也没有自动修复回答。解析器仍允许已知值的空 evidence 在结构上通过，评分时则不给 grounding 分。

新实验方案为：

| 实验条件 | 公共契约 | 最大输出 tokens | 新鲜请求计划 |
| --- | --- | ---: | ---: |
| legacy_4096 | 原说明 | 4096 | 90 |
| explicit_4096 | 公共显式契约 | 4096 | 90 |
| explicit_8192 | 相同显式契约 | 8192 | 90 |

每个条件均覆盖三个方法、三个开发风暴、完整两个分支。总计 9 个条件×方法组合、54 条五检查点轨迹、270 个评分机会，请求的输出 token 上限合计 1,474,560。条件和方法顺序按风暴轮换，以减轻固定顺序不均衡；这不消除缓存和时间干扰。

这三个条件可以比较“4096 时显式契约的变化”及“显式契约下提高预算的变化”。没有 legacy/8192 条件，因此不能完整识别契约与预算的交互效应。整个轨迹的变化还包含早期回答改变后续载体的间接作用。

已经生成的 128 个离线产物包括完整计划、九份配置、54 条未发送的初始请求和 1,080 个确定性程序回答。后者来自四个程序控制×九个组合×30 个检查点：正确抽取、错误地采用最后到达资料、不更新、以及注入无效回答的控制。这些不是模型输出，也没有证明任何一个 token 预算足够。

只预先生成初始请求，是因为后续真实请求中的载体取决于尚未收到的模型答案。不能把程序诊断回答或其他实验条件的回答填进真实模型历史。

### 为什么同时保存 actual trace 和 scoring projection

冻结的 scorer 会自行重建 legacy instruction。为在离线诊断中保留它，新 wrapper 先逐步验证 actual trace 的当前证据、契约、请求哈希、原始回答接受状态和载体，再单独生成只把 instruction 替换为 legacy 的 `scoring_projection.jsonl`。其余证据、政策、载体、回答和失败分母相同。

原 actual trace 完整保留；两份 trace 的哈希及投影规则都记录，输出显式声明 `actual_exposure_is_projection=false`、`live_collection_verified=false`。这是程序控制的评分兼容路径。projection 不是模型实际看到的提示，更不是新契约真实采集已通过审计的证据。

### 预算选择规则与尚未执行的部分

拟议规则要求完整且经过独立审计的 270 个响应及有效使用量记录。一个候选预算必须在每种方法中至少有 29/30 个结构有效回答、最多一个 `finish_reason=length`，并且没有采集或费用核算失败。选满足条件的最小共同预算，否则无选择；不按方法分别挑预算，也不只重跑失败组合。

该阈值是开发筛选规则，不是具有统计置信度的总体可靠性保证。当前只有测试过的聚合计数筛选函数，尚没有模型证据支持选择 4096 或 8192。

拟议新实验条件额度为 USD 3、最多 270 次请求、无自动重试。它还不是实际调用授权，也不保证能完成全部请求。未来运行前必须重新核验价格和模型限制；不能把 2026-09-06 的周日价格直接用于任意未来时段。按已捕获高峰价格，全上下文预留分别为 USD 0.46678016 和 USD 0.47218688；每次需要先预留，再按有效 usage 结算。全部请求都用满保守上下文上界会达到 USD 126.517248，说明 USD 3 是条件停止额度，不是这个上界的覆盖承诺。

详见 [OUTPUT_CONTRACT_V1.md](docs/OUTPUT_CONTRACT_V1.md)、[CALIBRATION_PROTOCOL_V1.md](docs/CALIBRATION_PROTOCOL_V1.md) 和 [plan.json](work/calibration-v1-preparation/plan.json)。新契约的真实采集路径、持久化调度、累计预算 guard 和独立采集审计仍待完成；当前没有 live launcher。

## 10. 已知研究限制

| 限制 | 对结论的影响 |
| --- | --- |
| 一个模型、三个已查看的开发事件、一次重复 | 当前只能做描述性校准，不能建立广泛模型排名 |
| 同事件分支和检查点相关 | 不能把 30 个检查点视作 30 个独立风暴 |
| 四个数字字段容易从标准公告中抽取 | 高分可能代表任务过于简单，而非完整灾害推理能力 |
| 原始证据累计全部保留 | 当前没有隔离记忆依赖、长期压缩或检索缺失 |
| 港口重开字段始终未知 | 有“固定答未知”的捷径，缺少同字段可回答的匹配反例 |
| 受控交付而非严格证实的历史公开可用性 | 不能声称真实历史 as-of replay 的全部因果前提成立 |
| 连续观测不等于同窗口修订 | 尚未评测真正的版本覆盖、冲突、撤销和部分更新语义 |
| 有限的证据支持语法 | 不能把所有未验证引用都解释为虚假事实 |
| provider 别名、缓存、服务负载与原实验重启 | 费用、时延与方法差异有混杂，别名也不能独立证明底层模型版本不可变 |
| 当前准入目录较小且有格式性排除 | 没有总体采样代表性、充分去污染或普遍解析覆盖的证明 |

最值得避免的结论是：“structured_state 达到 100%，所以它已解决极端天气推理”或“snapshot 低分证明模型没有记忆”。当前数据不支持这些推论。

## 11. 建议的后续工作顺序

### 第一阶段：把已有校准方案接入可审计的真实执行链路

实现支持显式契约的 collector 与独立 collection audit，并把契约版本、实际公共输入、最终 wire body 和接受状态一并绑定。不能简单沿用只会重建旧 instruction 的 P1 runner，也不能把诊断 projection 当作真实曝光记录。

实现持久化的 270 槽位调度、单一累计费用账本、调用前预留、错误或未知 usage 后停止、单次启动归属和防重复提交。每条轨迹使用自身真实有效答案；每个失败和未发送机会保留。先做不触网的故障、崩溃、恢复前缀、顺序和费用边界测试，再冻结执行包和实际调用范围。

随后在价格与限制核验、范围及预算绑定后执行新鲜三条件实验。保留原 P1 为历史资料，不拿旧 90 个回答替代新的 concurrent control。若预算未能完成整个矩阵，报告部分结果并不给出共同预算选择。

### 第二阶段：扩展能区分真实能力的任务语义

优先在独立命名、可自动验证的受控任务轨道中加入：

1. **部分更新**：patch 只更改指定字段，遗漏表示未更新；其他事实和值/来源必须保留。
2. **同有效时间窗口纠正**：明确事实键、issue time、valid window 和 supersedes；旧版本再到达不能恢复权威性。
3. **可恢复的证据缺失**：同一字段既有有证据样本，也有暂时无证据样本，之后再恢复支持；需要隐藏全部支持副本，不能只删摘要而正文还保留答案。

这些生成值、编辑和交付时间必须标成 controlled/generated，保留真实 NHC 轨道作为独立参考。参考编译器与 runtime 要有独立检查和变形关系测试，不能只有生成器自己验证自己。

冲突、撤销、过期和多实体多时间窗口可以随后加入。现有回答只支持数值或未知，新增 conflict 等状态需要明确的新协议，不能偷偷塞入原 schema。提高难度应基于预先定义的能力覆盖，不能只筛 DeepSeek 已经做错的题组成主评分。

### 第三阶段：验证泛化与可选的机制研究

在开发集冻结任务和评分后，预先规定共同模型、重复数和预算，再使用保留的七个 heldout 风暴。若看过 heldout 模型结果后修改协议，应将该结果标为探索性，并为新的正式评估另选未用事件集。

可增加第二模型家族与更多预先选定事件，报告每事件指标及依赖结构，而非只汇总题目数量。热浪等第二天气领域应在日期、单位、缺失值和参考答案都能自动验证时再纳入。

若论文的中心问题确实是记忆机制，可另设有限证据窗口和相同前缀的 carrier reset、删除或受控错误注入实验，保留无关事实控制。它们应作为单独诊断条件，不能由当前全证据比较直接推导。后续研究规划见 [OPTIMIZATION_ROADMAP.md](OPTIMIZATION_ROADMAP.md)。

## 12. 希望审阅者优先回答的问题

请优先根据可见代码和记录判断，不把计划中的功能当作已经实现。若缺少某个产物，请明确指出缺失如何限制判断。

1. **研究定位是否足够清晰？** 当前最合理的定位是“动态证据可靠性与状态更新”还是更窄的“顺序资料抽取”？哪种定位能被现有实验真实支持，主要创新应在哪里体现？
2. **格式与预算的校准是否应先于任务扩展？** 三个条件是否足以解决当前主要测量混杂；60 秒共同 timeout 是否会成为高预算条件的另一个限制；是否需要第四个条件或另一期实验？
3. **固定分母与已知字段主指标是否合适？** 未知控制、无效答案和引用语法边界是否仍可能夸大或低估能力；如何报告程序控制和满分样本而避免天花板效应？
4. **自动 Gold 与支持验证的可信边界在哪里？** 哪些失败可用独立实现、负例或变形关系检测，哪些任务天然不能在当前“无需新增逐题人工复核”的约束下可靠纳入？
5. **投影评分的边界是否清晰？** 当前离线 actual/projection 双记录能否充分解释兼容性处理；未来真实契约采集器与独立审计应怎样设计，才能不牺牲曝光可追溯性？
6. **P2 的最小有价值任务集是什么？** 部分更新、同窗口纠正、可恢复缺失应采用什么公开语义和反例，才能测出与简单“取最后值”不同的能力，又保持自动验证？
7. **实验规模与 heldout 策略应该如何调整？** 哪些结论需要第二模型、更多事件或重复；三个开发事件的结果应怎样展示而不产生伪精确的统计结论？
8. **发布与复现还缺什么？** 外部资料快照、许可证归属、路径绑定、环境和完整失败记录是否足以支持他人重新构建及独立核对，而不仅是阅读结果摘要？

建议审阅输出先列高优先级问题及其证据、对结论的影响和可执行修正，再给推荐的下一阶段最小实验。请避免仅罗列大量可选功能；需要明确哪些应该立即实施、哪些应延后，以及验收标准是什么。
