# DisasterTrace 后续阶段复查交接文档

本文面向没有参与前序对话的 ChatGPT Pro 或其他代码审查者。请同时审查研究设计、
测量有效性和代码实现，优先指出会改变结论的错误。文档中的运行结果以所链接的
冻结产物为依据；正在运行的阶段会在本次自主工作结束前更新。

## 1. 项目到底在评测什么

用户的长期目标是评测 LLM 在极端天气场景中的能力，并尽可能使用自动构建的标准答案，
避免逐题人工标注和 LLM judge。当前实际实现的核心任务更窄：读取官方热带气旋公告，
在公告按发布时间依次出现时，维护指定风暴、指定绝对预报时刻的状态，并引用正确版本的来源行。

例如，查询某场风暴在 9 月 13 日 06:00 UTC 的位置与最大持续风速。第 1 份可见公告覆盖
这个时刻，第 2 份公告没有对应时刻，第 3 份公告再次覆盖它且修改风速。当前任务规则是：
第 2 份出现时保留第 1 份的明确预报，第 3 份出现后改用第 3 份。更新时即便风速没变，
也需要引用最新覆盖版本及正确的行号。

这是对已发布预报的理解、版本选择、状态更新和证据引用。它没有让 LLM 根据大气状态预测天气，
不能用本项目的准确率替代数值天气预报技能，也不能据此声称覆盖了洪水、热浪、野火等全部极端天气。

“较新但没有覆盖该目标的公告不抹掉较早覆盖”是公开的任务解析规则。它不是关于 NHC 业务中
哪份预报仍然有效的外部事实判断。历史精确公开可见时间没有恢复，当前是受控的 issued-time replay。

## 3. 数据、时间和自动答案

原始资料来自 NHC 历史 forecast/advisory 正文，保存原字节、来源、获取时间、哈希、
解析产物和排除记录。两套解析路径进行核对；编译器再按显式目标时刻构建检查点和答案。
自动解析一致性降低了人为标注需求，但不能单独证明所有气象语义正确。

请特别检查两套解析器是否共享了会导致相同错误的规范化逻辑，以及终止状态、跨月/跨年时间、
经纬度符号、持续风与阵风、预报与当前观测的处理。程序中存在 synthetic fixture，
它们只验证软件，不能冒充真实风暴资料。

P10 新增 Dorian、Isaias、Henri、Fiona、Lee、Helene，使用各风暴最初 6 份编号公告。
最初解析接纳 26/36；随后版本化解析器支持 `POTENTIAL TROP CYCLONE` 标题，接纳 36/36。
最初 10 个失败保留在原目录，没有覆盖成“从未失败”。选取范围没有使用待测模型分数。

“最初 6 份编号公告”是一条可复核的取样规则，同时偏向风暴早期发展阶段；它没有覆盖
每场风暴完整生命周期，也没有专门保证登陆、峰值强度或快速增强片段。风暴名称多了，
并不自动意味着极端天气情境的种类和严重程度已经充分覆盖。当前公告和任务指令主要为
英文；中文交接文档也不代表已经完成中文或跨语言模型评测。

扩展任务共有 864 个候选检查点，其中 804 个保持目标在未来，60 个被规则排除。
标准答案包括 598 个 numeric、196 个 not_stated、10 个 DISSIPATED。
新增队列没有 terminal-revision 检查点，不能声称已经充分评测终止状态的版本变化。

对同一绝对预报时刻，资料中存在 138 次后续覆盖修订，96 次持续风变化、137 次位置变化。
邻接公告的预报时间网格经常交错，不能用相邻的相对 lead 标签代替相同绝对时刻。

全部用于当前新增推理的风暴属于开发用途。预先保留的 heldout 风暴没有进入这些模型运行。
公开历史资料也可能存在于模型训练语料中；未做 heldout 或去污染验证时，不声明不存在数据污染。

## 4. 三种输入方法

| 方法 | 每个检查点提供的主要信息 | 关键比较限制 |
| --- | --- | --- |
| snapshot | 当前允许可见的原始来源快照 | 输入长度与另外两种方法不必相等 |
| structured_state | 新证据与从该模型既往输出得到的结构化状态 | 之前答错的值可能进入后续状态 |
| answer_history | 新证据与该模型自己的既往最终答案 | 历史可能错误、冗长或格式损坏 |

每个请求使用新的消息列表，不依赖未保存的服务器会话。历史属于被评测模型自己的实际输出，
程序标准答案和诊断输出不能进入真实模型历史。审计器从原始捕获重建请求，检查这项边界。

不同模型即便使用相同源检查点和 seed，也会生成不同历史；因此 P7/P9 和 P11 的比较是
完整模型与输入方法的轨迹比较。它们不是保持历史前缀完全一致的单步因果干预。

P8 则显式保存原生前缀，再比较下一步的 JSON 与文本表示。但文本多了 36–54 个输入 token，
平均约 47.34；观察到的 5.92 个百分点差别仍包含表示长度等条件差异。只有两个风暴来源组，
不能据此宣称文本状态在普遍意义上优于 JSON。

## 5. 输出契约和评分

主分数要求全部相关字段同时正确：风暴键、绝对目标时间、forecast 类型、状态、
三个数值、规定单位、来源版本和引用行号。每个预注册槽位都在分母里，缺失答案不得删掉。
字段正确率、引用错误分类、回答覆盖率和完整轨迹成功率作为解释层单独报告。

坐标要求 N/E 为正、S/W 为负，单位字符串为 `deg`；风速要求最大持续风，单位为 `KT`。
输出单位写成 `N`、`W` 或 `degrees` 不会自动归一化后算主分数正确。这个严格约定写在
实际 system 消息中，但它仍然是解释模型低分时应单独展示的协议因素。

XGrammar 只限制公开输出结构。它仍允许错误的值、单位、风暴名、时间和来源 ID。
标准答案、正确来源 ID 或正确风速不会被注入动态语法。实际后端测试包含故意错误但
结构合法的答案，确认它们仍然能生成。

正确形状不等于正确语义；未完成的合法 token 前缀也不等于完整 JSON。
独立 token replay 验证生成过程没有越过静态语法掩码，最终 JSON 解析与语义评分另行进行。
推理 token 计入 8,192 的输出上限，超限不会单独为某个模型延长预算或补答。

当前真实预报任务的公开确定性 latest-explicit resolver 可以达到满分。
请判断任务更适合称为预报文档/版本理解基准，还是已经有足够证据支持更强的“状态推理”主张。
不能因为 LLM 答错，就推断任务必然需要深层推理或证明某种内部记忆机制。

## 6. 必须保留的失败：P9

P9 使用 DeepSeek-R1-Distill-Qwen-7B，四个作业分别保存 218、254、234、280 个回答后，
在准备下一批请求时触发上下文保护。986 个实际回答和 556 个未尝试槽位均保留。
所有作业平台状态仍是 FAILED；后续通过的是独立审计，不是把失败作业改写成成功。

每个被阻止的下一批请求中，都有一个 answer_history 请求超出 32,768 的完整上下文预算。
四个超限请求的“输入 + 预留输出”分别为 33,020、38,338、60,086、33,079 token。
同批其余三个请求本来可以容纳，但旧收集器会停止整个 worker，后面的独立轨迹也因此没跑到。
这既是观察到的模型输出问题，也是收集器故障隔离不足的问题。

保存的最终答案合计约 355 万字符，其中约 289 万是空白字符。某些答案超过 33 万字符，
而生成 token 数仍在上限内，因为 tokenizer 存在一次解码成大量空白的 token。
保留这些原样答案会把冗余内容带入之后的答案历史。离线程序对照的有限长度历史，
不能保证所有模型实际生成的历史都不超限。

该轮有 90 个长度结束、92 个无效最终 JSON、9 个推理到最终答案提取错误，这些数目有重叠。
在 894 个形状有效的答案中，只有 28 个使用要求的坐标单位 `deg`。
主分数 1/1,542 因此必须同时展示格式、单位、目标键、数值和引用层的情况。

DeepSeek 的模型卡推荐避免 system prompt；这轮保留了共同 system 契约。
所以当前分数衡量的是共同协议下的表现，没有优化每个模型的官方推荐提示方式。
此外，这个 distill 模型与 Qwen 有架构血缘，不能视为架构独立复现。

第一版 P9 观察进程还曾误判 ACP 在 STARTING 时返回的 replicas=0。修订的是外部观察器：
仅在明确的过渡状态下接受“运行副本数暂为零”，继续核对原始单卡申请；终态仍严格验证。
旧失败状态保留在 `finalization_01`，实际完成的审计在 `finalization_02`。
观察器修订没有重新提交模型作业，也没有替换任何模型回答。

## 7. P11 与 P12 的关系

P11 在 P10 的同一开发任务上比较 Qwen3-8B 和 DeepSeek-R1-Distill-Qwen-7B。
每个模型有 804 × 3 × 1 = 2,412 个计划回答，两个单 H100 worker，合计四卡。
同一目标的轨迹保持在同一 worker，两个模型使用相同槽位、seed 和分配规则。
各自的历史仍由自己的模型回答产生。

P12 是看到 P9 空白退化之后单独注册的新实验。唯一预先指定的解码变化是关闭任意 JSON
格式空白：引擎和请求 guide 都使用 `disable_any_whitespace=True`，独立回放使用
`any_whitespace=False`。任务、标准答案、提示契约、采样、模型权重、上下文和输出上限不变。

实际 XGrammar 0.1.23 的这个选项采用默认 JSON 分隔符空格。最初测试样例用了不带空格的
紧凑 JSON，导致两个模型各 7 项测试失败；这些日志保留。修正测试样例后，两个后端各
11 项测试通过，包括“额外填入 512 个空格会被拒绝”和“语义错误答案仍然被接受”。

P12 不是对 P9 或 P11 答案做清洗。两组真实轨迹分别生成，后续历史会不同。
即使 P12 的结果更好，也不能把变化解释成保持历史完全相同的单步因果效应。
关闭任意格式空白也不保证字符串长度有界、不保证完整 JSON、不保证语义正确，
更没有修复旧收集器的整 worker 停止策略。

P11/P12 只有 repeat0。继承评分器的 `both_repeats` 字段名具有误导性：它实际上聚合
所有已计划 repeat，并不强制两个。新分析层独立重建并标为 `whole_target_single_repeat`。
不得把这两组的该指标写成“两次重复均成功”。旧评分器与原报告保持冻结。

P13/P14 补充同样的提示位置干预：完整 system 契约原文加两个换行，再加原 user 内容，
作为一条 user 消息交给各自冻结的原生 chat template。没有增加示例、单位提示或正确答案。
每个模型各计划 2,412 个新槽位，两张 H100，并保留逻辑消息、实际渲染消息及 token ID。
对照针对模型卡提醒的协议因素，保留所有历史运行，不能称为对旧失败的补答。

因此扩展队列实际比较三种协议条件：P11 的 system/任意格式空白、P12 的 system/默认 JSON
空白，以及 P13/P14 的 user/默认 JSON 空白。后两项角色对照在读取 P11/P12 分数之前注册。
这不是完整的提示角色乘空白规则析因实验，不能估计任意空白条件下的角色效果或假设效果可相加。
两模型对照分开冻结与排程，以在全局四卡限额内衔接运行。

另对三个程序控制策略、两个模型共 14,472 对已保存的诊断请求做了完整输入核对。
逻辑消息和采样设置逐对相同；DeepSeek 改为 user 位置后输入 token 数全部不变，
Qwen 全部减少 5 个 token。两者实际渲染文本和 token 序列均发生变化。
这项检查使用程序控制历史，不能替代真实模型轨迹上的输入比较，也不能宣称 P14 做到了
相同 token 数。记录为 `artifacts/autonomy_10h_v1/program_role_prompts_01.json`。

## 8. 实验与工程验证各自证明什么

```mermaid
flowchart LR
    A[官方公告原字节] --> B[两条解析路径与版本化审查]
    B --> C[公开来源与确定性参考答案]
    C --> D[冻结任务和槽位]
    D --> E[实际模型请求与原始 token 捕获]
    E --> F[独立请求重建与确定性评分]
    F --> G[CPU 迁移复算]
    G --> H[验收哈希与可还原证据包]
```

程序诊断证明收集、缺失处理、评分和重建路径在指定对照下运行正确，不是模型推理结果。
硬件预检实际加载指定 H100 与模型后端，但禁止生成，证明资源和配置可用。
真实模型验证需要有对应 ACP 申请、模型请求、原始返回和审计记录。

CPU 迁移复算会复制执行源码、tokenizer、请求和输出，阻止读取原项目与模型权重目录，
阻止网络与子进程，并核对复算报告。它减少对运行现场的隐式依赖，仍不能证明标准答案本身
完全符合外部气象事实，也不是训练数据去污染证明。

哈希清单证明文件版本一致，不能替代代码或研究设计审查。请核查验收记录的实际覆盖范围，
不要只根据某个 JSON 中的 `status: passed` 接受“实验正确”的结论。

## 9. 统计解释与不足

主要表格报告预注册分母、收到回答数、严格正确数、格式与字段分项，再按风暴与方法展开。
缺失槽位保留为失败。已收到答案的条件准确率只能作为补充，不能替代完整计划分母。
自然风暴是主要依赖组，多个未来目标、检查点和采样重复不等于多个独立风暴。

P7/P9 有两个风暴组和两次重复，P11/P12 有六个风暴组和一次重复。
目前以描述性差异为主，不提供把数千检查点当独立样本得到的虚假精确显著性。
新增分析同时提供按检查点加权的总体结果和每场风暴等权的宏平均，避免规模差异掩盖反转。

需要继续改进的方面包括：更多独立来源与天气类型、终止状态修订覆盖、严格时间可见性证据、
冻结后的 heldout 运行、独立模型家族、官方推荐提示方式的对照，以及收集器在单条轨迹失败时
继续执行其他独立轨迹的能力。本轮不会把这些未完成事项写成已经解决。

## 10. 请复查者优先回答的问题

1. 当前任务名称与论文主张是否准确？什么证据才足以从“文档与版本理解”升级到“状态推理”？
2. 最新显式覆盖、未知状态和终止状态的规则是否一致，是否与实际指令、解析器和评分器对齐？
3. 双解析和公开程序基线是否可能共享系统性错误？哪些具体反例应加入软件测试？
4. 标准答案、未来证据、程序诊断或另一个模型的历史是否有进入真实请求的路径？
5. 主分数对单位字符串与引用行号的严格要求是否合适？应增加哪些独立分项，而不修改既有主分数？
