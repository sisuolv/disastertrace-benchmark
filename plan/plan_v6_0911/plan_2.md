**我建议更激进地改变“评测对象”，而不是继续增加数据、模态和任务数量：把 DisasterTrace 从“灾害证据理解与追踪 benchmark”，升级为“有时间与资源约束的主动预警评测环境”。**

最值得作为论文核心的问题是：

> **当时间和取证预算有限时，AI 能否主动找到真正有用的灾害证据，并将其转化为比既有预报更有价值的提前判断？**

这里的“有价值”，不只是预测最后对了，还包括：**是否在需要行动之前判断出来、是否避免不必要的误报、额外查询与计算是否值得。**

这比上一轮“加入滚动预测”更进一步。你原稿明确将实际天气预测、撤离质量和经济收益排除在已有结论之外；PDF 第 16 页也承认当前任务尚未验证预报技巧或业务价值。新的主线应当正面补上这个缺口，但用可以客观结算的窄任务实现，而不是直接跳到开放式应急决策。

**建议的升级版一句话定位：**

> **DisasterTrace 评测 AI 能否在异步证据、有限取证预算和预警时限的约束下，主动选择并核验多模态信息，持续修订同一未来风险，并改善相对既有预报的及时性与误报—漏报权衡。**

下面是我认为最值得押注的具体路线。

# 一、先讲清楚：为什么“多模态＋预测＋Agent”仍然不够新？

进一步检索后，有几个直接近邻意味着我们需要再次收紧定位。

| 已有工作已经覆盖什么你的论文不能仅靠什么来区分                 |                                        |                                                                                                                                                                                                             |
| --------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Extreme Weather Bench**               | 高影响天气事件、事件相关预报验证，以及用于缓解评估偏差的边缘事件       | 不能笼统说现有天气 benchmark 都只看全球平均误差，也不能把加入非灾害样本单独当创新。([arXiv](https://arxiv.org/html/2605.01126v1 "https://arxiv.org/html/2605.01126v1"))                                                                         |
| **SIREN，2026**                          | 预测、影响评估、响应决策和端到端工具链                    | “从预测走向行动”已经是已有研究目标。([arXiv](https://arxiv.org/html/2607.24588v1 "https://arxiv.org/html/2607.24588v1"))                                                                                                     |
| **EarthVerse，2026**                     | 多源科学调查、证据使用、研究过程与执行预算                  | 不能说已有 Agent benchmark 没有过程、工具或预算；更具体的差别是，其交互、延迟和 token 统计不进入主评分。([arXiv](https://arxiv.org/html/2608.23525v1 "EarthVerse: Benchmarking Scientific Agents AcrossDynamic Earth Systems and Natural Hazards")) |
| **Bayesian Linguistic Forecaster，2026** | 在循环取证中更新数值概率、语言证据与未解决问题；还讨论基于信息价值的停止准则 | “记忆状态＋滚动概率＋自主检索”也已有直接方法，不能只把它迁移到天气就宣称重大创新。([arXiv](https://arxiv.org/html/2604.18576v4 "https://arxiv.org/html/2604.18576v4"))                                                                              |
| **2026 年天气预报经济价值研究**                    | 在不同成本—损失情景下比较预报价值，并考虑复合损失与反复误报         | “增加一个经济价值指标”本身同样不是新的科学问题。([World Bank Reproducibility](https://reproducibility.worldbank.org/catalog/556 "https://reproducibility.worldbank.org/catalog/556"))                                              |

因此，我认为真正有机会的不是其中某一个模块，而是一个**此前这些评价通常没有共同固定的实验问题**：

> **在同一事件、同一基础预报、同一信息可用性和相同预算下，一个系统究竟应该查什么、什么时候停止查、什么时候提交预警，才能产生可验证的增量价值？**

这与一般“工具用得对不对”“最终报告写得好不好”不同，也不要求你重新训练一个天气基础模型。

但需要明确：\*\*主动信息获取本身已有理论和 Agent 研究基础。\*\*我们应争取的是新的灾害任务、自然数据条件和可解释实验，而不是声称首次提出主动取证或信息价值。([arXiv](https://arxiv.org/abs/2608.19202 "https://arxiv.org/abs/2608.19202"))

# 二、最应该解决的痛点：不是“模型不知道”，而是“知道得太晚、查错了东西，或者没有产生收益”

我建议将论文动机集中到下面三种断裂。

## 1. 信息已经存在，不代表系统会及时取得并使用

在你的旧任务中，证据主要由评测器按顺序提供。新任务可以进一步要求：

> **在当前能够取得的资料里，模型应该优先查看哪个来源、哪个地点、哪个时间段？**

这会把问题从被动理解升级为主动信息选择。

例如，系统可以继续阅读三份同源报告，也可以查询一个关键上游测站。两条路径都可能产生漂亮的分析文本，但它们消耗预算、带来的新信息和影响的预测目标可能完全不同。

## 2. 最后正确，不代表在预警上有用

假设一个模型在灾害发生前一小时才正确识别危险，而任务要求至少提前六小时准备。

它的最终分类可以是正确的，但**不满足这次任务的及时性要求**。

更重要的是，一份非常准确的新影像，如果在决策截止时间之后才发布，就不能被计入此前的预警收益。它仍可能有助于事后制图或后续风险判断，但不是同一个用途。

WMO 对预警系统的讨论本来就包含观测网络、数据交换、预测、影响预警及及时传递，而不是仅有一个预测模型。因此，这个研究问题与真实预警流程有明确联系。([World Meteorological Organization](https://wmo.int/resources/publication-series/global-status-of-multi-hazard-early-warning-systems/early-warnings-all-focus-hazard-monitoring-and-forecasting "https://wmo.int/resources/publication-series/global-status-of-multi-hazard-early-warning-systems/early-warnings-all-focus-hazard-monitoring-and-forecasting"))

## 3. 加入 AI，不代表优于已有预报

这是我认为你应该主动回答、而不是回避的问题：

> **当官方预报或专业模型已经给出不错的判断时，LLM/VLM 额外做了一轮取证与推理，到底改善了什么？**

改进可能来自新观测、局部空间理解、时间对齐或错误恢复；也可能没有改进，反而增加成本、延迟和误报。

**把“AI 的额外贡献是否值得”变成可测量问题，会比证明“LLM 在天气材料上会犯错”更有实际意义。**

# 三、建议的核心任务：一场有截止时间的“主动预警考试”

我建议主轨围绕一个固定未来目标运行，不再以一张图片或一条问答为基本单位。

例如：

> **“测站 A 在明天 08:00—14:00 UTC 的水位是否会超过提前登记的阈值？任务要求在指定截止时间之前，决定是否启动一个简化的准备措施。”**

这是**拟议任务**，不是已经找到并运行的真实案例。简化准备措施只用于公开评价情景，不是现实撤离或道路关闭指令。

每个系统获得相同的基础预报、初始信息和工具权限。随后资料逐步变得可用，系统自行选择查询或等待，并持续提交对同一未来结果的概率。

| 系统选择可能发生什么benchmark 要测什么 |                  |                 |
| ------------------------ | ---------------- | --------------- |
| 连续读取同一预报的文本、地图和表格        | 消耗预算，但未必获得新的独立观测 | 是否把重复呈现误当成新增证据？ |
| 查询相关上游观测，再结合目标区域地图       | 可能获得与未来目标有关的新信息  | 是否选择了真正有用的来源？   |
| 等待更清晰的影像                 | 影像可能在预警截止后才可用    | 是否为了更确定而错过有效窗口？ |
| 更新概率，但没有及时提交准备判断         | 最后的预测可能不错        | 预测能力是否转化为及时响应？  |
| 因一张旧图重新出现而回退             | 旧状态重新影响后续预测      | 版本追踪失败是否产生实际代价？ |

\*\*这个任务不要求存在唯一正确的工具调用顺序。\*\*不同路径都可以有效，最终比较的是合法信息下的预测、及时性、误报—漏报和成本。

这也契合你原先“不新增逐题人工标注、不用 LLM judge 作为主评分”的约束：不必让专家逐条写出标准调查过程，只需要定义可核验目标、资料权限、时间约束和结算规则。原稿也是通过限制任务范围来换取确定性评分，而不是完全消除研究者对语义的判断。

# 四、我认为最值得争取的三项实质创新

## 创新方向一：让“取得信息的选择”影响预警结果，而不是只影响回答长度

上一版主要问“新证据来了，是否正确更新”。更激进的版本问：

> **系统是否值得为了这份证据花费时间和预算？**

建议设置三类对照：

**固定取证策略**按照预定顺序查询；**主动策略**根据当前目标和已有证据选择下一次查询；**完整资料条件**作为额外诊断，观察访问限制究竟造成多大影响。

核心输出不是“调用了多少工具”，而是：

> 在相同预算下，哪个策略获得更好的预测？
> 在相同预测质量下，哪个策略需要更少查询？
> 当要求更早发出预警时，哪个策略的性能下降更小？

这可以产生一组**预算—预警质量曲线**，而不只是一张平均准确率表。

但必须避免把实验中的分数差直接称为“真实期望信息价值”。对某个系统，新增信息有无收益需要实测；自然事件中，我们通常没有每个检查点的真实条件概率。

**这里能测的是：特定证据访问策略在固定条件下的实际增益，而不是自动获得一个全知的最优取证策略。**

---

## 创新方向二：把“多模态”升级成“证据是否真正独立、有新增价值”

我认为这是比单纯加入卫星图更有潜力的一点。

现实中可能出现：

> 一份数值预报 → 一张概率地图 → 一份摘要表 → 一段新闻或公告。

它们看起来来自不同模态，但可能共享同一个上游产品。

因此：

> **三种模态一致，不一定意味着三份独立证据支持同一个结论。**

CEMS 已经实际采用矢量数据、地图和汇总表分批提供的方式。这为调查“不同呈现形式先后到达”提供了真实入口；但同一产品的几种格式，不应被自动当成几次独立观测。([Copernicus EMS](https://mapping.emergency.copernicus.eu/news/rapid-mapping-products-delivered-faster-and-with-new-formats/ "https://mapping.emergency.copernicus.eu/news/rapid-mapping-products-delivered-faster-and-with-new-formats/"))

建议你增加一个专门的**来源关系对照**：

| 条件真正改变了什么应分析什么 |             |                 |
| -------------- | ----------- | --------------- |
| 同一观测换一种呈现形式    | 可读性或表示方式    | 是否帮助模型理解原有信息？   |
| 同一产品被多个渠道重复转述  | 重复曝光        | 是否出现没有收益的置信度膨胀？ |
| 同一目标获得独立新观测    | 信息内容        | 是否改善预测与校准？      |
| 新资料描述其他时间或地点   | 表面更新，但作用域不符 | 是否错误修订当前目标？     |

这里不能机械要求“看到同源地图后概率绝对不许变化”。新的表示可能帮助模型读懂此前没理解的事实。**正确实验应把感知改善、真正新增信息和重复计数分开。**

这个设计的实际价值是：系统不仅要知道“来源新不新”，还要知道\*\*“这究竟是新证据，还是旧证据换了一种外观”\*\*。

它也让你现有的 provenance 从格式要求，升级为预测与预警中有可验证后果的机制。

---

## 创新方向三：区分“模型没做好”与“当时根本没有足够及时的信息”

这是另一个值得作为核心贡献的诊断视角：

> **一次预警失败，在什么条件下可以被避免？**

不要把所有失败都算成“模型能力不足”。建议区分：

| 情况需要什么证据支持诊断？        |                     |
| -------------------- | ------------------- |
| 必要资料在截止前根本不可用        | 真实发布时间、交付记录或明确的受控条件 |
| 资料可用，但系统没有查询         | 同一可见目录、预算和取证日志      |
| 已查询，但视觉或文字理解错误       | 独立事实参考与感知诊断         |
| 理解正确，但状态没有更新或被旧状态覆盖  | 保存前缀、状态载体干预         |
| 预测已经较好，但准备判断过晚或选择不合理 | 同一概率、公开决策规则和截止时间    |

\*\*注意，这不是说一定可以把总误差精确分摊成五个互不重叠的百分比。\*\*这些因素会相互作用，必须用匹配对照逐项检验。

例如，给模型正确视觉事实之后成绩提高，只能说明在该诊断条件下感知环节限制了表现；不能直接宣称已经证明了模型内部某个记忆机制。

更有价值的论文结论会是：

> **在相同数据可用性下，一部分失败可以通过更合理的取证和状态处理减少；另一些失败主要受制于证据到达时间，增加推理并不能补救。**

这是待检验的研究假设，不是我们现在已经有的数据结论。

# 五、实际意义怎样评价？不能再只用“最后答对了吗”

## 1. 预测质量继续用成熟指标，不为 novelty 生造总分

二元未来事件可以用 Brier score，并按不同提前量分别报告：

```math
\mathrm{BS}=\frac{1}{N}\sum_i(p_i-y_i)^2.
```

其中 `p_i` 是预测概率，`y_i` 是后续观测结算结果。概率评分本来就是现有预测研究的基础，不应把它写成新指标。([arXiv](https://arxiv.org/html/2604.18576v4 "https://arxiv.org/html/2604.18576v4"))

需要固定共同的评价检查点。**不能让模型只在自己最有把握时提交，然后用这些精选提交计算主分数。**

超时或没有更新时，也要对所有方法使用一致的回退规则，例如保留最近一次提交或相同的初始基线。

## 2. 决策价值采用公开的成本—损失情景

首版可以非常简单：在截止时间之前，做一次二元准备选择。

一个示意性成本函数是：

```math
J_\pi= \frac{1}{N}\sum_i \left[ C_i a_i+ L_i y_i(1-a_i)+ C^{\text{query}}_{\pi,i} \right].
```

`a_i=1` 表示及时做出任务中的准备选择；`C_i` 是准备成本；`L_i` 是漏报罚分；最后一项是查询成本。

\*\*这只是公开评价情景，不是已经估计出实际经济损失。\*\*最简形式假设及时准备消除情景内的漏报罚分，这也不代表现实措施能够完全防止损失。

成本—损失评价已有长期气象研究基础，近期研究还表明，不同成本、风险与损失假设可能改变模型优劣判断。因此，应报告多个情景，而不是挑一个最有利的权重。([ECMWF](https://www.ecmwf.int/en/elibrary/76153-skill-and-relative-economic-value-ecmwf-ensemble-prediction-system "https://www.ecmwf.int/en/elibrary/76153-skill-and-relative-economic-value-ecmwf-ensemble-prediction-system"))

## 3. “提前”必须与误报一起看

不能奖励一个系统从第一轮开始就对所有目标喊危险。

建议比较：

> **在相同误报水平下，能够多早识别目标风险？**
> **在同样最低提前量要求下，漏报有多少？**

数据必须包含可确认未发生目标危险状态的监测窗口，以及“有明显前兆但最终没有越过阈值”的情形。EWB 已经针对类似评估偏差加入边缘事件，你应借鉴，而不是把它当作自己的独立首创。([arXiv](https://arxiv.org/html/2605.01126v1 "https://arxiv.org/html/2605.01126v1"))

还要区分：为了诊断而构建的平衡样本，与真实监测中的事件发生率并不相同，不能直接拿前者宣称部署校准。

**最终建议保留三块结果：预测质量、时间与成本价值、证据合法性。不要把它们任意加权成一个难以解释的总分。**

# 六、为了让方案真正落地，我建议新增主场景优先选洪水

\*\*研究方向可以更激进，数据工程反而应该更集中。\*\*我不建议第一版就全面覆盖十种灾害。

结合这次查到的官方接口，我会优先调查：

> **洪水测站数值＋测站地面影像＋空间目标／设施相关阈值。**

这比只从 GEE 拉一些遥感图，再配上灾害新闻，更容易形成预测与实际结果的联系。

## 一个值得优先核查的新入口：USGS 的组合数据

USGS 官方水数据平台提供连续水位、流量及测站信息，同时列出了 **Real-Time Flood Impacts（RTFI）**：其中的设施位置经过测量，并关联附近的实时测站。([Water Data APIs](https://api.waterdata.usgs.gov/ "https://api.waterdata.usgs.gov/"))

它的 **NIMS** 则提供测站相机元数据和可以按日期窗口查询的影像文件清单。([Water Data APIs](https://api.waterdata.usgs.gov/docs/nims "Getting Started with the NIMS Imagery API"))

这使下面的任务成为一个值得调查的实际方向：

> **根据截至当前的水文观测、地面图像和空间信息，预测指定未来窗口是否会超过与目标相关的水位阈值。**

相较于纯粹读出“风速为多少”，它与具体地点的风险更接近，也有机会使用后续测量自动结算。

但有三个必须保留的边界：

\*\*其一，官方存在入口，不等于你需要的每个事件都具有完整图文序列。\*\*要先核对测站、相机、时间范围和质量是否重叠。

\*\*其二，不能因为某个设施靠近测站，就把测站水位直接等同于设施处水位。\*\*只有来源提供了足够明确的关联、阈值和必要的基准转换，才考虑设施相关任务；否则退回测站超阈值预测。

\*\*其三，超过相关水位阈值，不等于已经证明道路关闭、桥梁损坏或建筑受损。\*\*这些仍然需要不同的结果证据。

另外，影像可能并没有额外预测价值，尤其当数值观测已经充分描述了状态。应当让实验回答这一点，而不是为了证明多模态必要，故意削弱数值基线。

**我建议：洪水作为新增主示范，现有 NHC 作为诊断与后续迁移；其他灾种等主实验成立以后再加。**

# 七、怎么做实验，才能证明这不是“把几种已有方法拼起来”？

论文最需要的不是二十个消融，而是少数能够否定替代解释的实验。

## 实验一：AI 的增量究竟来自哪里？

所有系统使用相同基础预报和相同合法工具，比较：

| 基线作用                   |                  |
| ---------------------- | ---------------- |
| **专业／官方预报＋公开决策规则**     | 回答是否需要额外 AI      |
| **同预算的固定顺序、最近优先或随机取证** | 回答主动选择是否优于简单策略   |
| **版本过滤检索＋结构化状态**       | 排除“只是加了时间过滤”这一解释 |
| **强概率预测 Agent 的匹配适配**  | 避免只打败上一条答案或简单摘要  |
| **候选的时限与来源感知策略**       | 检验你提出的机制是否带来净收益  |

同一个专业预报可能已经利用过部分观测，不能把这些资料重新给 VLM 就自动当作独立信息增益。应保存可核查的初始化时间和来源关系；不清楚的依赖关系明确标为未知。

完整资料、正确视觉事实和 Oracle 状态条件，应当单独作为诊断，不能与同预算方法混排。

## 实验二：模型排名会不会随着任务目标改变？

同一批系统分别按以下目标评价：

> 静态理解正确率；
> 未来概率预测；
> 截止时间前的误报—漏报权衡；
> 包含取证成本的情景价值。

**值得检验的假设是：静态图文高分或复杂 Agent，并不必然对应更好的及时预警价值。**

不能预先保证一定出现排名反转，但这个实验本身能回答读者关心的“高分究竟意味着什么”。

## 实验三：新信息、重复信息和迟到信息，是否被正确区分？

固定同一事件与未来结果，分别改变：

> 相关资料按时或延迟到达；
> 同源资料重复呈现；
> 旧版本再次到达；
> 无关地点或有效时间的资料加入。

重点观察预测、校准、查询成本和及时性，而不是只看模型是否修改了答案。

这里干预的是**系统看到信息的条件**，不是改变真实天气。因此，可讨论信息访问对系统表现的影响，不能把它说成证明了气象因果机制。

## 实验四：错误能否恢复，恢复是否还来得及？

在保存的相同前缀上，对历史状态做 Actual、Masked、相关编辑和无关编辑等对照。

不仅看后续是否改对，还看：

> 在新的可靠证据出现以后，系统是否及时摆脱错误状态？
> 修正发生时，是否仍在有效预警窗口内？

这将你已有的状态追踪与未来预测真正连接起来。

## 实验五：跨事件、跨来源和前瞻验证

主划分按独立事件、流域或复合事件组，而不是按图片和问答随机划分。

尤其要避免同一气旋的风灾和洪水被拆到不同集合，从而制造虚假的“跨灾种泛化”。

最后增加一个小规模前瞻影子测试：提前冻结模型、协议和目标，记录实际资料到达与后续结果。它用于增强时间有效性，不直接证明没有训练污染，更不涉及真实应急部署。

# 八、论文可以附带一个轻量方法，但不要变成第二个大项目

如果只给 benchmark，没有展示“哪些机制可能有效”，论文故事可能仍不够完整。

我建议附带一个小型方法，重点只有三件事：

\*\*维护有来源关系的可撤回状态。\*\*不仅保存上一答案，还保留对象、有效时间、证据来源、是否同源派生，以及哪些结论依赖它。

\*\*围绕决策相关的不确定性选择查询。\*\*不是哪个问题最不确定就查哪个，而是优先关注“这次查询是否可能改变当前准备选择”。开发集上的统计或冻结启发式可以作为起点，不必新增 RL。

\*\*剩余时间不足时及时提交。\*\*不要为了生成更长、更完整的解释，错过任务窗口。

这套方法不应声称知道真实期望信息价值，也不要让 LLM 自己写出的“这条信息很有价值”充当评分依据。

**你要展示的是：一个明确的小机制，是否比更长的上下文、更多的工具调用和更复杂的通用 Agent 更值得。**

# 九、现有工程怎样接到这条主线，而不是全部重做？

我建议将已有工作重新定位为三层：

```text
已有文本／状态／来源任务
        ↓
作为感知、对齐与更新诊断
        ↓
新增固定未来目标与观测结算
        ↓
新增预算、时限与主动访问
        ↓
评价预测与及时预警的增量价值
```

你已经建设的来源保存、公开／私有隔离、自身历史和独立复算，仍然是优势。需要新增的是**查询动作与执行收据、公开截止规则、成本情景、来源派生关系和结果结算**，而不是重新写所有旧模块。

GEE 继续作为资料构建后端即可。正式主实验使用冻结快照，在线采集用于构建新版本和前瞻测试。仅按 GEE 的日期筛选并不能证明历史可用性，因为 `filterDate` 对应的是 `system:time_start`。([Google for Developers](https://developers.google.com/earth-engine/apidocs/ee-filter-date "https://developers.google.com/earth-engine/apidocs/ee-filter-date"))

实施顺序建议压缩为三个里程碑：

| 里程碑真正要交付什么继续推进的条件 |                                |                      |
| ----------------- | ------------------------------ | -------------------- |
| **A：预测闭环**        | 少量真实事件、固定未来目标、合法输入、真实观测结算、专业基线 | 不依赖未来资料，结果能够客观结算     |
| **B：主动预警主轨**      | 有限工具、预算、时限、来源关系和配对干预           | 强基线之间出现可解释的策略差异      |
| **C：泛化与前瞻**       | 扩大独立事件，增加迁移场景和真实到达记录           | 结论不只来自单一来源、单一事件或受控噪声 |

EWB 已有公开代码、事件组织和评价模块，相关部分应优先复用，而不是自己再搭一套完整数值天气预测评价体系。([GitHub](https://github.com/brightbandtech/ExtremeWeatherBench "GitHub - brightbandtech/ExtremeWeatherBench: Benchmarking of machine learning and numerical weather prediction (MLWP & NWP) models, with a focus on extreme events. · GitHub"))

# 十、怎样判断这次升级真的成功了？

我会用下面三个问题，而不是“模型是不是被难倒”来判断。

**第一，是否产生了旧 benchmark 难以回答的结论？**
例如，两个系统都能读对资料，但只有一个能在有限预算下及时使用关键证据；另一个需要完整资料才表现好。

**第二，是否解释了 AI 什么时候值得用、什么时候不值得？**
如果专业预报加简单规则已经最好，应保留这个结论。它不意味着 benchmark 失败，反而说明评测没有通过削弱基线制造收益。

**第三，是否将实际意义控制在已有证据范围内？**
可以说降低了公开情景下的决策成本、改善了固定误报水平下的提前量；不能由此直接说减少了现实伤亡或经济损失。

最终论文最值得争取的三条贡献是：

> **一个由真实信息可用性、未来目标、预算和时限共同定义的交互任务；一套区分迟到、过期、同源重复与状态错误的配对数据；以及与相同基础预报匹配、能够衡量 AI 增量价值的评价体系。**

\*\*我的整体判断：这比继续做“大而全的多灾种多模态问答集”更值得推进。\*\*它的激进之处不是工程范围更大，而是把主问题从“模型会不会理解材料”，推向：

> **模型能否在还来得及的时候，找到值得看的证据，并作出值得其成本的判断？**

详细的研究重构、实验设计、数据准入和阶段验收已整理为补充文件：

[**下载：DisasterTrace 限时主动预警与 Novelty 重构方案**](sandbox:/mnt/data/DisasterTrace_ActiveWarning_Strategy/DisasterTrace_ActiveWarning_Novelty_Blueprint_CN.md)**结合这次源码核对，我的结论是：现有数据格式能够支撑已经定义的 NHC 文本任务，但还不能直接支撑你希望做的“在线、多灾种、多模态、主动获取证据并持续修订判断”的 benchmark。问题不是完全没有相关代码，而是两套代码路径尚未真正接通。**

而且需要纠正此前一个过强的判断：\*\*仓库里已经有图片输入、增量状态策略、证据门控和四臂状态干预的通用实现。\*\*不能再笼统地说“目前只有文本能力”。真正的缺口是：这些通用组件的契约和验证还比较初步，已验收的原生实验使用的是另一套较窄的纯文本接口。

# 二、当前数据格式满足哪些要求，又卡在哪里？

## 1. 原生主轨的格式确实比较窄

`forecast_task/contract.py` 直接固定了：

```python
FIELDS = ("latitude", "longitude", "max_sustained_wind")
STATUSES = ("numeric", "DISSIPATED", "ABSORBED", "not_stated")
```

引用则限定为：

```text
source_id + forecast_line + wind_line
```

而且 schema 不允许额外字段。这对当前任务很清楚，但意味着你不能仅在数据中增加一张图、一项洪水面积或一个概率区间，就让现有主轨自动支持它。**输入、输出、参考编译和评分都需要新契约。**

`forecast_task/compiler.py` 也按照同一逻辑构建任务：按公告发行时间排序，从整个来源集合提取目标有效时刻，生成查询机会，再分别输出公开材料与私有参考。这是一个完整的**冻结档案任务编译器**，但不是持续发现新事件、新产品和新目标的在线环境。

## 2. 通用格式已经留了扩展位置，但“有字段”不等于“功能已成立”

| 要求当前代码情况是否足够 |                                                  |                                  |
| ------------ | ------------------------------------------------ | -------------------------------- |
| 图片输入         | `ModelRequest.image_paths` 会转换成实际图像消息            | **基础接口有了**                       |
| GIS 数据       | 有 `Modality.GIS`，但渲染器对所有非 image 文件都直接读文本         | **不够**：GeoTIFF、ZIP、NetCDF 不能这样处理 |
| 图像区域引用       | 有 `EvidenceReference.region_id`                  | **不够**：还需要区域存在性、所属图片及空间对应验证      |
| 历史可见性        | 通用 `Artifact.available_at` 要求时间区间；原生数据明确为 `None` | **契约不兼容，需要显式适配**                 |
| 状态修订         | 有 ADD／KEEP／UPDATE／RETRACT／KEEP\_UNKNOWN          | **有基础，但值更新与依据刷新未分清**             |
| 多灾种          | `Episode` 必填 `storm_id`；原生变量是气旋专用                | **需要通用事件与变量定义**                  |
| 在线使用         | 已有 NHC HTTP 下载和获取记录                              | **仅达到档案采集，不是持续在线评测**             |

这些判断分别对应 `models.py`、`adapters.py`、`policies.py`、原生编译器和来源采集器。

**我的建议不是推翻现有格式，而是把影响研究结论的字段，从松散的** **`metadata`** **提升为有验证规则的正式契约。**

# 三、这次发现的几个关键问题，会直接影响后续论文结论

以下问题主要出现在**通用框架**。不能据此断言历史 P7 成绩有误；P7 的来源和行号评分采用另一套实现。

## 1. “填写了交付列表”，并不意味着模型只看这些资料

`Checkpoint` 有 `released_artifact_ids`，但自然执行路径中：

```text
EvidenceGate → 所有满足 available_at 的资料
IdentityIntervention → 原样返回这些资料
```

没有依据 `released_artifact_ids` 进一步控制交付。

我构造的探针中，检查点声明只释放 A，但 A、B 都满足可用时间，实际自然路径返回了 **A 和 B**。

\*\*影响：\*\*以后你即使在 JSON 里写了“地图 B 延迟到下一轮”，也可能没有真正改变模型输入。

需要正式拆开：

> **可以取得的资料 → 本次实际交付的资料 → 当前策略实际读到的资料。**

这三个集合不能用一个字段代替。

## 2. 当前“旧版重放”不是我们讨论的那种重放

`StaleVersionReplay` 的实现会移除指定新版，再加入其合法父版本。

也就是说，它实现的是：

> 新版被拿走，改给旧版。

而不是：

> 新版仍在上下文中，又重新出现一份旧版，检查模型会不会被带回过去。

局部探针确认：对新版 B 执行后，结果只剩旧版 A。

两者都可以是合法实验，但研究问题不同。更重要的是，目前使用 `set/frozenset` 表示资料，无法保留“同一份旧图又交付了一次”的顺序和重复次数。

**建议增加独立的** **`DeliveryEvent`****，不要只在 Artifact 集合上做加减。**

## 3. 值保持与来源刷新，目前会互相冲突

`StateLedger.apply()` 遇到 `KEEP` 会直接跳过。因此，模型即使为相同数值附上新版依据，账本也不会刷新。

用 `UPDATE` 保持相同数值可以更换依据；但通用 scorer 的 `must_preserve` 比较的是**整个** **`SlotState`** **对象**，包括来源和更新时间。探针显示：数值仍为 60，仅来源从 A 变为 B，也会得到 `preservation_correct=0`。

这不一定违反旧契约——旧契约可能就是要求整个状态不变——但它不能直接用于新的“局部修订”评价。

建议明确分为：

**必须改变值、必须刷新依据、必须保持值、需要重新检查但结果未必变化。**

还要区分“环境要求更新”与“模型纠正自己上轮错误”。后者不应被算成无关误改。

## 4. 区域引用存在，但与来源的绑定还不可靠

当前 `StateLedger` 只保存 `artifact_id`，会丢掉提交中的 `span_id/region_id`。原始提交里仍可能找到定位，但下一轮只拿账本时不能完整恢复它。

另外，通用 scorer 分别核对“有没有要求的来源 ID”和“有没有要求的区域 ID”，没有验证区域是否属于该来源。

我构造了一条引用：提及正确来源 A，却把属于 A 的区域名挂在 B 上；当前函数仍给出 `grounding_correct=1`。这是**评分函数层面的反例**，不代表真实历史数据中已经出现这种问题。

后续支持关系应绑定为：

```text
artifact_revision_id + asset_id + locator
```

而不是几个互不约束的字符串集合。

## 5. 通用图像运行器不能直接接替已验收采集器

早期通用 adapter 会在异常时最多尝试四次，且在返回前就解析模型输出；通用 runner 则在整条 episode 结束后才写轨迹。解析失败或中途异常可能让原始响应未按预期落盘。

因此，正确的复用方式应是：

> **复用通用框架的图像和状态接口，接入后续实验已经建立的原始记录、失败隔离和独立核算机制。**

不是因为旧框架已经能发送图片，就直接开始几千次多模态生成。

全部 8 个探针及具体输出已保存在文末审查包中；其余两项确认了通用 Artifact 接受反向有效时间区间，以及无法用 `None` 表达未知 `available_at`。

# 四、数据格式应该怎样升级，才能同时支持多模态和 online？

我建议采用\*\*“不可变来源修订＋有序交付日志＋状态提交”\*\*，核心是六个对象，而不是再增加一份庞大的问答 JSON。

| 对象应解决的问题                    |                                             |
| --------------------------- | ------------------------------------------- |
| **ArtifactRevision**        | 这究竟是哪份产品、哪个版本、哪些原始字节？保存多个上游依赖，不绑定单个 episode |
| **AvailabilityObservation** | 我们在什么端点、什么时候实际看到这个版本？历史首次可用时间的证据是什么？        |
| **DeliveryEvent**           | 哪个分支在什么顺序、什么时候向模型交付了它？允许旧内容重复交付             |
| **QuerySpec**               | 问哪个区域／地点、变量、测量种类、有效窗口、阈值，以及按什么规则选择来源？       |
| **BeliefCommit**            | 模型当前的值、知识状态、未知原因、完整依据及修订操作                  |
| **ReferenceRecord**         | 当时可支持的答案与事后验证结果分别是什么？不能混成同一个 Gold           |

### 必须新增或正式化的字段

\*\*时间上：\*\*观测时间、有效区间、发行时间、处理时间、指定端点首次发现时间、获取时间、模型交付时间。

\*\*空间上：\*\*产品覆盖范围、坐标系、像元大小、有效掩码、观测覆盖率，以及地理坐标与展示图片像素之间的映射。

\*\*语义上：\*\*观测／预报／重分析／公告陈述分别标识；概率档位、持续风、阵风等不能混用；`unknown_reason` 至少区分未交付、未观测、云遮挡、过期、冲突和目标不兼容。

\*\*来源上：\*\*原始产品、重绘图、裁剪图和语言摘要保留依赖关系，不能被计成四份独立证据。

STAC 很适合复用为地理资产与检索层，但它不会替你完成模型交付、参考答案和状态评分；这些仍需要 DisasterTrace 自己的协议。([STAC Specification](https://stacspec.org/en/about/stac-spec/ "https://stacspec.org/en/about/stac-spec/"))

向后兼容时，旧 `forecast_task_v1` 保持原样。旧数据无法证明的历史可见性继续留空，不能为了通过新版 schema，把 `issued_at` 填成 `available_at`。

# 五、online 能力可以做到，而且应该成为研究设计的一部分

## 1. 当前已经有“网络下载”，但还没有完整的“在线数据流”

`forecast_source/pipeline.py` 已保存 HTTP headers、`retrieved_at`、原始字节和哈希，这是可复用资产。

但该路径绑定固定风暴及公告范围，一次性创建采集目录，并严格核验预定选择。它是**有边界的历史档案采集**，不是增量发现、持续轮询、版本替换追踪和在线任务编译。

建议新增 Provider 层：

```text
discover → fetch → normalize → commit_snapshot → detect_revision
```

其中 `discover` 不能只记“已经下载到哪个观测日期”。后续可能补发旧观测时间的资料，或修订已有产品；需要产品版本／更新时间游标，或有预算的重叠窗口检查。

## 2. GEE 可以负责获取和处理，但不能自动提供历史版本真值

GEE 的 `filterDate` 使用的是 `system:time_start`。它不是“查询历史某一时刻，当时数据库中能看到什么”的接口。([Google for Developers](https://developers.google.com/earth-engine/apidocs/ee-imagecollection-filterdate "https://developers.google.com/earth-engine/apidocs/ee-imagecollection-filterdate"))

官方 IMERG 集合更直接说明了这一点：临时产品可能被更新版本替换，`status` 由 `provisional` 变为 `permanent`，当前还存在向 V08 迁移的产品边界。([Google for Developers](https://developers.google.com/earth-engine/datasets/catalog/NASA_GPM_L3_IMERG_V07 "https://developers.google.com/earth-engine/datasets/catalog/NASA_GPM_L3_IMERG_V07"))

所以：

> **今天查过去的日期，拿到的不一定是过去当时能拿到的版本。**

需要从现在开始记录实际发现过程，并为研究用到的有限区域保存版本化快照。GEE 可以导出这些栅格及空间处理结果；同时固定投影、分辨率、表达式和渲染方式。([Google for Developers](https://developers.google.com/earth-engine/guides/exporting_images "https://developers.google.com/earth-engine/guides/exporting_images"))

## 3. 建议明确三种 online 层级

| 层级做法我建议的定位    |                                 |                   |
| ------------- | ------------------------------- | ----------------- |
| **在线获取、离线运行** | 取得近期数据后形成固定资料包                  | 最快落地的工程版本         |
| **持续采集、逐批冻结** | 不断加入新事件，但每批数据和协议固定              | **适合作为论文主榜单**     |
| **在线主动监测**    | Agent 决定查什么、何时等待、何时修订；查询具有耗时与成本 | **适合作为更激进的研究主任务** |

第三种不应直接让所有模型在不同时间查询公共网站再共用榜单。更稳妥的办法是：先采集真实产品与响应记录，再在固定事件时间线上提供可回放工具；真正 live 的运行另列，完整记录外部服务影响。

### 数据源先接三组就够

\*\*NHC：\*\*复用现有气旋文字与 GIS，对应同目标预报修订。

\*\*OPERA DSWx-HLS／DSWx-S1：\*\*对应洪水／地表水空间证据与覆盖限制。官方产品明确提供云、阴影、无效区域及覆盖元数据，但两种传感器的类别定义不同，不能直接共用一个 mask 表；DSWx 也不是天然无误的洪水真值。([Google for Developers](https://developers.google.com/earth-engine/datasets/catalog/OPERA_DSWX_L3_V1_S1 "https://developers.google.com/earth-engine/datasets/catalog/OPERA_DSWX_L3_V1_S1"))

\*\*NASA FIRMS：\*\*通过 API 获得火点资料，用于检测出现、时效和未知保持。火点信息与“火已熄灭／火场边界”仍需独立任务政策。([NASA-FIRMS](https://firms.modaps.eosdis.nasa.gov/api/area/ "https://firms.modaps.eosdis.nasa.gov/api/area/"))

这已经可以验证跨灾种能力，不必一开始铺开所有卫星和气象产品。

# 六、如何更激进地提升 novelty？我建议从“被动回答”转向“主动消除关键未知”

单纯将“文本＋图片＋多灾种＋状态更新”拼在一起，仍有很强的近邻竞争。

| 已有工作已经覆盖什么你的新增重点应在哪里      |                               |                                                                                                                        |
| ------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Extreme Weather Bench** | 高影响天气事件、观测与预报验证               | 与其互补，评价资料使用和监测过程；不能用引用正确率替代真实预测技巧。([arXiv](https://arxiv.org/abs/2605.01126 "https://arxiv.org/abs/2605.01126"))       |
| **EarthVerse**            | 多源灾害调查、主动证据发现、可执行参考、过程评价和证据扰动 | 重点不是再做事件资料包，而是逐时刻的可支持状态、补证成本和修订时效。([arXiv](https://arxiv.org/html/2608.23525v1 "https://arxiv.org/html/2608.23525v1")) |
| **DORA／SIREN**            | 地理工具与灾害工作流、预警链                | 必须证明动态证据变化如何改变中间判断，而不只是完成一次工具链。([arXiv](https://arxiv.org/abs/2605.11633 "https://arxiv.org/abs/2605.11633"))          |
| **StateMemBench**         | 当前／过期状态、关系依赖及匹配控制             | 加入真实观测覆盖、时空兼容和证据获取代价，而不只是换成天气字段。([arXiv](https://arxiv.org/abs/2608.19652 "https://arxiv.org/abs/2608.19652"))         |
| **Gaia2**                 | 环境独立演化、异步事件、时间约束及动作验证         | “异步”本身也不是创新，需要灾害观测语义与实际来源支持。([arXiv](https://arxiv.org/abs/2602.11964 "https://arxiv.org/abs/2602.11964"))             |

尤其不能把 EarthVerse 描述成普通静态 QA：它已经让系统选择资料、修订解释，并评价整个调查过程。其明确采用固定、可回放的事件档案，这才是可以进行协议差异化的位置。([arXiv](https://arxiv.org/html/2608.23525v1 "https://arxiv.org/html/2608.23525v1"))

## 我建议的新中心问题

> **在灾害证据不完整、更新不同步、获取时间和预算有限的情况下，智能体能否主动找到最有用的下一份证据，区分灾情变化与观测变化，并在正确时间修订正确范围的结论？**

这比此前的“只更新受影响状态”再推进了一步：

**此前：别人把证据交给模型，检查它会不会更新。**

**新版：模型需要知道自己缺什么、去哪补证、是否值得等待，以及什么时候信息足够支撑判断。**

这里的研究价值，不是让 Agent 模拟一个全能灾害指挥官，而是评价一个实际可部署的环节：

### **持续监测中的证据获取与判断修订。**

# 七、一个能把 novelty、数据和实际意义串起来的任务

以洪水为例，以下是**建议的任务设计，不是已经跑出的结果**。

给模型一个区域列表 A、B、C，要求持续维护指定时间窗的水体状态及依据：

- A 已有有效观测。
- B 被云遮挡，仍然未知。
- C 只有过时资料。
- 模型在当前预算下只能查询有限次数。

可用工具不是“返回正确答案”，而是查询某个区域、时段、传感器或站点，返回当时真实可获得的资料，并记录耗时和成本。

### 这时可以检验三个重要问题

**第一，它会不会反复查询已经知道的 A，却一直忽略 B？**

这测的是补证价值，而不是普通召回率。正确策略不必只有一条，但应在预算内尽量消除影响任务的重要未知。

**第二，B 后来被看见了，它会不会将“新看见的水体面积”误写成“洪水刚刚扩张的面积”？**

如果资料对应同一目标时间，主要改变的是认识；如果资料对应更晚观测时刻，就需要新的时间状态。两张不同时刻、不同覆盖率的图，并不总能唯一确定实际变化原因。

**第三，关键资料延迟时，它会不会提前采用未来信息？**

同一个真实事件构造正常和延迟两个分支，各分支按自己当时可见的证据评分。关键证据尚未到达时，两边允许有不同答案；补齐以后，才检查是否正确收敛。

这项任务的实际意义是可量化的：

> **是否更快发现尚未核实的重要区域，是否减少没有依据的确定断言，是否避免因观测覆盖变化误报灾害变化。**

它比直接宣称“提高撤离决策安全”更容易获得可信证据，也比只报告 JSON 正确率更接近真实使用价值。

# 八、进一步增强论文：同时保留“事前合理”与“事后正确”

我认为，这是值得加入的第二个重要升级。

建议数据中独立维护：

```text
EvidenceReference_t：
按照本分支在 t 时刻可见的证据，哪些结论可以成立？

OutcomeReference_T：
在之后取得合格验证资料后，目标实际情况或更可靠估计是什么？
```

**这两种参考不能互相覆盖。**

模型在证据不足时保持未知，可能是事前正确行为；事后发现该区域确实受灾，不应把此前的诚实未知改判成错误。

反过来，模型当时无依据地猜对，也不能因此获得“正确使用证据”的满分。

这使论文能够同时讨论：

**证据纪律、知识边界、事后结果与补证效率。**

### 可以加入预测，但要独立成任务

更激进的版本可以要求模型在未来资料公开前，提交某个固定目标的概率判断，之后用站点或合格观测验证，并与官方预报、持久性等基线比较。

但这应是一个独立的预测分支，不是把当前“读取官方 forecast 数字”的任务换个名字。现有原生契约明确要求读已发布陈述，并不要求模型产生独立气象预报。

我的优先级是：\*\*先把当前状态、主动补证和修订做扎实，再将未来概率预测作为一条有可靠结果标签的扩展。\*\*否则容易在同一篇论文里同时承担过多无法充分验证的主张。

# 九、需要哪些实验，才能证明新方案不是“功能更多”？

我建议主实验围绕四张表展开，而不是继续追加大量格式消融。

| 实验主要比较能支撑什么结论 |                                   |                         |
| ------------- | --------------------------------- | ----------------------- |
| **感知与修订分层**   | 单次读图、正确空间事实的 oracle、原始图文流         | 分清没看懂图与不会维护状态           |
| **局部更新配对**    | 正常到达、关键资料延迟、旧版重放、无关更新             | 模型是否只响应应响应的变化           |
| **预算化主动补证**   | 固定轮询、随机查询、常规 Agent、版本过滤、状态／覆盖感知方法 | 查询策略是否更有效，而不只是多用了工具     |
| **前瞻及跨灾种验证**  | 固定模型／策略后，新事件批次与未用于开发的灾种           | 检验事件记忆、格式适应与通用更新原则之间的差别 |

候选方法可以很简单：维护时空兼容的事实与支持关系，显式记录未知原因；新证据只触发相关依赖重查；剩余预算优先用于重要且可能补足的未知区域。

**这只是候选方法，不能在没有对照前宣称它已经新颖或优于已有状态系统。**

### 指标也应体现实际使用问题

建议至少分别报告：

**必要更新成功率、来源刷新正确率、稳定状态误改率、正确未知保持、任务覆盖率、补证成本，以及充分证据到达后的修订延迟。**

特别注意两点：

\*\*不能让一直回答 unknown 获得最优分。\*\*正确拒答应与覆盖率、主动补证后的任务完成度一起报告。

\*\*不能把全部延迟算在模型头上。\*\*观测周期、生产者发布、平台入库、网络获取和模型处理，是不同层次的延迟。你的数据格式必须先记录这些层次，指标才有解释力。

前瞻采集还可以减少“历史事件可能在训练中见过”的混杂，但只能说降低风险，不能宣称绝对无污染；需要固定模型身份、事前保存提交，并避免用测试事件反复调策略。

# 十、我建议的实际推进顺序

**第一优先级：接通已有两条路径，而不是重新造框架。**
把通用框架已有的图片、增量策略和干预，接到可靠的原始记录及独立评分体系上；先修复交付语义、来源—区域绑定、值保持与依据刷新等问题。

**第二优先级：实现一个真正在线更新的来源适配器。**
完成“发现修订—保存新快照—不覆盖旧版本—断网可回放”。它比接入十个只能一次性下载的数据源更有价值。

**第三优先级：用一个洪水／覆盖事件做完整样例。**
从资料获取，到未知判断、补证、局部修订和评价全部跑通。先检查任务成立，不要求模型一定失败。

**第四优先级：增加预算化查询与前瞻批次。**
此时再扩到气旋、洪水、野火三种互补场景，并运行强基线及跨事件测试。

我的最终判断是：

> **最有机会提高论文 novelty 和实际意义的，不是把现有 benchmark 变得更大，而是将它从“资料已经给齐后的答案追踪”，推进到“资料尚不完整时的主动监测、补证与可追溯修订”。**
>
> **对应的数据格式也必须从“静态题目＋文档列表”，升级为“来源修订＋可见性记录＋有序交付＋知识状态＋事后验证”。**

这是一条更激进、但仍可以利用现有代码逐步完成的路线。它是否最终构成足够独立的论文贡献，要由任务有效性、强基线比较和前瞻结果证明，不能靠增加“online”“multimodal”两个标签保证。

# 一、先看清竞争格局：哪些方向已经不能单独支撑强 novelty？

重新核对近期工作后，我认为不能再笼统地说“现有 benchmark 都是静态 QA、没有真实数据、没有行动”。

| 方向已有工作已经做到了什么对你的启示 |                                                                                                         |                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **真实天气预测评价**       | Extreme Weather Bench 已提供高影响天气案例、观测和 impact-based metrics；RealBench 已引入低延迟业务分析与大规模站点实测，研究重分析分数与真实表现的差异。 | “真实数据、极端天气、影响指标”不是单独的新贡献。([arXiv](https://arxiv.org/abs/2605.01126 "https://arxiv.org/abs/2605.01126"))           |
| **专业气象语言生成**       | AFDBench 从结构化 WeatherNext 2 数据生成专业 AFD，任务重点是输入忠实度与专业表达。                                                 | 不要再平行增加完整气象报告生成，去竞争一个不同的问题。                                                                                       |
| **业务与工具型灾害 Agent** | SIREN 已经组织完整预警链；DORA 涵盖感知、空间关系、救援规划和时间演化；GeoDisaster 还提供可执行地理流程与确定性一致性检查。                               | 多 Agent、多工具、可执行 Gold、业务流程，本身都不够新。([arXiv](https://arxiv.org/abs/2607.24588 "https://arxiv.org/abs/2607.24588"))   |
| **多来源科学调查**        | EarthVerse 已让 Agent 自主选择兼容证据、计算、协调来源差异并保留 provenance。它不是简单“给图答题”。                                       | “证据选择＋时空对齐＋可追溯计算”已经有非常强的近邻。([arXiv](https://arxiv.org/html/2608.23525v1 "https://arxiv.org/html/2608.23525v1"))   |
| **实时观测与灾害生命周期**    | Obshazard-bench 已强调原始高频观测，以及灾前预判、灾中演化、灾后影响。                                                             | “在线、多模态、全生命周期”不能直接等于 novelty。([arXiv](https://arxiv.org/html/2608.00012v1 "https://arxiv.org/html/2608.00012v1")) |

此外，**主动获取信息也不是全新概念**。AFABench 已系统评价有成本的序贯特征获取；LEAP 已研究逐条证据的概率贡献与聚合；近期还有面向地球观测的云条件可观测性预测，以及资源受限的星上灾害 Agent。([arXiv](https://arxiv.org/abs/2508.14734 "https://arxiv.org/abs/2508.14734"))

因此，我不会建议你简单改名为：

> “首个主动感知的多模态极端天气 Agent benchmark。”

**真正需要提出的是一个更具体、能产生新结论的测量对象。**

# 二、我认为最值得切入的痛点：目前难以分清“模型不行”与“信息根本不够”

## 1. 痛点不是只有模型答错，而是答错的性质混在一起

同样一次错误预警，可能来自完全不同的原因：

| 情况实际问题改进系统的方法不同       |        |              |
| --------------------- | ------ | ------------ |
| 当时没有足够观测，却要求模型给确定结论   | 信息不足   | 补观测、明确不确定性   |
| 已有充分证据，但模型读错了时间、空间或版本 | 证据理解失败 | 改进解析、关联与版本管理 |
| 模型知道证据不足，却不断读取无关材料    | 取证策略失败 | 改进下一步查询选择    |
| 判断最终正确，但形成得太晚         | 决策时效失败 | 优化等待、查询与停止策略 |
| 所有资料都查一遍才成功           | 资源效率差  | 寻找最小且足够的证据路径 |

当前你的 benchmark 主要覆盖第二类。上一轮提出的“区分灾情变化与证据变化”，能够加强第一、第二类，但还没有解决：

> **模型识别出缺口以后，应该怎么办？它能否用有限资源填补这个缺口？这样做是否真的改善了预警？**

这就是更激进升级应该补上的部分。

## 2. 这个痛点有明确的业务依据

SIREN 在论文局限中直接指出，回顾性评测与实际部署之间仍存在距离，真实环境中的**数据延迟、缺失、不断演化的预报和业务约束**可能影响表现。([arXiv](https://arxiv.org/html/2607.24588v1 "https://arxiv.org/html/2607.24588v1"))

WMO 的相关计划也强调：预警不仅要预测天气，还应服务风险决策；同时，带宽和基础设施限制是实际服务设计必须考虑的问题。([World Meteorological Organization](https://public.wmo.int/activities/severe-weather-forecasting-programme-swfp/severe-weather-forecasting-programme-swfp "https://public.wmo.int/activities/severe-weather-forecasting-programme-swfp/severe-weather-forecasting-programme-swfp"))

因此，研究重点可以从：

> 怎样让 LLM 在灾害题目上多得几分？

转为：

> **当预报产品已经存在时，LLM 这一层究竟能为受限环境下的风险识别增加什么价值？**

这是我认为最能增强论文实际意义的问题。

# 三、推荐的新核心：评测“证据充分性—主动取证—预警收益”的闭环

我建议保留 **DisasterTrace** 这个名字，不再不断更换项目名称。

新的研究定位可以是：

> **DisasterTrace：面向观测受限极端天气的主动取证与预警价值评测。**

它包含三个不可拆开的环节，但只有一个核心目标：

```text
当前证据是否足够？
        ↓
不足时，下一步查什么最值得？
        ↓
得到新证据后，能否更及时、更可靠地预警？
```

## 1. 第一环：知道当前能断言什么

模型不仅输出一个数值，还要判断：

```text
已有充分支持
仍然存在信息缺口
两份资料不可直接比较
当前结论只适用于部分区域或时间窗口
```

这延续你已有的版本、作用域、缺失和引用研究。

## 2. 第二环：主动弥补具体信息缺口

模型不再被动接收所有材料，而可以选择：

```text
读取另一个区域的影像
获取最新一期预报
查看观测质量或覆盖掩膜
查询目标站点的最新实测
查询上游站点
等待下一份已登记产品
停止取证并提交判断
```

每个选择都有明确的信息范围、可用时间、处理延迟和资源成本。

## 3. 第三环：用结果衡量这些选择是否有价值

最终不只看：

> 结论有没有引用？

而要看：

> 是否漏报？是否虚警？提前了多久？用了多少数据和计算？相对于不使用 Agent 的固定流程，收益是否存在？

**注意：这里的闭环是“取证—判断—后续结果验证”，不是让模型控制真实灾害，也不是自动发布现实预警。**

# 四、先用一个具体例子理解：新任务与旧任务到底差在哪里？

以下数值是**用于说明任务逻辑的受控示例，不是实际洪灾数据或官方处置规则**。

## 场景：判断一个区域是否达到某个面积阈值

目标区域为 100 km²。当前已经取得的同一时刻地图，只覆盖其中 70 km²，其中有 12 km² 被参考标签标记为水域；另外 30 km² 尚未取得。

研究任务问：

> 当前水域面积是否已经达到 20 km²？

### 旧式任务容易怎样评价？

给模型一个最终完整图，要求它判断面积或输出 yes/no。

### 新任务首先检查什么？

当前证据只能支持：

```math
A_{\text{water}}\in[12,\;42]\;\text{km}^2
```

下界是假设未知区域全部不是水；上界是假设未知区域全部是水。

因此，模型不能声称：

```text
“只有 12 km²，所以没有达到阈值。”
```

合理的事实判断是：

```text
“目前可确认至少 12 km²，尚不能确定全区域是否达到 20 km²。”
```

这里的区间是**限定标签与观测模型下的可确定范围**，不是现实洪水面积的统计置信区间，也没有假设遥感分割绝对无误。

## 然后，模型必须选择下一步

假设剩余预算为 5 个研究成本单位，判断截止时间还有 60 分钟：

| 可选操作成本延迟可能获得的信息        |   |       |                  |
| ---------------------- | - | ----- | ---------------- |
| 再读一份复述当前结果的公告          | 1 | 2 分钟  | 可能没有新增空间支持       |
| 获取尚未读取区域中的 20 km² 地图瓦片 | 4 | 15 分钟 | 缩小目标面积的不确定范围     |
| 等待完整汇总产品               | 8 | 90 分钟 | 信息完整，但超预算且超过截止时间 |

模型不能提前知道第二项里面有多少水域，它只能根据目标、覆盖和已有信息判断这次查询是否值得。

假设获取后，新瓦片中有 10 km² 水域，那么：

```math
A_{\text{water}}\in[22,\;32]\;\text{km}^2
```

此时已经足够确认达到 20 km²，**不需要为了完整重建所有像素而继续获取剩余区域**。

这个例子同时测试四件事：

**能否识别信息不足；能否选择有价值的证据；能否在信息足够时停止；能否避免把“读到了更多区域”描述成“洪水新增了 10 km²”。**

## 一个必须保留的业务边界

**“不能确定面积是否超阈值”不等于“不能采取任何预防行动”。**

在漏报代价很高的场景，模型可能合理地建议先准备，同时继续取证。因此，应分别评价：

```text
事实断言是否有充分支持
≠
在不确定性下采取预防行动是否合理
```

不能制定一条“只有完全确定以后才允许预警”的规则，否则 benchmark 反而会奖励危险的迟疑。

## 这还不是未来天气预测

上面的例子属于**当前态势识别**。

若论文要强调真正的提前预警，还必须增加一个独立目标，例如：

> 未来六小时，指定水文站的水位是否超过预先固定的阈值？

该问题要求现在提交概率和预警时间，再由之后的质量合格观测检验。**不能把“读取同一时刻的完整地图”冒充未来预测。**

# 五、真正有辨识度的技术贡献：为“信息不足”建立可计算的参考，而不只是让模型输出 unknown

这是我认为比继续增加 JSON 字段更值得深入的一步。

## 1. 建立“当前证据能支持的结论集合”

对于一类受限任务，我们可以根据公开证据计算：

```math
\mathcal{Y}(E_t) = \{\text{在当前证据与公开规则下仍可能成立的答案}\}
```

例如上面的面积问题，当前范围横跨阈值，不能给出确定二分类；新证据到达后，所有可接受答案都在阈值以上，就可以确认。

不同任务可以使用不同的确定性规则：

| 任务可以自动判断的证据充分性 |                         |
| -------------- | ----------------------- |
| NHC 同有效时刻的预报修订 | 是否存在当前可用且明确覆盖该时刻的产品     |
| 部分影像上的面积阈值     | 已知面积下界与未知区域上界是否跨越阈值     |
| 持续时间阈值         | 观测间隙是否足以改变“连续超过阈值”的判断   |
| 两期灾害范围比较       | 共同有效区域、测量定义与时间是否允许比较    |
| 多来源数值判断        | 单位、位置、统计窗口与产品类型是否对应同一个量 |

\*\*集合界限和主动信息获取都不是我们发明的新数学。\*\*贡献在于：把它们落实成极端天气 Agent 可以接受严格测试的“信息充分性参考”，并据此分开评价信息瓶颈和模型瓶颈。

## 2. 这样能够区分以前混在一起的失败

建议将每次错误归入四种有明确证据的情况：

```text
A：给定证据本来不足，模型却确定断言。
B：证据已经充分，模型仍然回答错误。
C：存在可负担、及时的信息补充，模型没有选到。
D：取证与判断都完成了，但超过有效决策时间。
```

这比一个总准确率更能指导后续研究：

- A 需要改进不确定性与支持判断；
- B 需要改进感知、时空对齐或推理；
- C 需要改进取证策略；
- D 需要改进停止与时间规划。

## 3. 不要声称能够自动判断所有真实问题的“可回答性”

对于自然灾害，完整的物理状态通常不可直接获得，也不能枚举所有可能未来。

因此，第一版只对**可以精确定义观测语义的子任务**提供充分性参考。对未来风险预测，不提供伪造的“正确概率”，而是评价多个事件上的概率质量和后续结果。

例如，模型预测概率为 0.8，而某次事件没有发生，不能据此直接断定这次概率错误；概率预测需要跨样本评价，而不是用一次结果反推唯一正确概率。

**这条边界是新方案科学可信的关键。**

# 六、怎样把“更多证据”变成“更有用的证据”？

## 1. 让信息获取改变可见证据，而不是给模型加一个浏览器按钮

每个查询都应定义为：

```text
查询对象与变量
目标时空范围
来源／产品版本
预计信息类型
可用时间
资源成本
处理延迟
```

模型必须在这些条件下选择下一步。

例如，一张分辨率更高但已经过期的图，并不必然比当前低分辨率观测更有价值；重新下载同一预测的另一种格式，也不能自动算成一条独立证据。

## 2. 灾害场景相对于普通主动特征获取的特殊性

AFABench 已提供静态、贪心和非贪心主动获取方法，所以“查什么、什么时候停止”不能作为全新的算法思想。([GitHub](https://github.com/Linusaronsson/AFA-Benchmark "https://github.com/Linusaronsson/AFA-Benchmark"))

你真正应利用的是灾害信息的这些结构：

\*\*信息会过时。\*\*查询花费的时间可能使已有预测失效。

\*\*信息会被修订。\*\*后来发布的估计不一定代表物理过程变化。

**信息具有空间支持。**“我看到了这个区域”不等于“我看到了整个灾区”。

\*\*信息可能相关或重复。\*\*同一模型、同一观测经不同网页或文本转述，不能按多份独立支持叠加置信度。

\*\*信息是否值得获取，取决于当前决策。\*\*能降低整体预测误差的数据，不一定能改变眼下的预警选择。

这些结构应直接影响查询结果与评分，而不是只写进说明文档。

## 3. 最值得尝试的方法：面向决策的证据缺口规划

可以构建一个轻量方法，而不训练新的天气基础模型：

```text
识别当前结论的未解决部分
→ 判断哪些来源能够改变这一部分
→ 排除过时、重复或不兼容来源
→ 比较预期决策收益、成本和延迟
→ 选择查询，或停止
```

这里的关键不是“最大程度减少所有不确定性”，而是：

> **优先减少会改变当前风险决策的不确定性。**

例如，要判断目标区域是否超过面积阈值，继续分析一个已经确认无关的区域，即使能提高整张图的完整度，也未必具有决策价值。

可以先用规则、有限前瞻搜索和固定预测器实现，再比较是否需要 LLM 规划。LEAP 的证据概率聚合可以作为一个基线，但它已经有公开方法和代码，不应改个名称就算成你的新方法。([GitHub](https://github.com/layingfish/LEAP "https://github.com/layingfish/LEAP"))

\*\*如果最终只是标准信息价值公式加上一个 prompt，就不宜声称算法创新。\*\*只有在版本相关性、空间支持或延迟处理上提出明确机制，并通过消融证明它必要，方法贡献才成立。

# 七、最终评分应从“引用正确率”转向三条主轴

我不建议再把二十多个分数加权成一个不透明总分。

## 主轴一：是否知道当前证据能够支持什么？

核心检查：

> 在证据不足时不过度断言，在证据充分时不继续逃避，在证据不可比较时不制造变化结论。

可以报告“可回答／不可回答匹配对同时通过率”，同时保留数值、版本、引用和视觉支持诊断。

这样既不能靠“永远回答 unknown”获高分，也不能靠“总给一个确定答案”获高分。

## 主轴二：预警到底提前了多久，付出了多少虚警与漏报？

对于有独立后续观测的预测轨，报告：

- 事件检出与漏报；
- 无事件窗口上的虚警；
- 有效预警提前量；
- 概率预测质量。

\*\*提前量必须与虚警和检出率一起报告。\*\*一个系统如果对所有时间都报警，当然可能“提前很久”，但并不有用。

更严格的比较方式是：

> **在预先固定的虚警约束、可比检出水平和信息预算下，谁能获得更长的有效提前量？**

不能只计算成功预警案例的平均提前量，把漏报事件从结果中消失。

此外，必须加入无灾害窗口，不能只从灾害目录中取正例，否则无法可信地评价虚警。

## 主轴三：相对于强固定流程，Agent 是否增加了价值？

建议使用一个公开、可计算的研究损失：

```math
J(\pi) = \frac{1}{N}\sum_{i=1}^{N} \left[ L_{\rho}(a_{i,0:T},y_i) + \lambda\sum_{q\in Q_i}c(q) \right]
```

其中：

- `L_{\rho}` 是预先定义的虚警、漏报和延迟损失；
- `c(q)` 是信息获取与处理成本；
- `\rho,\lambda` 在开发阶段固定，并做敏感性分析。

成本—损失和提前量的联系已有气象决策研究，不能把这个公式本身写成原创贡献。([DOI](https://doi.org/10.3389/fcomm.2026.1762033.s001 "https://doi.org/10.3389/fcomm.2026.1762033.s001"))

真正需要报告的是：

```math
\Delta J=J(\text{强固定流程})-J(\text{Agent})
```

它回答：

> **加入 Agent 后，是否比已有预测器加固定规则更有用？**

这里的损失是明确假设下的研究代理指标，**不是已经证明减少了真实经济损失、人员伤亡或撤离成本**。

# 八、怎样与最接近的论文拉开真正的差距？

## 1. 对 EarthVerse：从“调查完成得好不好”到“证据是否来得及产生价值”

EarthVerse 已经允许主动选择证据，也评价科学计算与来源关系。但它主要组织事后事件包调查，论文说明延迟、token 和证据访问等轨迹统计不进入主评分。([arXiv](https://arxiv.org/html/2608.23525v1 "https://arxiv.org/html/2608.23525v1"))

你的差异应当是：

> 查询哪份资料、等待多久、何时停止，会直接改变预警收益，而不是仅作为成本附表。

因此，即使两个系统最终给出同样正确的结论，也可能获得不同评价。

## 2. 对 SIREN：把其披露的部署距离变成可重复实验变量

不是再做一条预警工作流，而是将以下条件明确纳入环境：

```text
资料延迟
观测缺失
预测版本变化
截止时间
资源约束
```

然后在同一事件上比较不同信息条件，测量工作流在这些变化下是否仍然有收益。

## 3. 对 Obshazard-bench：从“给定观测流上的问答”到“决定下一步观测”

不是只输入更多原始通道，而是要求模型选择：

> 哪个区域、哪个变量、哪个时刻、哪个产品最能弥补当前决策缺口？

其结果应由实际得到的信息与后续预警表现检验，而不按是否选中作者预设的唯一工具顺序判分。

## 4. 对 AFABench 和可观测性研究：不是泛化的缺失特征分类

你需要证明：**版本更新、时空支持和信息时效，与风险决策之间的相互作用，产生了普通静态获取任务看不到的失败。**

例如：

```text
获得更多证据，结论反而更不可靠
```

原因不是一般输入噪声，而是把旧版本当成新增独立支持，或者把不同时间窗口拼成同一时刻的灾情。

但也必须承认，观测可用性预测已存在专门研究，不能把“知道影像能不能用”单独作为首次贡献。([arXiv](https://arxiv.org/abs/2607.13651?utm_source=chatgpt.com "From Surface Forecasting to Observability Forecasting: A Latent World Model for Cloud-Aware EO Monitoring"))

**最稳妥的 novelty 不是“每个模块都是新的”，而是提出一个此前没有被这些评测充分分离的目标：模型能否把有限、会过时和修订的证据，转化为可验证的及时决策增益。**

这仍然需要最终实验支撑，不能只靠设计描述宣布成立。

# 九、数据上怎样做，才能不把项目扩大到无法完成？

## 我的建议：一个旗舰场景，两条互补验证轨

不要一开始建设八灾种综合平台。

### 旗舰场景：洪水

洪水可以同时承载两种互补任务，但二者要分开：

| 子任务检验对象自动参考 |                       |                      |
| ----------- | --------------------- | -------------------- |
| 当前水域／淹没范围识别 | 覆盖是否充分、两期是否可比、该查询哪个区域 | 已有参考掩膜、质量标签、固定空间计算   |
| 未来站点水位阈值预警  | 该查询什么观测或预报、能否及时形成风险判断 | 后续质量合格站点观测、固定阈值与时间窗口 |

WorldFloods v2 的参考数据将 clear/cloudy 与 land/water 分为两个通道，适合构建覆盖感知测试；可以复用已有标签，不需要新增逐题标注。其数据与预训练模型有非商业许可条件，应按来源要求使用。([GitHub](https://github.com/spaceml-org/ml4floods/blob/main/jupyterbook/content/worldfloods_dataset.md "https://github.com/spaceml-org/ml4floods/blob/main/jupyterbook/content/worldfloods_dataset.md"))

USGS 提供水文观测 API；NOAA NWPS 提供业务河流预报、观测、洪水等级等数据。这里有一个实际限制：**NWPS 主 API 不是完整历史预报档案，实验性 HEFS API 的当前服务范围也有限，不能假定可以一次下载多年所有历史发布版本。**([Water Data APIs](https://api.waterdata.usgs.gov/ "https://api.waterdata.usgs.gov/"))

历史预报应另外核查业务档案。WRF-Hydro 官方文档分别列出 NWM operational archive 与 retrospective 数据，二者不能混用成同一种业务证据。([WRF-Hydro Documentation](https://wrf-hydro.readthedocs.io/en/latest/appendices.html?utm_source=chatgpt.com "APPENDICES — WRF-Hydro Modeling System 5.4.0 documentation"))

### 第一验证轨：保留现有 NHC

你的现有自然预报版本任务非常适合继续作为：

> 版本理解、有效时间、单位与来源绑定的基础对照。

不需要重新实现，更不应为了新故事改写旧成绩。

### 第二验证轨：野火或热浪，择一

野火更适合检验观测缺失、active fire 与 burned area 的区别；TS-SatFire 已提供时序检测、监测与预测数据和代码，可以作为复用起点。([GitHub](https://github.com/zhaoyutim/TS-SatFire "https://github.com/zhaoyutim/TS-SatFire"))

热浪更适合较明确的站点阈值和持续时间预测，工程上可以考虑 GFS 加站点观测。GEE 的 GFS 集合已区分创建时间、预测时间和预测时效，适合构建同目标时间的跨周期证据。([Google for Developers](https://developers.google.com/earth-engine/datasets/catalog/NOAA_GFS0P25 "GFS: Global Forecast System 384-Hour Predicted Atmosphere Data  |  Earth Engine Data Catalog  |  Google for Developers"))

**选择由旗舰实验暴露的问题决定，不以灾种数量最大化为目标。**

## 不要忽略跨数据集对齐成本

WorldFloods 的影像事件，不保证恰好有合适的站点、业务预报和时间重叠。不能把“两个数据集都存在”当成“完整样本已可自动拼接”。

应先做事件级覆盖清单，确认：

```text
目标位置
观测时间
预报发行时间
预报有效时间
产品类型
质量标记
参考结果
```

无法可靠对应的样本，要隔离而不是插值编造成完整事件链。

# 十、Online 和 AutoResearch 怎样加入，才不是装饰？

## 1. Online 的作用：获得真实的信息到达过程

建议采用：

```text
持续采集
→ 保存每版内容与实际取得时间
→ 定期封存事件快照
→ 所有模型在同一快照上重放
```

GEE 用于发现和处理新数据，但不是天然的历史版本保险箱。例如 IMERG 集合存在 provisional 被后续更新产品替换的机制，仅保存集合 ID 和日期不足以重现当时的证据。([Google for Developers](https://developers.google.com/earth-engine/datasets/catalog/NASA_GPM_L3_IMERG_V07 "https://developers.google.com/earth-engine/datasets/catalog/NASA_GPM_L3_IMERG_V07"))

因此，在线采集最重要的研究价值不是“用了最新数据”，而是：

> **能真实观察证据何时可用、何时修订、什么时候才足以改变判断。**

历史资料无法确认首次公开时间时，使用受控到达计划；前瞻采集记录的是你系统的 first-seen，不夸大为全球首次可见时间。

## 2. AutoResearch 的作用：优化或检验取证策略，而不是自动修改考卷

可以保留一个受约束循环：

```text
发现失败类型
→ 提出取证策略假设
→ 修改一个查询／停止组件
→ 在开发事件验证
→ 在未见事件与不同信息条件下测试
```

但数据、目标、成本、时间、参考答案与测试事件必须冻结。

这里要区分：

- **被测 Agent**：为具体灾害任务选择证据；
- **研究 Agent**：在开发集上研究哪类取证策略更好。

二者不能混成“每遇到一道测试题，自动改 benchmark 和方法直到成功”。

AutoResearch 不需要成为第一篇论文的主贡献；它可以作为证明该环境能推动方法改进的案例。

# 十一、如何从你当前代码出发，而不是再重建一个庞大系统？

我建议只新增三个研究组件。

| 组件作用现有内容如何复用   |                             |                          |
| -------------- | --------------------------- | ------------------------ |
| **观测支持与可比性检查** | 计算当前哪些结论有支持、哪些仍不确定          | 扩展已有 scope、版本、引用与公开输入隔离  |
| **有界取证环境**     | 模型选择来源／区域，环境返回当时可用证据并计成本与延迟 | 复用冻结任务、真实调用记录与轨迹审计       |
| **结果与预警评价**    | 根据独立后续观测、阈值和成本协议评价          | 保留原 scorer 为基础诊断，新增独立评分轨 |

当前 `forecast_task` 为三种方法都提供累计可见文本。要研究主动取证，必须新增独立信息访问协议，不能只换 prompt 就宣称实现了主动观察。

## 最小开发路线

**第一阶段：不调用模型，先证明任务本身成立。**

选择少量已有标签场景，构造可回答／不可回答、覆盖增加／物理变化、同值修订／重复交付的配对；写两个独立参考实现，确认错误程序会在对应任务失败。

**第二阶段：让模型在有限查询空间中运行。**

每个案例只提供约 6–8 类候选操作，先比较固定流程、随机查询、贪心信息获取与模型规划。不需要一开始接几十种工具。

**第三阶段：完成至少一条有独立结果的未来预警轨。**

必须有预测提交时刻、未来目标窗口、后续参考观测与无事件对照。否则论文应称主动灾情识别，而不是提前预警。

**第四阶段：再做跨事件、跨观测条件和第二灾种。**

先按真实事件划分训练／开发／测试，再派生切片、版本和缺失条件。重复采样与新增切片不能冒充新增独立灾害。

这几个阶段首先要产出的是**能够改变研究判断的实验结果**，而不是继续扩充 manifest、测试数量和汇报页面。

# 十二、必须加入哪些强基线，才能证明 LLM 真的有用？

这是新方案成败的关键。

| 基线为什么必须有     |                       |
| ------------ | --------------------- |
| 最新有效预报＋固定阈值  | 检验是否只需要简单业务规则         |
| 正确版本解析＋结构化计算 | 排除“LLM 只是执行确定性查表”的解释  |
| 固定取证顺序       | 检查主动选择是否优于合理默认流程      |
| 随机／最便宜优先查询   | 排除资源分配上的弱基线优势         |
| 贪心信息价值获取     | 与已有主动获取思想比较           |
| 全部证据输入       | 定位信息限制，但若超预算，只能作为上界参考 |
| 模型主动规划       | 真正的被测方法               |
| 正确测量值替代视觉输入  | 诊断瓶颈来自视觉，还是时空与取证推理    |

AFABench 已开源多类主动获取实现，可以借鉴其方法与评估组织，不必全部重建。([GitHub](https://github.com/Linusaronsson/AFA-Benchmark "https://github.com/Linusaronsson/AFA-Benchmark"))

尤其建议设一个**获取策略隔离实验**：

> 各方法共享同一个天气／水文预测器和同一个告警转换规则，只改变获取哪些证据。

然后再设置端到端实验，允许不同方法改进融合与决策。

这样才能知道收益到底来自：

```text
更强的物理预测器
还是更好的证据获取
还是更好的证据理解
还是不同的决策规则
```

**如果 Agent 不能优于“最新有效预报＋固定规则”，就不能因为其推理过程很复杂而声称实际价值更高。**

# 十三、什么结果才足以支持更强的论文主张？

我建议把最终论文围绕三个可证伪问题组织。

## RQ1：静态理解能力能否预测实际预警价值？

检验：

> 在完整资料上得分高的模型，是否也能在缺失、延迟和版本变化下获得较好预警收益？

可能出现的有价值结果是：完整输入正确率高，但主动取证与及时停止差，最终业务代理收益反而低。

这必须由实验观察，而不是提前假定。

## RQ2：模型能否区分信息不足与自身推理失败？

检验：

> 模型是否在不可确定时过度断言，在已有充分证据时仍然请求无关资料，或者只因图像覆盖变化就声称灾害扩张？

如果你的充分性参考确实能稳定区分这些情况，benchmark 就提供了普通最终准确率没有的信息。

## RQ3：主动取证能否在未见事件与不同观测条件下真正节约成本、改善时效？

检验：

> 在相同虚警约束和可比检出率下，是否减少查询、缩短无效等待，并获得更长有效提前量？

若优势只存在于人工安排的“正确工具永远是 SAR”模板，或只在单一成本设定下存在，就应收缩主张。

# 最终建议：把论文主张收敛为三个贡献

## 贡献一：新的评测对象

**面向决策的证据充分性。**

不仅问答案是否正确，还问：在当时的时空覆盖、版本与质量条件下，这个结论是否已经有充分支持。

## 贡献二：新的实验协议

**信息会演化、获取有代价、判断有时限的主动取证回放。**

对同一灾害控制观测条件，分别观察信息缺口、模型理解、查询选择与停止行为，而不是混成一项总失败。

## 贡献三：更接近实际意义的验证

**在固定预报底座与风险约束下，测量 Agent 的增量预警价值。**

把数值、来源与状态正确性连接到可计算的虚警、漏报、提前量和信息成本，但不将研究代理损失夸大为真实减灾效果。

---

## 一句话介绍这个更激进的版本

> **DisasterTrace 在有时限、有成本且持续修订的灾害信息流中，区分“证据还不够”和“模型没有用好证据”，并检验主动取证能否在控制虚警的同时带来可验证的预警提前量。**

更适合口头汇报的说法是：

> **我们不只考模型看到资料后能否答对，而是考它是否知道还缺什么、该去查什么，以及查完以后能不能更早、更可靠地预警。**

\*\*这条路线比“多灾种＋多模态＋online＋memory”更值得投入，因为每一个组件都服务于同一个可检验的问题：AI 在现有预报系统之上，究竟有没有增加及时、可靠且资源可承受的决策价值。\*\*它不会天然保证高 novelty，但比继续扩大数据规模或增加模块，更有机会形成一个有清楚科学问题、强对照实验和实际用途的研究贡献。**我建议更激进地调整论文的“主问题”，而不是继续增加任务数量：把“多模态状态修订”从最终卖点，变成支撑机制；把“信息不完整时，系统能否在准备窗口关闭前形成有用的预警”提升为主研究对象。**

你现有材料已经把证据时间、版本、局部修订和状态保留定义得比较清楚，但当前实测仍主要回答“资料是否被读对、更新对”，还没有直接回答“这些能力究竟带来了多少有用的提前预警”。这一边界在原方案中也有明确说明。

我会将升级后的中心问题写成：

> **面对异步、多模态且不完整的灾害信息，系统能否主动选择值得获取的证据，在等待新信息与保留准备时间之间作出合理取舍，并通过后续真实观测验证其预警的准确性、及时性和成本？**

**这比“动态多模态问答＋预测”又前进了一步：不再只评测给定信息后的答案，而是评测系统如何把有限的信息机会转化为有效预警。**

下面是我建议的整体重构。文献判断基于截至 **2026 年 9 月 9 日**的本次检索；具体任务、实验和方法是新的研究建议，不是已有实现或结果。

# 一、首先修正对“当前 benchmark 痛点”的描述

不能再把已有工作概括成“都是静态问答”“只看均方误差”“没有工具和动态过程”。最新研究已经覆盖不少这些内容。

| 已有研究已经做到的事情DisasterTrace 应进一步回答的问题      |                                                     |                                                                                                                                        |
| --------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Extreme Weather Bench**               | 按高影响天气事件组织验证，关注提前量、空间影响和边缘事件，也讨论只选灾害事件导致的评测偏差       | **系统应该获取哪份证据、是否值得等待，以及获取后是否还来得及利用？** ([arXiv](https://arxiv.org/html/2605.01126v1 "https://arxiv.org/html/2605.01126v1"))              |
| **RealBench，2026 年 5 月**                | 在更接近业务的低延迟初始资料和站点观测下评价天气预报，加入极端事件挑战                 | 除预报模型本身外，**整个信息获取与预警策略**是否在真实时间约束下可靠？ ([arXiv](https://arxiv.org/abs/2605.24945 "https://arxiv.org/abs/2605.24945"))                   |
| **EarthVerse，2026 年 8 月**               | 多源灾害调查、工具选择、记忆、证据一致性和停止行为；论文明确将任务置于固定事件资料包中，未覆盖实时预测 | **结果尚未发生时，系统如何逐时刻提交不可事后修改的预测和预警？** ([arXiv](https://arxiv.org/html/2608.23525v1 "https://arxiv.org/html/2608.23525v1"))                |
| **SIREN，2026 年 7 月**                    | 已有灾害刻画、预测、影响评估、响应决策，以及主动工具调用                        | **新增证据究竟改善了多少预警价值，还是只增加了耗时与输出？** ([arXiv](https://arxiv.org/html/2607.24588v1 "https://arxiv.org/html/2607.24588v1"))                  |
| **LEAP／Bayesian Linguistic Forecaster** | 已研究证据贡献、概率更新，以及检索过程中维护预测信念                          | \*\*外部资料发布时间与行动截止时间，如何改变证据的实际价值？\*\*而不只是一次预测推理内部如何更新概率。 ([arXiv](https://arxiv.org/abs/2609.01337 "https://arxiv.org/abs/2609.01337")) |

同时，**“主动获取信息”和“现在行动还是等待下一版预报”本身也不是新的理论问题**。Interactive Benchmarks 已研究预算约束下的信息获取；2021 年的气象决策研究已经用真实预报和观测分析“立即决定还是等待”。所以，不能把这些概念换个灾害名称就称为首次提出。([arXiv](https://arxiv.org/abs/2603.04737 "https://arxiv.org/abs/2603.04737"))

真正值得切入的是它们之间仍需要更清楚测量的接口：

> **预报能力 → 获取和理解证据 → 及时形成判断 → 在尚有准备时间时作出决定。**

WMO 的预警体系也明确区分风险知识、观测与预测、预警传播，以及准备与响应，说明“预报准确”只是完整预警体系中的一部分。你的论文可以研究其中的信息—预测—时机接口，但不应声称一个 benchmark 解决了整个社会预警体系。([World Meteorological Organization](https://public.wmo.int/activities/early-warnings-all/wmo-and-early-warnings-all-initiative "https://public.wmo.int/activities/early-warnings-all/wmo-and-early-warnings-all-initiative"))

# 二、我最推荐的升级：从“回答一道题”改成“完成一次限时预警任务”

## 2.1 改变 benchmark 的基本单位

此前的基本单位接近：

> 给定截至当前的证据，回答一个问题。

加入预测后变成：

> 给定截至当前的证据，预测一个未来结果。

我建议进一步升级为：

> **给定监测目标、信息获取权限、预算和准备时限，系统自主获取证据、维护预测，并在截止前提交研究规则下的预警决定。**

一条任务包含五个要素：

| 要素具体含义      |                                              |
| ----------- | -------------------------------------------- |
| **固定未来目标**  | 例如某站点在绝对时刻 `T` 是否超过水位阈值，不能每轮偷偷换成新的“未来 24 小时” |
| **外部信息时间轴** | 观测何时产生、产品何时发布、何时可取得，均独立于模型推理轮次               |
| **有限的信息访问** | 系统可查询站点、查看地图、读取公告、调用已有专业预报工具，但有明确权限和成本       |
| **准备截止时间**  | 某类研究决策必须在 `D<T` 前作出，晚到的正确判断不能补回已经失去的准备时间     |
| **后续结果验证**  | 用质量可检查的实际观测评价预测，用预先公开的损失函数评价研究决策             |

这时，模型不只是回答“风险是多少”，还需要回答：

**下一份值得读取的资料是什么？是否需要重新检查旧图？下一版预报是否值得等？继续获取资料是否已经没有时间价值？**

## 2.2 “闭环”要限定在信息与决策层，不必搭建灾害世界模拟器

我不建议首版就模拟撤离群众、改变水库调度、预测道路阻断后的交通流。

这些行为会改变现实后果，若没有经过验证的环境模型，所谓“反事实收益”很容易由你编写的模拟规则决定，而不是由真实资料支持。

更稳妥的闭环是：

**选择信息 → 获得资料 → 修改预测 → 再选择信息或停止 → 提交预警。**

不同策略可以看到不同的证据，但其预测的物理结果相同。这样能够做可重复的策略比较，而不需要声称模拟了灾害本身。

# 三、用一个例子说明：为什么这比“多次预测”更有实际意义？

**下面是教学设定，不是已采集数据或实验结果。**

任务目标：

> **某水文站在今天 15:00 是否超过规定水位阈值？**

研究规则规定：某项准备措施需要两小时，因此最迟应在 **13:00** 提交决定。

| 时间与信息系统可以做什么需要权衡什么     |                  |                          |
| ---------------------- | ---------------- | ------------------------ |
| 09:00：已有官方集合预报和历史水位    | 先提交预测，决定下一步读取什么  | 当前风险是否足以作出决定？            |
| 之后：可读取上游站点、降雨空间资料和流域关系 | 选择有可能改变目标风险的证据   | 哪个来源更有价值，而不仅是更新或更详细？     |
| 11:00：新的上游信息可用         | 修订概率，重新判断是否行动    | 新信息可能提高风险，也可能避免一次错误预警    |
| 13:00：准备窗口关闭           | 提交决定，或承担未行动的研究损失 | 不能无限等待确定性                |
| 14:00：更完整的新预报发布        | 继续进行预测评测         | 即使更准确，也不能追溯性改变 13:00 的决定 |
| 15:00 之后               | 获取实际结果           | 分别验证预测轨迹和截止前决定           |

这里可能出现三种系统：

\*\*系统 A：\*\*最后预测最准，但一直等待，错过准备窗口。

\*\*系统 B：\*\*适时取得关键证据，在截止前形成较可靠的判断。

\*\*系统 C：\*\*始终报高风险，很早预警，但产生大量误报。

单看最后一次准确率，不能完整区分三者；单看提前量，又可能错误奖励系统 C。

**你的 benchmark 应评价三者在相同信息权限、误报约束和准备时限下的长期表现，而不是预先认定越早越好或越准确越好。**

“立即决定还是等待”的取舍已有气象决策基础；你的新工作应是把这种取舍落实到**异步多模态信息、可执行交互和模型实际行为**，而不是重新发明一个等待公式。([American Meteorological Society Journals](https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml "https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml"))

# 四、最值得强化的三个研究增量

## 增量一：评测“获取了什么信息”，而不只评测“拿到信息后怎么回答”

这是相较你当前方案最实质的变化。

现有 Evidence-Arrival Twin 主要由评测器决定给模型什么、何时给。新主任务则让系统参与决定：

**读取哪个站点、检查哪张地图、访问哪个预报产品、是否等待下一次发布。**

不过，系统只能操作已经允许的资料，不能通过查询提前获得尚未产生的未来观测。

### 关键的新测量：信息量与决策价值不是一回事

一份更详细的地图，可能减少很多不确定性，但不改变当前目标的决定。

一个看似很小的上游观测更新，却可能影响是否在截止前进入准备状态。

一份非常准确的产品，如果发布时已经错过准备窗口，对当前决定的价值可能有限。

因此，建议比较的不是“读取了多少资料”，而是：

> **在有限预算和剩余时间下，所选择的资料是否改善了最终预测与截止前决定？**

这也让多模态具有更清楚的作用：地图提供的空间关系，必须能够改变有意义的风险判断，而不仅是多一个视觉输入。

### 不要人为制造信息获取困难

这一点很重要。

不能为了让主动选择显得有用，把原本一秒能读取的公告规定为“消耗三十分钟”。应区分：

**真实产品等待时间、实际计算／网络耗时、以及明确标记的实验预算情景。**

完整历史读取、并行获取和低成本“全部读取”都应是合法强基线。它们在某些任务中足够好，就如实报告。

---

## 增量二：测量“预警机会为什么丢失”，而不只是列出错误答案

我建议把原有感知对照、版本追踪和状态干预重新组织为一个问题：

> **这次失败是因为当时根本没有足够信息，还是信息已经可用但系统没有正确利用？**

可以形成四种可区分的诊断：

| 诊断问题对照方式能得到什么解释 |                            |                          |
| --------------- | -------------------------- | ------------------------ |
| **证据取得失败**      | 在合法时间内，提供同一份本可取得却未被选择的资料   | 判断信息选择是否限制了表现            |
| **感知／对齐失败**     | 用该公开图像可支持的正确事实替代读图步骤       | 判断是否主要卡在视觉识别、时间或空间对齐     |
| **状态维护失败**      | 固定后续输入，进行实际状态、删除、编辑和参考状态对照 | 判断历史压缩、失效版本或错误状态是否影响后续   |
| **停止／决定失败**     | 固定同一条预测轨迹，仅替换预先规定的决定策略     | 判断问题是否发生在“何时停止等待、如何使用预测” |

其中，正确事实与参考状态都是**特权诊断条件**，不进入可部署系统排行榜。也不能把四个对照的改善简单相加成“失败原因百分比”，因为它们可能相互作用。

你原方案已经有感知与载体实验的基础；这里不是重新发明这些实验，而是把它们连接到**可观测的预警机会损失**上。

这种结果具有更直接的工程意义：

**应该投入更快的数据获取、更好的地图解析、更强的预测模型，还是更合理的停止策略？**

比“某模型在复杂灾害问答中得分较低”更能指导改进。

---

## 增量三：专门检验“极端情况下的信息失灵”，而不只是普通天气下的平均成绩

我建议把外推测试从简单的“换一个风暴”升级为：

**事件强度外推 × 信息条件外推 × 决策时限外推。**

为什么值得做？2026 年的研究在所测试的 GraphCast、Pangu-Weather、Fuxi 等模型与 HRES 的比较中发现：总体天气指标上的优势，并不必然延续到破纪录高温、低温和大风。这里的结论有具体模型和实验范围，不能外推成所有当前 AI 模型都不可靠，但足以说明平均排名不能代替尾部验证。([PubMed Central (PMC)](https://pmc.ncbi.nlm.nih.gov/articles/PMC13127558/ "https://pmc.ncbi.nlm.nih.gov/articles/PMC13127558/"))

建议分开测试：

\*\*强度外推：\*\*超过开发数据范围的事件，风险是否被系统性低估？

\*\*信息外推：\*\*关键来源缺失、产品延迟、不同来源不一致时，系统是否仍能维持校准和合理行动？

\*\*时限外推：\*\*同样的预测系统，在准备窗口较短时，是否还能保持有效性？

缺失与延迟可以有两种来源：真实日志支持的自然缺口，或明确标记的受控压力实验。**不能把人工生成的“极端事件时更容易断网”包装成已经观测到的灾害事实。**

你的 benchmark 不会因此解决物理预测的外推难题，但可以回答：**当底层模型进入不擅长的区域时，上层系统能否识别信息限制、切换可靠来源，而不是更加自信地放大错误？**

# 五、我还会加入一个很有针对性的难点：避免把“多个来源”误当成“多份独立证据”

这比单纯做跨模态一致性更贴近你已有的来源追踪能力。

可以构造两类严格区分的材料：

\*\*第一类：同一信息的多种表达。\*\*同一轮预报被呈现为文字、地图和摘要，或者同一文件被重新交付。

\*\*第二类：真正新增的信息。\*\*新站点观测、新观测时段，或另一条有明确来源关系的数据。

研究问题是：

> **模型是否因为看到了三种表达，就把同一条信息当成三次独立支持，从而不合理地提高置信度？**

这可以作为你的**来源谱系追踪如何产生预测价值**的具体证据，而不只是“引用版本必须正确”。

但要注意两点。

第一，不能要求任何重复输入后概率都逐字不变。模型可能利用再次阅读修正先前的理解错误；应该把这种合理修复与“重复数量导致的虚假确信”区分开。

第二，预测具有真实空间关联。不能仅因为新资料没有提到地点 B，就强制 B 的风险完全不变。原方案中的局部保持义务可以明确用于字段和公开依赖规则；扩展到概率预测时，需要更谨慎的语义控制。你现有方案已经提醒：不同变量、不同范围之间的表面不一致，不一定是真冲突。

# 六、评分必须从“更复杂的总分”转向“预测—时机—资源”三方面

## 6.1 预测层：保持标准、可解释的评分

继续采用前面讨论的概率预测评分，而不是为每次更新编造唯一正确概率。

每个固定检查点都要提交预测，之后不能覆盖旧记录。主结果按事件和提前量报告。

\*\*不能要求每次新证据到达都使预测更接近最终结果。\*\*一次合理的概率上调，也可能遇到最终没有发生的事件。单次结果不足以判断概率更新是否合理。

同时，不应允许模型只在有信心时提交、再只对这些提交评分。未提交、拒答、使用默认基线预测和正常作答，需要事先规定口径。

## 6.2 决策层：用公开成本模型，不依赖 LLM judge 评价“建议是否合理”

首版可以采用一个很小的标准研究模型。

设 `Y\in\{0,1\}` 表示目标事件是否发生；`a=1` 表示在截止前完成研究规定的准备决定，`a=0` 表示未完成。将事件损失归一化，准备成本比例为 `\rho`：

```math
\ell_\rho(a,Y)=\rho a+(1-a)Y.
```

这是一个**理想化的成本—损失模型**：假设及时准备可以避免所定义的这项损失。它不是实际撤离或防洪措施的效果声明。

在该模型中，若预测概率为 `p`，截止时的成本最小决定是比较 `p` 与 `\rho`。关于成本—损失模型及等待下一次预报的扩展，已有成熟研究可作为理论与基线依据。([American Meteorological Society Journals](https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml "https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml"))

你的评测增量不是这个公式，而是：

**概率怎样在实际信息约束下形成，何时形成，系统是否在仍能使用它的时候作出了决定。**

不要只选一个对自己方法有利的 `\rho`。应预先规定若干成本比例、准备时限和访问预算，报告策略表现曲线。

若以后获得可靠的真实成本、措施有效性和实施时间资料，可以做外部应用验证；在此之前，应称为**公开决策模型下的预警价值**，不能换算成“挽救多少生命”或“减少多少真实经济损失”。

## 6.3 资源层：预算内的质量与及时性同时报告

建议主表保留：

| 结果维度核心内容   |                              |
| ---------- | ---------------------------- |
| **预测质量**   | 概率评分、校准、不同提前量的表现             |
| **预警效果**   | 固定误报约束下的召回与有效提前量             |
| **研究决策价值** | 不同成本比例、准备截止时间下的损失，相对可部署基线的改善 |
| **信息效率**   | 读取、检索、图像处理、预测调用与状态维护的实际成本    |
| **可靠性**    | 旧版回退、证据重复计数、无效输出、错过截止和错误恢复   |

不要把这五项再相乘成一个很难解释的分数。也不要把 token、秒和经济损失直接相加，除非转换规则有明确依据。

# 七、必须改变数据抽样：不仅收集“已经发生的灾害”

这对实际意义非常关键。

如果每条 episode 都来自一场最终发生的灾害，系统会得到一个隐含提示：

> 这里肯定发生了值得研究的事情，积极报风险通常有利。

这会削弱对误报、校准和等待策略的评价。Extreme Weather Bench 已讨论这一“预报者困境”，并通过边缘事件等方式缓解，因此不能把问题描述成它完全没有注意。([arXiv](https://arxiv.org/html/2605.01126v1 "https://arxiv.org/html/2605.01126v1"))

我建议正式数据包含：

**实际发生的极端事件、接近阈值但未发生的情况、普通监测窗口，以及有较高早期预报风险但最终没有发生的情况。**

更进一步，任务生成应尽可能依据**事先可定义的区域、时间、阈值和监测规则**，而不是先看到最终灾情，再倒推最有戏剧性的输入序列。

需要区分两种用途：

\*\*诊断集：\*\*可以富集关键修订、旧版重放和困难事件，用于定位错误。

\*\*总体性能集：\*\*应保留或明确恢复目标使用场景中的事件频率，用于解释校准、误报和预警价值。

同一气旋及其诱发洪水、同一原始影像衍生的多份产品，也要按关联事件和共享来源分组，不能拆成独立训练／测试样本。你已有的共享 artifact 分组原则可以直接扩展。

# 八、论文应争取哪些真正有分量的实验发现？

我建议预先提出以下三个假设，但**不能以必须得到这些结果作为数据筛选条件**。

## 假设一：最终预测排名与限时预警价值排名可能不同

要检验的不是一句常识，而是：

**在真实资料到达序列上，排名差异是否稳定存在？在哪些提前量、成本比例和数据条件下出现？**

最有说服力的图是：

**同一批系统的预测评分排名，与不同准备窗口下的决策价值排名。**

若没有明显差异，也有意义：说明在该任务范围中，普通预测指标已经很好地代理了所测决策价值。不能为了制造反转继续改规则。

## 假设二：信息管理错误可能比底层预测能力差异更影响部分任务

固定同一个专业预报来源和同一个语言／视觉后端，仅改变：

**版本处理、来源去重、信息选择和停止策略。**

再与“只换成更强模型、策略不变”比较。

如果小型可靠策略在某些条件下比更强但不受控的模型更有效，你就获得一个有操作价值的结论：

> 系统升级不一定优先需要更大的模型，也可能需要更正确的信息时间与使用策略。

这不是预定结论，需要真实结果支持。

## 假设三：最有信息量的下一份资料，不一定是最值得读取的资料

比较以下选择策略：

**全部读取、随机选择、固定顺序、优先最新、优先减少预测不确定性，以及考虑剩余准备时间的价值导向选择。**

如果价值导向策略能在独立事件上改善时限内的决策表现，同时不过度增加误报，就说明 benchmark 测到的不只是检索相关性。

这组结果可以形成论文最核心的**质量—预算—提前量曲线**。

# 九、建议附带一个轻量参考方法，而不是只交付一个更难的排行榜

我会给论文配一个透明的参考系统，但不先训练新的天气基础模型。

结构可以很简单：

**专业预报基线 → 时间／来源有效性检查 → 当前证据状态 → 候选资料价值估计 → 获取或停止 → 提交预测与决定。**

这里有三项关键设计。

### 1. 以专业预报为基线，不让 LLM 凭语言自信随意改概率

专业集合预报、持久性预测和简单统计后处理都应纳入比较。

系统新增证据后是否修正基线、修正多少，需要在开发数据上验证和校准。官方预报本身已经很好时，保持或直接采用它是成功，不是“没有发挥智能体作用”。

### 2. 选择资料时估计“可能降低多少决策损失”，而不仅是相关性

这个估计可以先用开发集中的简单统计模型或小型策略实现。

\*\*不能用测试事件后来是否发生，反过来决定当前哪份证据最值得读。\*\*事后最佳资料只能作为明确标记的分析参照，不能伪装成在线策略。

### 3. 停止条件要考虑资料尚需等待多久

一份可能有用但要到截止后才能取得的产品，不应与立即可读的资料使用同样的选择标准。

不过，这种价值导向与停止思想已有决策理论和交互式信息获取的研究基础。论文方法的新颖性应落在你的具体建模、实现和验证上，不把通用“信息价值”重新命名后宣称首创。([American Meteorological Society Journals](https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml "https://journals.ametsoc.org/view/journals/mwre/149/5/MWR-D-20-0392.1.xml"))

**参考方法的意义是证明 benchmark 能引导实际改进，而不是要求你再同时完成一篇大型新模型论文。**

# 十、实施范围应更聚焦，而不是因为研究问题更激进就扩大工程

## 10.1 第一版只做一个主预测任务，加一个外推任务

我优先建议：

**主任务：降雨／河流水位相关的超阈值预警。**

理由是预测目标可以明确，观测结果能直接核验，空间信息、上游关系和多时刻证据也有明确角色。USGS 提供水位、流量等水文观测接口，NOAA NWPS 提供官方水文预报与相关信息。([Water Data APIs](https://api.waterdata.usgs.gov/ "https://api.waterdata.usgs.gov/"))

但这里有一个需要收紧的可行性判断：

\*\*不能因为 HEFS API 写着支持历史数据，就假设能直接获得多年逐轮预报。\*\*当前 NOAA 官方说明，实验性 HEFS API 目前提供约 **10 天数据**；常规 NWPS API 也不提供完整历史预报。多年版本需另外核查归档，或者从现在开始进行前瞻采集。([NOAA Water API](https://api.water.noaa.gov/about/api "https://api.water.noaa.gov/about/api"))

因此，先做档案可行性审查。若完整历史链不足，优先用已有气旋来源打通时间、预测提交和验证接口，不要为坚持某个灾种而伪造信息可用时间。

**外推任务：气旋的明确未来强度／位置目标，或另一种观测可核验的天气阈值任务。**

不要求首篇同时覆盖地震、野火、滑坡和复杂撤离。地震估计修订可以留作其他任务，不能与极端天气的发生前预测混成一个标签。

## 10.2 现有工作怎么保留？

| 已有资产在新论文中的角色                 |                |
| ---------------------------- | -------------- |
| Text Core、原文解析与版本评分          | 输入可靠性诊断和回归测试   |
| 多时间字段、来源哈希与交付记录              | 新交互环境的证据基础     |
| 多模态配准与区域引用                   | 地图证据理解和来源有效性检查 |
| 状态载体与后续查询                    | 有限预算下的历史保留机制   |
| Evidence twins、carrier audit | 预警失败的分层诊断      |
| 新增预测与决定记录                    | 不可事后修改的任务输出    |
| 新增观测结果与决策评估器                 | 把信息处理连接到可验证结果  |

这不是推倒重来，而是把已有模块放进一个更有意义的任务里。

## 10.3 最小新增工程可以只围绕三个接口

\*\*交互时间环境：\*\*决定哪些资料此刻可见，查询和等待如何消耗时间及预算。

\*\*预测／决定登记器：\*\*按固定目标和检查点保存真实提交，不允许覆盖早期结果。

\*\*结果与价值评估器：\*\*关联后续观测，计算预测质量和公开决策模型下的损失。

先做少量完整任务验证接口、资料真实性和评分。正式扩充规模应由独立事件覆盖决定，而不是把重复运行次数当作数据规模。

## 10.4 前瞻验证采用“影子运行”，不直接发布真实公众预警

系统按真实资料时间运行、提交并保存预测，但不替代官方预警，也不直接控制现实行动。

之后用观测结果评价。

这能补强“当时真的可用”和“预测确实先于结果”的证据，但仍不自动证明对任意模型完全无训练污染。历史公开数据的污染限制也已经在你的材料中说明。

GEE 可以服务于资料获取、空间计算和缓存；正式比较仍应使用冻结的证据批次，而不是让每个模型在不同日期自行读取变化中的 latest 数据。

# 十一、最后，论文的 novelty 应怎样写？

我建议收敛成三个贡献，而不是罗列“多模态、Agent、记忆、知识图谱、预测、AutoResearch”。

### 贡献一：一个新的、定义清楚的评测任务

**在外部资料发布时间、信息预算和准备截止时间共同约束下，评价智能体的信息获取、预测修订与及时决定。**

区别不只是有动态输入，而是**时间会改变一份证据能否被有效利用**。

### 贡献二：能够解释预警失败的测量协议

**用信息交付、感知替换、状态载体和停止策略的分层对照，区分无法获得信息、没有理解信息、没有保留信息和没有及时使用信息。**

不是因为最终答错就推断“记忆失败”，也不是因为最终答对就默认整个过程可靠。

### 贡献三：能够指导系统改进的实证与参考方法

**在真实事件、未发生事件、关键尾部和不同信息条件下，比较专业预测、简单策略及智能体，说明何种信息管理投入能改善可验证的预警价值。**

如果这些关系确实被数据和实验支持，论文就不仅是一个领域题库，而是一个**检验预警系统信息使用能力的实验平台**。

可以考虑的工作标题是：

> **DisasterTrace: Evaluating Active Evidence Acquisition and Forecast Revision for Timely Extreme-Weather Warning**

相应的一句话定位是：

> **DisasterTrace 不仅评测极端天气能否被预测，还评测系统能否在信息不完整、来源异步且准备时间有限时，主动获取有价值的证据，并将预测修订转化为及时、可验证且不过度误报的预警。**

## 我的最终判断

\*\*这条路线比继续强化“来源更新＋多模态记忆”的 headline 更有机会形成清晰的研究意义。\*\*但它的优势不在于某个组件从未出现，而在于改变了最终需要解释的现象：

**为什么一个看起来更聪明、最后预测更准的系统，仍可能错过有价值的预警机会？又怎样用可检查的策略避免这种失败？**

最值得保留的核心不是“必须让模型失败”，而是：

> **最后预测正确，不等于及时预警有效；DisasterTrace 要测清楚，系统如何在还有时间时，把可获得的信息转化成值得采取行动的判断。**

这既给出了比现有方案更激进的研究方向，也留下了可执行边界：**先解决“怎样可靠测量预警价值”，再用实际结果证明某种系统设计改善了它，而不是用更大的任务范围代替 novelty。**
